## 1. 문서와 구조를 먼저 읽을 수 있게 만든 것

- README 첫 화면을 프로젝트 개요와 현재 경계 중심으로 다시 정리하고, **시스템 구조**와 **데이터 흐름·실패 처리** 그림을 추가했다.
- 그림은 수집·연구·모의매매의 진행 단계를 분리해 보여 준다. 실제 코드 진입점은 파이프라인 지도, 설계 근거와 목표 구조는 별도 아키텍처 문서로 연결한다.
- 구조도에는 “2026-11-01 기준 운영 기록을 옮긴 그림이며 이 커밋의 코드가 보증하는 내용은 아니다”라는 경계를 남겼다. 문서 그림도 실행 근거와 같은 수준의 증거로 오해하지 않게 하기 위해서다.

## 2. 저장소 감사에서 고친 정확성 문제

- **장전 수집 공백은 실행을 바꾸지 않고 근거만 남긴다.** raw-v2 수집 세션 전체를 기준으로 장전 coverage를 판정해 연구·fast 결과와 manifest·exact bridge에 기록하도록 했다. 거래소와 무관한 시간대 게이트의 NXT 표현도 정리했다.
- **실패 종목을 성공한 것처럼 세지 않는다.** 종목 처리 성공 여부를 반환해 실패 종목을 별도 사유로 집계하고 universe 값에서 제외한다.
- **MDD는 시간순으로 계산한다.** 결과를 날짜·청산 시각 순으로 정렬한 뒤 MDD를 계산하고, 청산 규칙이 여러 개인 실행의 상위 MDD는 하나의 값으로 합치지 않고 비워 둔다.
- **NaN 손익을 통계에서 조용히 섞지 않는다.** 건수·승률·평균·일수 계산에서 제외하고 `pnl_missing`으로 따로 센다.
- **재현성 메타데이터 실패도 기록한다.** git SHA를 읽지 못하면 이유를 `git_sha_error`에 남긴다.
- **런 저장은 완성본만 보이게 한다.** 임시 staging 폴더에 모두 쓴 뒤 rename하고, overwrite 중 실패하면 이전 결과를 되돌릴 수 있게 했다.

## 3. 검증 결과와 남은 한계

- 감사 묶음 A·B를 합친 트리 전체 실행은 **5,678 passed · 0 failed · 35 skipped · 15 xfailed**로 기록됐고, 두 감사 브랜치의 수동 GitHub CI도 success였다.
- 다만 이 검증은 **합성 자료 중심**이다. 실제 런 값과 대시보드 화면은 다시 확인하지 않았다.
- 감사 묶음 A의 마지막 소규모 수정은 사용자 결정으로 별도 독립 리뷰를 거치지 않았다.
- 이전 전체 실행에서 간헐적으로 났던 Windows `WinError 5`는 이번 실행에서는 재발하지 않았지만 원인은 아직 확정하지 않았다.

## 4. 배운 점

- **결과 파일의 숫자뿐 아니라 결과를 만드는 계약도 정확성의 일부다.** 실패 종목, NaN, 시간 정렬, 코드 revision 기록이 틀리면 같은 백테스트라도 해석이 달라진다.
- **“기록만 추가”하는 변경과 “실행을 바꾸는” 변경을 분리하면 검증 범위가 선명해진다.** 장전 coverage는 우선 증거를 남기는 기능으로 넣고 거래 로직은 건드리지 않았다.
- **산출물 저장은 원자적으로 공개해야 한다.** 중간 상태가 완성본처럼 보이지 않게 staging → rename 경계를 두는 것이 재현성과 복구에 유리하다.
- **구조도에도 현재 구현, 운영 기록, 목표 설계를 구분해서 적어야 한다.** 그림이 보기 쉬운 만큼 실제보다 완성돼 보이는 위험도 있기 때문이다.
