## 1. 🏗️ 퀀트 백테스팅 엔진 모듈화 아키텍처 설계

### 1.1 기존 코드의 문제점 (Code Smell)
기존 백테스팅 코드 분석 결과, 포트폴리오로 제출하기엔 다음과 같은 결함이 존재했음:
1. **하드코딩된 절대 경로:** `C:\Users\user\...` 로컬 경로로 인해 타 컴퓨터 실행 불가.
2. **거대한 단일 파일 (God Class):** DB 조회, 캔들 생성, 지표 연산, 손절/익절이 한 파일에 밀집되어 유지보수 불가능.
3. **실행 재현성 부족:** 600MB 규모의 대용량 DB로 인해 깃허브 업로드(100MB 제한) 및 빠른 실행 검증 불가.

### 1.2 모듈 분리 아키텍처 (7-Module Architecture)
역할과 책임을 단일화하는 단일 책임 원칙(SRP)에 따라 패키지를 재설계함.

```text
Stock/
├── pyproject.toml         # uv 기반 선언적 의존성 명세
├── uv.lock                # 버전 및 해시 동결 잠금 파일
├── REFACTORING_PLAN.md    # 리팩토링 로드맵 문서
├── config.py              # pathlib 기반 상대 경로 및 파라미터 통합
├── utils.py               # 호가단위, 상한가, 시간차 순수 함수 유틸
├── data_loader.py         # 일봉 CSV 및 SQLite LOB DB 연결 전담
├── risk_manager.py        # 손절, 익절, 트레일링 스탑 제어
├── strategy.py            # 호가 잔량 및 윈도우 시그널 연산
├── engine.py              # 백테스팅 핵심 실행 조율기
└── run_parallel.py        # 멀티프로세스 병렬 가동 및 자동 결과 병합
```

## 3. 🧠 깊이 있는 CS/자료구조 고민: Hash Table vs B-Tree

### 3.1 파이썬 `dict`/`set`의 해시 테이블 ($O(1)$)
* 파이썬 내장 `dict`와 `set`이 $O(1)$의 탐색 속도를 보임을 테스트함.
* `set`은 단순 기능이 아니라 해시 테이블 기반의 독립된 자료형이며, "Value 없이 Key만 모아둔 딕셔너리"임을 확인.

### 3.2 왜 관계형 DB(RDB)는 더 느린 B-Tree($O(\log N)$)를 사용할까?
* **핵심 깨달음:** 해시는 단건 조회는 $O(1)$로 빠르지만, 결과값이 무작위로 분산되어 **범위 검색(`WHERE price BETWEEN 10000 AND 50000`)이나 정렬(`ORDER BY`)이 원천적으로 불가능함.**
* 따라서 DB는 정렬 상태를 유지하며 리프 노드 스캔이 가능한 B-Tree/B+Tree 인덱스를 채택한다는 시스템적 이유를 이해함.

## 4. 🛠️ 트러블슈팅 기록 (Troubleshooting)

### 이슈 1: 한글 깨짐 및 CSV 인코딩 에러 (`SAMG엔터` ➔ `SAMG`)
* **원인:** 파이썬 파일 저장 시 `encoding='euc-kr'`로 저장되어 VS Code 및 OS 기본 `UTF-8` 환경과 충돌 발생.
* **해결:** 모든 데이터 저장 로직을 **`encoding='utf-8-sig'`**로 통일함. BOM(Byte Order Mark)이 추가되어 엑셀, VS Code, Linux 환경 모두에서 한글이 절대 깨지지 않도록 방어.

### 이슈 2: 대용량 데이터 백테스팅 속도 지연
* **원인:** 단일 프로세스 연산 시 1초 단위 호가 데이터 처리 시간이 지연됨.
* **해결:** `multiprocessing.Pool`을 도입하여 CPU 코어별로 분할 백테스팅을 수행하고, 완료 즉시 `pd.concat`으로 결과를 자동 병합하는 파이프라인 구축 (실행 시간 최대 80% 이상 단축).
