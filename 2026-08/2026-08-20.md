## 1. SQL & 데이터베이스 엔지니어링 심화

### 1.1 SQL 논리적 실행 순서와 `WHERE` vs `HAVING`의 본질
- **문제 인식:** `WHERE`와 `HAVING`이 둘 다 조건 필터링인데 왜 분리되어 있는지, 파이썬의 중첩 if문처럼 단일 키워드로 해결할 수 없는지 의문 발생.
- **아키텍처적 분석:**
  - **SQL 실행 파이프라인:** `FROM` ➔ `WHERE` (행 필터) ➔ `GROUP BY` (그룹화) ➔ `HAVING` (집계 필터) ➔ `SELECT` ➔ `ORDER BY`
  - **성능 최적화(I/O 절약):** 1,000만 건 중 불필요한 데이터를 `WHERE`로 먼저 버려야 메모리에 최소 데이터만 올려 `GROUP BY` 연산을 수행할 수 있음.
  - **서브쿼리 등가성 실험:** `HAVING`은 사실 서브쿼리 + `WHERE`의 단축 문법(Syntactic Sugar)임을 증명.
    ```sql
    -- HAVING을 대체하는 서브쿼리 중첩 WHERE 방식 (파이썬 if 중첩과 동일한 원리)
    SELECT review_score, review_count
    FROM (
        SELECT review_score, COUNT(*) AS review_count
        FROM order_reviews
        GROUP BY review_score
    ) AS sub
    WHERE review_count >= 10000
    ORDER BY review_count DESC;
    ```

### 1.2 `COUNT(DISTINCT)` 및 `UNION` / `UNION ALL` 연산 메커니즘
- **고유 집계 문법:** `SELECT COUNT(DISTINCT order_id)` 형태로 집계 함수 내부에 `DISTINCT`를 주입해야 중복 제거 카운팅이 정상 수행됨.
- **`UNION` vs `UNION ALL`:**
  - `UNION`: 해시/정렬 연산 기반 중복 행 제거 (고유값 유지, 연산 비용 발생)
  - `UNION ALL`: 단순 수직 연결 (중복 유지, 연산 속도 빠름)
- **트러블슈팅 (DBeaver Statement Delimiter):**
  - `UNION` 쿼리 중간에 빈 줄(Blank Line)이 포함될 경우, DBeaver 기본 파서가 빈 줄을 문장 구분자로 인식하여 상단 `SELECT`문 1줄(1,019건)만 단독 실행하는 함정 발견.
  - **해결:** 단일 쿼리 내부에는 빈 줄 없이 붙여 쓰는 스타일 표준화 및 `SELECT COUNT(*)` 서브쿼리 래핑을 통한 즉각적인 건수 비교 기법 수립.

### 1.3 `LEFT JOIN`과 데이터셋 참조 무결성(Referential Integrity) 분석
- **실험:** Olist 데이터셋에서 `products` LEFT JOIN `order_items` 수행 후 `oi.order_id IS NULL`인 미주문 상품을 조회했으나 **0건** 출력.
- **원인 분석:** Kaggle Olist 데이터셋 생성 시 실제 주문이 발생한 상품만을 필터링하여 `products.csv`를 구성했기 때문에, 두 테이블 간 고유 `product_id` 개수가 32,951개로 100% 일치하는 데이터 특성 때문임을 확인.
- **검증:** 실제 불일치 데이터가 존재하는 `orders` LEFT JOIN `order_reviews` (리뷰 미작성 주문) 조합으로 조인 시 `NULL`이 정상 생성됨을 교차 검증.

### 1.4 PostgreSQL 인스턴스 vs Database vs Schema 계층 구조

| 계층 | 비유 | 분리 목적 |
| :--- | :--- | :--- |
| **PostgreSQL Instance** | 건물 (서버 프로세스) | CPU/RAM 물리 리소스 격리, 서버 전역 설정(`postgresql.conf`), 운영/개발 서버 분리 |
| **Database (DB)** | 독립된 호수 (101호) | 프로젝트 간 완전 물리/논리 격리, 독립 백업/복구, 크로스 쿼리 불필요 시 |
| **Schema** | 집 내부 방 (거실/안방) | 동일 프로젝트 내 도메인 분리, 스키마 간 자유로운 `JOIN` 필요 시 |

## 2. Stock 퀀트 플랫폼 저장소 통합 (Phase 2)

│   ├── config.py / utils.py / data_loader.py
│   ├── strategy.py / risk_manager.py / engine.py
│   └── main.py / run_parallel.py
├── dashboard/                   # 📈 Streamlit 분석 & Ollama AI 대시보드
│   ├── __init__.py / app.py
│   ├── analyzer.py / charts.py / data_service.py / metrics.py / ollama_client.py

### 2.2 트러블슈팅 및 해결 과정

#### 🚨 이슈 1: 패키지 디렉토리 이동에 따른 `BASE_DIR` 경로 불일치
- **문제:** `engine/main.py` 실행 시 `sampledata/Daily` 경로를 찾지 못하고 `⚠️ 일봉 데이터(open.csv 등)를 읽을 수 없습니다.` 경고 발생.
- **원인:** `engine/config.py`의 `BASE_DIR`이 `Path(__file__).resolve().parent`로 되어 있어 `Stock/engine/sampledata`를 탐색함.
- **해결:** `BASE_DIR = Path(__file__).resolve().parent.parent`로 수정하여 프로젝트 최상단 루트(`Stock/`)를 정상 참조하도록 수정.

#### 🚨 이슈 2: 파이썬 모듈 실행 시 네임스페이스 충돌
- **문제:** `uv run python engine/main.py` 실행 시 `ModuleNotFoundError: No module named 'engine.config'; 'engine' is not a package` 발생.
- **원인:** 스크립트 직접 실행 시 파이썬이 `engine/` 폴더를 `sys.path[0]`으로 잡아, 동명의 `engine.py` 파일과 `engine/` 패키지를 혼동함.
- **해결:** `uv run python -m engine.main` 모듈 실행 방식을 적용하고, `main.py` 내부 임포트를 `from engine.engine import BackTestEngine`으로 정밀 지정하여 해결.

#### 🚨 이슈 3: 백테스트 가동 후 거래 결과 0건 발생
- **문제:** 백테스트는 정상 완료되었으나 `results/cross_Today_1.csv`의 저장 건수가 0건으로 기록됨.
- **원인:**
  1. `engine.py`에 기아(`000270`) 1개 종목만 테스트하도록 `if code != '000270': continue` 하드코딩 필터가 걸려 있었음.
  2. 리팩토링된 `strategy.py`의 `check_entry_conditions()` 내부에서 계산되지 않은 지표(`max10_trigger`, `ctotal`, `amt_10s`)를 참조하여 항상 `False`를 반환함.
- **해결:** 기아 제한 필터를 해제하고, 시가 돌파 및 매수세(`cbv_5`, `cbv_1`) 기반 시그널 조건으로 정상화.

#### 📦 대시보드 에셋 물리적 복사 완료
- `app.py`, `dashboard/*.py`, `pages/*.py`, `results/cross_Today_1.csv`를 `Stock/` 디렉토리 내부로 안전 복사 완료 (`dashboard/__init__.py` 패키징 완료).
