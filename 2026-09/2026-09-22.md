## 1. 오늘 배운 것

### 1.1 프로덕트 분석은 분석 기법이 아니라 질문에서 시작한다

오늘 수업의 전체 흐름은 다음처럼 연결됐다.

> 서비스 상황 이해 → 데이터 확인 → 분석 질문 → 사용자 행동 분석 → 문제 구체화 → 원인 가설 → 개선안 → A/B 테스트 → 제품 의사결정 → 다시 측정

처음부터 “Funnel을 해보자”, “Retention을 계산하자”라고 정하는 것이 아니라, 먼저 서비스가 무엇을 궁금해하는지와 현재 데이터로 무엇을 확인할 수 있는지를 연결해야 한다.

- **AARRR:** 서비스 전체에서 어떤 행동을 더 자세히 볼 필요가 있는가?
- **Funnel:** 특정 목표 행동까지 가는 과정에서 어디에서 많이 이탈하는가?
- **Retention / Cohort:** 사용자가 시간이 지나도 다시 이용하는가?
- **Segmentation:** 특정 사용자 집단에서 차이가 더 크게 나타나는가?
- **A/B Test:** 개선안을 실제로 적용했을 때 행동이 달라지는가?

첫 분석 결과가 끝이 아니라 **다음 분석 질문의 출발점**이라는 점이 핵심이다.

### 1.2 이벤트 수와 고유 사용자 수는 다르고, AARRR은 Funnel이 아니다

한 사용자가 `view_course`를 세 번 수행했다면 이벤트 수는 3이지만 고유 사용자 수는 1이다.

그래서 “조회가 몇 번 일어났는가?”에는 이벤트 수가 적절할 수 있지만, “몇 명이 조회했는가?”에는 고유 사용자 수가 더 적절하다. AARRR과 Funnel에서도 주로 `nunique()`로 행동에 도달한 사람 수를 센다.

오늘 `product_1` 수업 데이터의 AARRR 결과는 다음과 같았다.

| 단계 | 사용자 수 | 전체 사용자 대비 |
| :--- | ---: | ---: |
| Acquisition | 260 | 100.0% |
| Activation | 150 | 57.7% |
| Retention | 62 | 23.8% |
| Revenue | 28 | 10.8% |
| Referral | 23 | 8.8% |

이 숫자를 순차 Funnel처럼 읽으면 안 된다. 각 비율은 전체 사용자 260명을 기준으로 서로 다른 행동을 본 값이다.

반면 Funnel에서는 이전 단계를 분모로 사용한다.

$$
Conversion_i = \frac{|S_i|}{|S_{i-1}|}
$$

$$
Drop_i = 1 - Conversion_i
$$

구독 Funnel은 `visit → view_course → start_trial → subscribe`였고 실제 결과는 다음과 같았다.

| 단계 | 사용자 수 | 이전 단계 대비 전환율 | 이탈률 |
| :--- | ---: | ---: | ---: |
| 방문 | 260 | 100.0% | 0.0% |
| 강의 조회 | 235 | 90.4% | 9.6% |
| 무료 체험 시작 | 132 | 56.2% | 43.8% |
| 유료 구독 | 28 | 21.2% | 78.8% |

따라서 데이터에서 직접 확인할 수 있는 사실은 **무료 체험 시작 → 유료 구독 구간에서 이탈이 크다**는 것이다. 가격이 비싸다, 결제가 불편하다, 콘텐츠가 부족하다는 설명은 아직 원인 가설이다.

> Funnel은 **어디서(Where)** 문제가 보이는지 알려 주지만, **왜(Why)** 그런지는 증명하지 않는다.

### 1.3 Retention은 숫자보다 정의와 시간 창을 먼저 봐야 한다

이번 실습에서는 가입일을 Day 0으로 놓고 Day 1, Day 7, Day 14에 **정확히 `visit` 이벤트가 있었는지**를 Retention으로 정의했다.

핵심 계산은 결국 다음 의미다.

```python
visit_df["day"] = (
    visit_df["event_time"].dt.normalize()
    - visit_df["signup_date"].dt.normalize()
).dt.days
```

즉,

$$
day = 방문일 - 가입일
$$

이다.

이 정의에서는 Day 7 Retention이 Day 1보다 높을 수도 있다. 실제 데이터의 2026-09-10 Cohort는 Day 1 38.9%, Day 7 44.4%, Day 14 22.2%였다.

이는 누적 생존율이 아니라 **각 날짜에 정확히 다시 방문했는가**를 독립적으로 확인한 값이기 때문이다. 같은 “Retention”이라도 정확히 N일째, N일 이내, N일 이후, 특정 구간 내 활동 등 정의에 따라 숫자의 의미가 달라진다.

### 1.4 A/B 테스트는 결과 차이보다 실험을 믿을 수 있는지 먼저 확인한다

2장 5강 실습에서는 `WA_Marketing-Campaign.csv`를 이용해 A/B 테스트의 핵심 설계 오류를 점검했다.

실제 데이터에서

- A: 172행, 43개 매장
- B: 188행, 47개 매장

이었다.

같은 매장이 4주 동안 반복 기록되어 있으므로 표본 단위는 행이 아니라 `LocationID`, 즉 매장이다.

또한 무작위 배정은

$$
P(A)=P(B)=0.5
$$

를 의미하지, 결과가 정확히 50:50이어야 한다는 뜻은 아니다. 100개 매장을 0.5 확률로 배정했을 때 53:47이 나오는 것은 가능한 결과다. 반대로 숫자가 정확히 50:50이라고 해서 무작위 배정 절차가 정상적이었다는 증거도 아니다.

오늘 정리한 대표적인 실험 설계 오류는 다음 네 가지다.

- **Novelty Effect:** 처음에는 새로운 처치에 반응하지만 시간이 지나며 효과가 약해질 수 있음
- **Sample Contamination:** 같은 대상이 A와 B를 모두 경험해 효과가 섞임
- **Early Stopping:** 유리한 중간 결과를 보고 예정 기간 전에 임의 종료
- **SRM(Sample Ratio Mismatch):** 예정 배정 비율과 관측 비율이 지나치게 달라 배정·수집 이상을 의심해야 함

실제 WA 데이터의 매장별 4주 평균 주간 매출의 집단 평균은 A 58.099, B 47.329, B−A -10.770(천 단위)이었다.

하지만 이 관측 평균만으로 “B가 매출을 감소시켰다”는 인과 효과를 확정할 수는 없다. 실제 무작위 배정 절차, 목표 표본 수, 예정 기간과 종료 기준은 CSV만으로 확인할 수 없기 때문이다.

### 1.5 유의한 핵심 지표 개선도 제품 적용의 충분조건은 아니다

`product_1`의 실제 A/B 데이터에서는

- A 구독 전환율: 23.3%
- B 구독 전환율: 27.4%
- 절대 차이: +4.1%p
- 상대 개선율: 약 +17.6%
- 두 비율 z-test: $p \approx 0.0351$

로 B의 구독 전환율이 높게 나타났다.

하지만 가드레일 지표는

- 결제 오류율: A 2.3% → B 3.4%
- 구독자 기준 취소율: A 4.72% → B 5.47%

로 B가 수치상 더 높았다.

따라서 `p < 0.05`라는 사실만으로 바로 B를 전면 적용한다고 결론 내리면 부족하다. 목표 지표, 통계적 근거, 효과 크기, 가드레일, 배정·수집·적용의 정상성을 함께 봐야 한다.

2장 5강 교육용 사례에서도 매출이 50 → 55로 좋아졌지만 환불률이 2% → 5%로 악화되는 예를 통해 같은 점을 확인했다.

### 1.6 프로젝트 분석에서는 먼저 테이블의 grain과 연결 키를 이해해야 한다

3장 1강 RavenStack 실습에서는 5개 테이블을 먼저 탐색했다.

- `accounts`: 계정 단위
- `subscriptions`: 구독 이력 단위
- `feature_usage`: 기능 사용 기록 단위
- `support_tickets`: 문의 티켓 단위
- `churn_events`: 이탈 이벤트 단위

연결 구조도 모두 같지 않다.

- `accounts.account_id ↔ subscriptions.account_id`
- `subscriptions.subscription_id ↔ feature_usage.subscription_id`
- `accounts.account_id ↔ support_tickets.account_id`
- `accounts.account_id ↔ churn_events.account_id`

특히 `accounts`와 `subscriptions` 모두 `churn_flag`라는 이름의 컬럼이 있지만, 계정의 대표 이탈 지표는 수업에서 **`accounts.churn_flag`**로 정의했다.

> **컬럼 이름보다 grain과 지표 정의가 먼저다.**

### 1.7 현재 상태 지표와 미래 개선 목표 지표는 다를 수 있다

RavenStack 데이터에서 전체 계정의 `churn_flag` 평균은 22.00%였고, 표본 20개 이상 산업 중 DevTools는 30.97%(n=113)로 가장 높게 관찰됐다.

여기서 “DevTools이기 때문에 이탈한다”고 말할 수는 없다. 현재 가능한 문제 정의는 다음 수준이다.

> DevTools 계정에서 상대적으로 높은 누적 이탈 비율이 관찰되므로 초기 사용과 지원 경험의 개선 가능성을 조사한다.

또한 `accounts.churn_flag.mean()`으로 얻은 값은 현재 스냅샷에서 과거 이탈 경험을 가진 계정의 비율이지, 특정 기간에 새로 이탈한 비율은 아니다.

그래서 개선 목표를

> 다음 분기 시작 시 활성인 DevTools 계정을 고정 모집단으로 두고 90일 내 신규 이탈 비율을 대조군 대비 5%p 낮춘다.

처럼 미래 평가 지표로 새로 정의했다.

여기서 **5% 감소와 5%p 감소도 다르다.** 30% → 25%는 5%p 감소이며, 상대적으로는 약 16.7% 감소다.

### 1.8 원인 후보 데이터는 결과보다 먼저 발생해야 한다

RavenStack에서 만든 초기 가설 중 하나는

> 초기 기능 사용이 적은 계정은 이후 이탈이 많다.

였다.

이를 검증하려면 가입 후 초기 30일 기능 사용량과 그 이후 90일 이탈처럼 시간 순서를 지켜야 한다. 이탈 이후 발생한 사용 행동을 “이탈의 원인 후보”로 넣으면 미래 정보가 과거 설명에 섞이는 leakage가 된다.

지원 경험도 마찬가지다. “지원 해결이 느린 계정은 이후 이탈이 많다”를 보려면 **이탈 전에 발생한 문의와 해결 시간**만 사용해야 한다.

관찰 데이터에서 연관성을 확인하는 것과 인과 원인을 확정하는 것은 별개의 단계이며, 최종 원인 검증에는 A/B 테스트 같은 개입 실험이 필요할 수 있다.

## 2. 내가 궁금했던 질문과 이해한 답

### Q1. Churn rate는 그냥 이탈률인가?

보통 **Churn rate = 이탈률**이라고 번역한다.

다만 지표 정의는 반드시 함께 봐야 한다. 오늘 `accounts.churn_flag.mean()`으로 계산한 22%는 “현재 데이터에서 과거 이탈 경험이 있는 계정 비율”에 가깝다.

반면 “향후 90일 신규 churn rate”를 정의한다면 예를 들어

$$
Churn\ Rate =
\frac{\text{90일 안에 새로 이탈한 계정 수}}
{\text{기간 시작 시점의 활성 계정 수}}
$$

처럼 시간 창과 모집단이 명시되어야 한다.

### Q2. `v.isna().sum()[v.isna().any()].to_dict()`는 왜 복잡해 보이나?

다음 한 줄은 여러 연산을 메서드 체인으로 압축한 코드다.

```python
v.isna().sum()[v.isna().any()].to_dict()
```

풀어쓰면 다음과 같다.

```python
missing_count = v.isna().sum()
has_missing = v.isna().any()
missing_only = missing_count[has_missing]
result = missing_only.to_dict()
```

- `isna()`: 각 값이 결측인지 True/False
- `sum()`: 컬럼별 결측 개수
- `any()`: 컬럼에 결측이 하나라도 있는지
- `[has_missing]`: 결측이 존재하는 컬럼만 선택
- `to_dict()`: 딕셔너리로 변환

그리고 `{k: ... for k, v in data.items()}`는 각 테이블에 대해 같은 작업을 수행하는 dict comprehension이다.

### Q3. 이런 한 줄짜리 코드는 AI가 주로 쓰는 스타일인가?

아니다. dict comprehension과 pandas method chaining은 사람이 작성하는 Python 코드에서도 흔하다.

다만 한 줄에 너무 많은 조건과 변환을 넣는 것이 항상 좋은 코드는 아니다. 의미가 바로 읽히는 짧은 변환은 한 줄이 편하지만, 필터·조건·변환이 여러 단계면 중간 변수로 나누는 편이 유지보수에 유리하다.

### 3.3 Stock — execution 현실성 계약과 독립 oracle 검증

Stock에서는 production 구현을 그대로 복제하지 않는 독립 oracle과 bounded exhaustive·metamorphic 검증으로 TickSimulator를 감사했다.

독립 감사 과정에서 NUM-1과 RUN-1 반례를 발견했고, 이후 정확 유한소수 장부와 예약 provenance fail-closed 검증으로 각각 닫았다.

두 수정의 통합 검증은 `1,418 passed, 6 deselected, 0 xfailed`였고, 후속 합성 lab에서는 `1,454 passed, 6 deselected, 0 failed, 0 xfailed`까지 확인했다. 다만 합성 검증 성공이 실제 운영 raw의 whole-file qualification·백테스트·실거래 승인 완료를 뜻하지는 않는다.

### 3.4 Airplane — 날씨 동일조건 평가와 제출용 문서 정리

Airplane은 동일한 180,332개 평가행과 동일 fold에서 weather-off/on을 비교했다.

| 지표 | 날씨 미사용 | 날씨 사용 | 변화 |
| :--- | ---: | ---: | ---: |
| Macro F1 | 0.573910 | 0.598945 | +0.025035 |
| LogLoss | 0.448116 | 0.436689 | -0.011428 |
| ROC-AUC | 0.640618 | 0.672936 | +0.032317 |

세 지표가 모두 개선됐지만 10분 publication latency는 실제 지연을 측정한 값이 아니라 고정 가정이고, 동일 데이터의 paired CV 결과가 날씨의 인과 효과나 미래 배포 성능을 증명하는 것은 아니다.

최종 README는 개발 순서보다 평가자의 질문 순서대로 문제·데이터·평가·결과·한계·재현 방법을 읽을 수 있게 정리했다.

### 3.5 career-agent — 근거 기반 선호 정책과 공개 채용공고 discovery

career-agent에서는 공개 프로젝트 근거, ownership, 개인 선호, 외부 공고 수집을 서로 다른 계약으로 분리했다.

개인 선호에서는 90분 통근을 soft preference로 두고, 회사 규모·하이브리드·주거지원처럼 외부 근거가 없는 정보는 `unknown`으로 유지한다.

공개 채용보드 discovery에서도 실패 응답을 공고 만료로 추론하지 않고 게시일·경력·회사 규모·근무형태 등 근거 없는 값을 `unknown`으로 보존하는 원칙을 유지했다.

자동화가 커질수록 빈칸을 그럴듯하게 채우는 것보다 **근거가 없는 상태를 그대로 보존하는 것**이 중요하다는 점을 다시 확인했다.

## 4. 아직 헷갈리는 것 / 다음에 확인할 것

### Product Analytics

- Churn rate와 Retention을 볼 때 항상 모집단·분모·시간 창을 먼저 확인한다.
- 현재 스냅샷의 누적 상태 지표와 미래 실험에서 사용할 신규 발생 지표를 구분한다.
- 여러 테이블을 JOIN할 때 결과 행 수보다 각 테이블의 grain과 1:N 관계를 먼저 확인한다.
- Segmentation에서 차이가 보여도 해당 속성을 원인으로 바로 해석하지 않는다.

### A/B Test

- MDE, power, sample size의 관계를 실제 숫자로 다시 계산해 본다.
- SRM은 단순 불균형과 어떻게 구분하고 어느 정도 차이부터 이상 신호로 보는지 검정 방식까지 이어서 확인한다.
- Guardrail Metric의 허용 기준은 통계적 유의성만이 아니라 제품·사업 기준과 함께 사전에 정해야 한다.

### Python / Pandas

긴 method chaining이나 comprehension을 만나면 한 번에 외우려 하지 않고, 중간 결과를 변수로 나눠 자료형과 shape가 어떻게 바뀌는지 확인한다.

### 프로젝트 운영

Stock·Airplane·career-agent에서도 오늘 수업과 같은 기준을 적용한다. **관찰된 결과, 원인 가설, 실제로 검증한 범위, 다음 의사결정**을 한 문장에 섞지 않고 단계별로 기록한다.
