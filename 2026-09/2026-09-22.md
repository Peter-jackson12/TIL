## 1. 오늘 배운 것

### 1.1 독립 oracle은 production과 같은 버그를 공유하지 않아야 한다

시뮬레이터 테스트가 production 내부 함수나 같은 수치 계산식을 그대로 재사용하면, 구현과 테스트가 같은 실수를 공유할 수 있다. Stock의 execution 감사에서는 production import 없이 `Fraction` 기반 상태 전이로 별도 oracle을 만들고, 작은 유한 공간을 전수 비교했다.

기본 감사 범위는 다음과 같았다.

- 6,912개 parameter/program 조합
- 40,692개 공개 호출 후 checkpoint
- lifecycle, resources, quote clock, 호출열(words), fee 행렬을 분리해 검사
- 실제 전략 `fixed`, `tick_trail`, `step_trail`도 작은 합성 fixture와 여러 chunk 분할에서 별도 대조

여기서 중요한 점은 **6,912개를 모두 통과했다 = 모든 가능한 입력에서 증명됐다**가 아니라는 것이다. 작은 정수·유한 소수·정해진 호출열이라는 bounded domain에서 강한 회귀 근거를 얻은 것이고, 범위 밖 Decimal·임의 API 호출열·실시장 구조까지 자동으로 인증되는 것은 아니다.

### 1.2 metamorphic test는 정답 하나보다 '바뀌면 안 되는 관계'를 검사한다

정확한 기대값을 매번 손으로 만들기 어려운 실행 엔진에서는 입력을 변형했을 때 유지되어야 하는 관계를 검사하는 것이 유용하다.

Stock 감사에서 확인한 예시는 다음과 같다.

- 완료된 prefix 뒤에 미래 suffix를 붙여도 이미 확정된 결과는 바뀌지 않아야 한다.
- 허용된 chunk 경계로 같은 이벤트를 나눠도 결과 identity가 유지되어야 한다.
- 미사용 provenance를 바꾸면 경제 결과는 같아야 하지만 provenance hash와 reproducibility key는 달라져야 한다.
- 단일 고정 buy에서 fee를 높였는데 체결 가능 수량이 늘어나면 안 된다.

반대로 `advance()` 호출을 더 잘게 나누는 것은 항상 불변이 아니었다. deadline과 endpoint 사이에 매칭 라운드가 추가되면서 자원 재시도·stale 경계가 달라질 수 있기 때문이다. **불변이라고 가정하기 전에 실제 계약이 그 관계를 보장하는지 먼저 정의해야 한다**는 점을 다시 확인했다.

### 1.3 수치 안정성은 '대충 높은 precision'보다 장부 불변식을 직접 지키는 쪽이 강하다

독립 oracle 감사에서 NUM-1 반례가 발견됐다.

- `cash = 1.01`
- `ask = 1.01`
- `fee_rate = 0.005`
- Decimal context: `prec=3`, `ROUND_HALF_EVEN`

정확한 1주의 비용은 `1.01505`라서 현금보다 크다. 하지만 옛 구현은 중간 반올림 때문에 1주를 허용했고 `cash=-0.01`을 만들 수 있었다.

수정에서는 affordability 계산만 따로 보정하거나 사후에 현금을 0으로 clamp하지 않고, **체결 수량·gross·fee·cash 장부 전체를 bounded exact finite-decimal 연산으로 일치**시켰다. 그 결과 `buy의 정확 비용 <= 체결 직전 cash`, `체결 후 cash >= 0` 같은 불변식을 mutation 전에 검사한다.

이 사례에서 배운 점은 다음과 같다.

> 수치 버그를 숨기는 후처리보다, 상태를 바꾸기 전에 경제적 불변식이 성립하는지를 확인하는 편이 훨씬 안전하다.

### 1.4 CI success와 미해결 결함 0개는 같은 말이 아니다

Stock의 첫 oracle 감사 PR은 CI가 성공했지만 NUM-1과 RUN-1을 `strict xfail`로 명시적으로 남겼다. 즉 **CI success는 알려진 실패를 숨겼다는 뜻이 아니라, 그 실패가 예상된 미해결 경계로 정확히 기록됐다는 뜻**이었다.

그 뒤 NUM-1은 정확 장부 수정으로, RUN-1은 예약 provenance를 출력 생성 전에 fail-closed 검증하는 방식으로 각각 별도 수정됐다. 두 수정의 합집합 검증에서는 전체 Git-only가 `1,418 passed, 6 deselected, 0 xfailed`까지 올라갔다.

따라서 테스트 숫자를 볼 때는 `passed`, `deselected`, `xfail`, 실제 데이터 실행 여부를 따로 읽어야 한다.

### 1.5 동일조건 비교는 '같은 평가행과 같은 fold'를 먼저 고정해야 한다

Airplane의 weather-off/on 비교는 날씨를 넣었을 때와 넣지 않았을 때를 **동일한 180,332개 평가행, 동일한 outer fold fingerprint, 동일 seed 42/1/7**에서 비교했다. 날씨 사용 조건도 10분 publication-latency **가정**과 고정 14개 weather feature만 사용했다.

3-seed 평균은 다음과 같이 기록됐다.

| 지표 | 날씨 미사용 | 날씨 사용 | 사용 - 미사용 |
| :--- | ---: | ---: | ---: |
| Macro F1 | 0.573910 | 0.598945 | +0.025035 |
| LogLoss | 0.448116 | 0.436689 | -0.011428 |
| ROC-AUC | 0.640618 | 0.672936 | +0.032317 |

세 지표 모두 개선됐지만, 여기서도 해석 경계가 중요하다.

- 10분은 실제 공개 지연을 측정한 값이 아니라 사전 고정한 가정이다.
- 같은 평가행에서 성능이 좋아졌다는 것이 날씨의 인과 효과를 증명하는 것은 아니다.
- 현재 데이터의 paired CV 결과가 미래 운항 환경에서도 그대로 유지된다고 일반화할 수 없다.

즉 **비교 설계를 통제한 것**과 **현실 전체를 증명한 것**은 구분해야 한다.

### 1.6 최종 README는 개발 순서보다 독자의 질문 순서로 재구성하는 편이 낫다

Airplane 제출용 README는 최종 결과가 이미 나온 뒤에도 초기 수집 상태·운영 로그가 상단에 남아 있어 처음 읽는 사람이 결론에 도달하기 어려웠다. 오늘 최종 문서 작업에서는 상단을 다음 순서로 바꿨다.

1. 무엇을 예측하는가
2. 최종적으로 무엇이 개선됐는가
3. 데이터와 평가 분모가 무엇인가
4. 어디까지 해석할 수 있고 어디부터는 과장인가
5. 그 뒤에 재현 방법과 역사적 실행 기록

시각화도 변화량만 보여 주는 대신 **전후 실제 수준 + 변화량 + 해석 경계**를 같이 보여 주도록 정리했다. 개발 이력은 버리지 않되, 현재 결론과 과거 진행 상태를 같은 층위에 섞지 않는 것이 중요했다.

### 1.7 커리어 자동화에서도 '근거 없음 = unknown'을 유지해야 한다

career-agent는 공개 Portfolio의 프로젝트 근거를 공고 준비 workflow에 연결하면서도 `repository_evidence`, `self_reported_only`, `not_evidenced` 같은 근거 수준을 분리했다. ownership도 Stock/Airplane을 `owner_confirmed`, `personal`, `end_to_end`, `ai_assisted`, `owner_statement`처럼 명시적으로 전달하도록 정리했다.

개인 선호 기능에서도 통근시간·회사 규모·하이브리드·주거지원이 확인되지 않았으면 추정하지 않고 `unknown`으로 유지한다. 90분 통근은 soft preference이며 대기업·하이브리드·해당 공고의 주거지원은 근거가 있을 때만 장거리 예외로 남긴다.

공개 채용보드 discovery도 같은 원칙을 적용했다.

- `--live`를 명시했을 때만 외부 요청
- 허용된 HTTPS host만 접근
- 실패·403·429·timeout·빈 응답을 공고 삭제나 만료로 해석하지 않음
- 게시일이 없으면 `unknown`
- 제목에 경력 표기가 없다고 신입으로 추론하지 않음
- 회사 규모·근무형태·주거지원·통근시간도 외부 근거 없이는 `unknown`

자동화를 많이 할수록 빈칸을 그럴듯하게 메우는 것보다 **모르는 상태를 보존하는 계약**이 더 중요하다.
