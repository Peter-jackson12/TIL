## 1. 문제 인식 (Problem Recognition)

### ① `GROUP BY`의 데이터 압축(Collapsing) 한계와 원본 행 보존의 필요성
* **요약과 상세의 딜레마:** 인사팀에서 "직원별 급여와 함께 해당 직원이 속한 매장의 평균 급여를 대조하라"거나, 마케팅팀에서 "개별 주문 상품 행을 유지하면서 고객의 누적 총 구매액 대비 비중을 구하라"는 분석 요구가 빈번히 발생한다.
* **`GROUP BY`의 치명적 한계:** `GROUP BY store_id`를 적용하면 그룹화 키 단위로 여러 행이 단일 행으로 물리적 압축(Collapse)되어, 개별 `employee_id`나 `order_item_id` 같은 트랜잭션 상세 레코드가 완전히 증발한다.
* **비효율적인 우회 방식:** 이를 해결하기 위해 `GROUP BY` 결과를 서브쿼리로 만들고 원본 테이블과 다시 `JOIN`하는 방식을 사용하면, 동일 테이블을 2번 풀 스캔하는 극심한 I/O 병목이 발생한다.
* **해결책:** 기존 원본 행(Granularity)을 100% 보존하면서 그룹 집계 값을 새로운 컬럼으로 덧붙이는(Append/Broadcasting) **윈도우 함수(`OVER (PARTITION BY ...)`)** 파이프라인으로 전환해야 한다.

### ② 동점(Tie) 처리 방식에 따른 비즈니스 순위 지표 왜곡
* 상품 판매량이나 고객 결제액을 기준으로 랭킹을 매길 때 동일한 수치를 기록한 동점자가 발생한다.
* `ROW_NUMBER()`(고유 번호 강제), `RANK()`(올림픽식 건너뜀), `DENSE_RANK()`(빈틈없는 연속 순위)의 차이를 명확히 구분하지 않으면, 상위 3개 상품을 필터링할 때 의도치 않게 동점 상품이 누락되거나 결과 행 수가 3개를 초과하는 현상이 발생한다.
* 또한 `NTILE(4)`를 적용할 때 "금액 구간을 4등분하는 것"이 아니라 **"정렬된 행(고객 모수)의 개수를 4등분(사분위수)"**한다는 통계적 본질을 명확히 인지해야 한다.

### ③ 윈도우 프레임(Frame) 기본값의 함정과 누적/이동 계산 왜곡
* `AVG(salary) OVER (ORDER BY salary)`처럼 프레임을 명시하지 않고 `ORDER BY`만 작성하면, PostgreSQL은 기본값으로 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`를 적용한다.
* 이로 인해 "최근 3개 행 이동평균"을 구하려던 의도와 달리 "파티션 첫 행부터 현재 행까지의 누적평균"이 연산되는 논리적 버그가 발생한다. 따라서 `ROWS BETWEEN N PRECEDING AND CURRENT ROW` 형태로 물리적 윈도우 프레임을 명시적으로 제어해야 한다.

### ④ 퀀트 인프라: 선택 편향(Selection Bias) 극복과 틱 단위 미시구조의 침묵
* **한투 KIS 웹소켓의 한계:** 세션당 40종목 제한으로 인해 사전에 종목을 선별해야만 했고, 이는 장중 레짐 체인지(오후 주도주)를 포착하지 못하는 치명적인 **선택 편향(Selection Bias)**을 낳았다.
* **키움 32비트 전 종목 수집 전환:** 코스피/코스닥 상장 보통주 2,550개 전 종목을 무차별 수집하는 아키텍처가 필수적이다.
* **1초봉의 한계(Bar-Close Illusion):** 1초봉 백테스트는 1초 내부에서 발생하는 호가 스프레드(삼성전자 -0.395% 확정 손실)를 은폐한다. 실제 체결 틱 하나하나에 반응하여 매도1호가($Ask_1$)와 매수1호가($Bid_1$)로 교차 체결시키는 순수 틱 이벤트 백테스트 엔진이 요구된다.

## 2. 직접 코드 실험 (Direct Code Experiment)

### ① PostgreSQL 윈도우 함수 실습 파이프라인
4장 실습문제 요구사항에 맞춰 작성한 윈도우 함수, 순위 함수, 프레임 누적합, 시계열 증감 쿼리셋이다.

```sql
-- [실험 1-1] GROUP BY vs 윈도우 함수 구조 대조
-- A. GROUP BY: 행이 압축되어 매장 수(N개)만 출력 (개별 employee_id 증발)
SELECT 
    store_id, 
    AVG(salary) AS store_avg_salary
FROM employees
GROUP BY store_id;

-- B. 윈도우 함수: 원본 행 수 100% 보존 + 매장 평균 브로드캐스팅
SELECT 
    employee_id,
    store_id,
    salary,
    AVG(salary) OVER (PARTITION BY store_id) AS store_avg_salary
FROM employees
ORDER BY store_id, employee_id;

-- [실험 2-1] PARTITION BY + ORDER BY + 물리적 프레임 누적 평균 계산
SELECT 
    employee_id,
    store_id,
    salary,
    AVG(salary) OVER (
        PARTITION BY store_id 
        ORDER BY salary ASC, employee_id ASC 
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_avg_salary
FROM employees
ORDER BY store_id, salary ASC, employee_id ASC;

-- [실험 2-2] CBO 실행계획 계측 (WindowAgg & Sort)
EXPLAIN
SELECT 
    employee_id, store_id, salary,
    AVG(salary) OVER (
        PARTITION BY store_id 
        ORDER BY salary ASC, employee_id ASC 
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_avg_salary
FROM employees;

-- [실험 3-1] CTE 기반 카테고리별 판매수량 상위 3개 상품 추출 (순위 함수)
WITH category_product_sales AS (
    SELECT 
        p.category_id,
        p.product_id,
        SUM(oi.qty) AS total_qty,
        RANK() OVER (
            PARTITION BY p.category_id 
            ORDER BY SUM(oi.qty) DESC
        ) AS category_rank
    FROM order_items oi
    JOIN products p ON oi.product_id = p.product_id
    GROUP BY p.category_id, p.product_id
)
SELECT category_id, product_id, total_qty, category_rank
FROM category_product_sales
WHERE category_rank <= 3
ORDER BY category_id, category_rank, product_id;

-- [실험 4-1] NTILE(4)를 이용한 고객 LTV 4분위수 분할 및 검증
WITH customer_totals AS (
    SELECT 
        o.customer_id,
        SUM(oi.qty * oi.price) AS total_amount,
        NTILE(4) OVER (ORDER BY SUM(oi.qty * oi.price) DESC) AS customer_group
    FROM orders o
    JOIN order_items oi ON o.order_id = oi.order_id
    GROUP BY o.customer_id
)
SELECT 
    customer_group,
    COUNT(*) AS customer_count,
    ROUND(AVG(total_amount), 2) AS avg_group_amount,
    MIN(total_amount) AS min_group_amount,
    MAX(total_amount) AS max_group_amount
FROM customer_totals
GROUP BY customer_group
ORDER BY customer_group ASC;

-- [실험 5-1] LAG() 함수를 활용한 일별 주문량 전일 대비 증감 및 증감률 계산
WITH daily_orders AS (
    SELECT 
        order_date,
        COUNT(*) AS daily_order_count
    FROM orders
    GROUP BY order_date
)
SELECT 
    order_date,
    daily_order_count,
    LAG(daily_order_count, 1) OVER (ORDER BY order_date) AS prev_order_count,
    daily_order_count - LAG(daily_order_count, 1) OVER (ORDER BY order_date) AS order_count_diff,
    ROUND(
        (daily_order_count - LAG(daily_order_count, 1) OVER (ORDER BY order_date)) * 100.0 
        / NULLIF(LAG(daily_order_count, 1) OVER (ORDER BY order_date), 0), 2
    ) AS growth_rate_pct
FROM daily_orders
ORDER BY order_date;
```

## 3. 트러블슈팅 및 해결 (Troubleshooting & Resolution)

### Issue 1: `WHERE` 절에서 윈도우 순위 컬럼 직접 필터링 에러
* **현상:** `SELECT ..., RANK() OVER (...) AS category_rank FROM ... WHERE category_rank <= 3;` 실행 시 `ERROR: window functions are not allowed in WHERE` 발생.
* **원인:** SQL 파이프라인의 논리적 실행 순서(Logical Query Processing Order) 때문임.
  $$\text{FROM} \to \textbf{WHERE (필터링)} \to \text{GROUP BY} \to \text{HAVING} \to \textbf{SELECT (윈도우 함수 연산)} \to \text{ORDER BY}$$
  `WHERE` 절이 수행되는 시점에는 윈도우 함수가 아직 계산되지 않아 `category_rank` 컬럼 자체가 존재하지 않는다.
* **해결:** `WITH category_sales AS (...)` 형태로 CTE를 정의하여 윈도우 함수 결과셋을 메모리 테이블로 먼저 확정 지은 후, 바깥 메인 쿼리의 `WHERE` 절에서 `category_rank <= 3`을 필터링하도록 캡슐화함.

### Issue 2: `ORDER BY`의 다중 정렬 우선순위와 윈도우 프레임 결정론성(Determinism)
* **질문 및 의문:** `ORDER BY salary ASC, employee_id ASC`에서 `salary`가 낮으면 `employee_id`가 높아도 먼저 출력되고 계산되는가?
* **검증:** SQL 정렬은 좌측 컬럼이 무조건 1순위다. 급여가 3,000인 999번 사원은 급여가 5,000인 101번 사원보다 무조건 먼저 출력된다.
* **트러블슈팅 인사이트:** `salary ASC`만 지정하면 급여가 같은 동점자들 간의 순서가 DB 옵티마이저의 편의에 따라 실행할 때마다 뒤바뀌는 비결정론적(Non-deterministic) 버그가 발생한다. 따라서 고유 식별자인 `employee_id ASC`를 2순위 안전장치(Tie-breaker)로 배치하여 누적 계산의 재현성을 100% 보장함.

### Issue 3: CBO 실행계획 `WindowAgg` 아래 `Sort` 노드의 존재 이유 규명
* **현상:** 윈도우 함수 쿼리에 `EXPLAIN`을 수행했을 때 `WindowAgg` 노드 바로 아래에 `Sort` 노드가 배치됨.
* **원인:** `WindowAgg` 노드는 전체 데이터를 메모리에 올려두고 무작위 탐색하는 복잡한 연산자가 아니라, **"파티션과 정렬 순서대로 들어오는 정렬 스트림을 순차적으로 읽으면서 누적 상태(Sum/Count)를 갱신하고 도장을 찍는 스트리밍 연산자"**다.
* **해결:** DB 옵티마이저는 `PARTITION BY` 및 `ORDER BY` 키(`store_id, salary, employee_id`)에 부합하도록 데이터를 정렬하는 `Sort` 노드를 하위에 먼저 배치하여, 데이터가 들어오는 즉시 $O(N)$ 시간 복잡도로 윈도우 연산을 끝마치도록 파이프라인을 최적화함을 확인함.

### Issue 4: 키움 실시간 체결에서 매수 틱 0% 적재 버그 (FID 14 누락)
* **현상:** 수집된 SQLite DB 조회 시 51,306건 중 매수(`BUY`)가 0건(100% 매도/UNKNOWN)으로 기록되어 백테스트 매수 시그널이 전멸함.
* **원인:** 키움 OpenAPI 실시간 체결 이벤트에서 FID 14(체결구분)가 빈 문자열(`""`)이나 한글 `"매수"`로 전달되어 `raw_side == "1"` 단순 비교문이 무조건 `False`로 떨어짐.
* **해결 (Lee-Ready 알고리즘):** 금융공학 표준 체결 판정 규칙을 도입하여, 체결가 $P_t \ge Ask_1$이면 시장가 매수(`BUY`), $P_t \le Bid_1$이면 시장가 매도(`SELL`)로 2중 교차 판정하도록 수정.
* **결과:** **매도 58.06% vs 매수 41.94%**의 지극히 정상적인 마켓 미시구조 비율로 데이터 정합성 복구 완료.

### Issue 5: 네이버 일봉 수집기 `daily_collector.py` `IndexError`
* **현상:** 2022년 하락장 테스트 데이터 수집 시 `IndexError: list index out of range` 발생.
* **원인:** `count=1000` 설정 시 영업일 기준 4년에 불과하여 2022년 1월 데이터 범위를 커버하지 못함.
* **해결:** `count=4000`(약 16년 치)으로 확장하여 2022년부터 2026년까지 **총 1,074영업일 8대 매트릭스 CSV(행: 1,074, 열: 4)**를 0.2초 만에 완벽히 생성하도록 수정.

## 4. 퀀트 & 통계학적 인사이트 (Key Takeaways)

### 1. "GROUP BY는 믹서기, 윈도우 함수는 영양성분표 라벨 부착"
* `GROUP BY`는 여러 행을 갈아서 하나의 요약 행으로 뭉개버리므로 미시적인 개별 트랜잭션 정보가 손실된다.
* 반면 `OVER (PARTITION BY ...)`는 1,000명의 직원 행을 그대로 유지하면서 옆에 그룹 통계량(매장 평균)을 라벨로 부착한다. 이는 고객 전체 총 결제액 대비 개별 품목의 매출 기여도(비중)를 구하는 바스켓 분석 등에서 불필요한 셀프 조인을 제거하고 단일 스캔으로 처리하는 핵심 최적화 기법이다.

### 2. "순위 함수의 3가지 얼굴과 NTILE의 사분위수(Quantile) 본질"
* **`ROW_NUMBER`**: 동점 무시, 엄격한 고유 번호표 (DB 페이징 쿼리 표준).
* **`RANK`**: 동점자 수만큼 건너뜀 ($1 \to 2 \to 2 \to 4$, 올림픽 순위).
* **`DENSE_RANK`**: 동점자가 있어도 등수를 건너뛰지 않음 ($1 \to 2 \to 2 \to 3$).
* **`NTILE(4)`**: 금액 간격($0\sim 100$만 원을 25만 원씩)을 4등분하는 것이 아니라, **전체 고객 수(모수)를 균등하게 25%씩 4개 버킷으로 분할**하는 사분위수 함수다. 파레토 법칙(상위 20%가 매출 80% 점유)이 지배하는 금융/이커머스 데이터에서는 Group 1에 매출이 극단적으로 쏠리는 비대칭 분포를 보이므로 반드시 구간별 `MIN/MAX/AVG`를 함께 검증해야 한다.

### 3. "시계열 팩터 엔지니어링의 정수: ROWS BETWEEN과 LAG/LEAD"
* 금융 시계열 데이터에서 5일/20일/60일 이동평균선(MA), 모멘텀, 볼린저 밴드를 계산할 때 `ROWS BETWEEN N PRECEDING AND CURRENT ROW`는 필수적이다.
* `LAG(price, 1)`을 통해 이전 행의 값을 현재 행으로 끌고 오면, 복잡한 파이썬 루프 없이도 SQL 레벨에서 전일 대비 수익률, 가격 변동량, 갭(Gap)을 $O(N)$으로 연산할 수 있다.

### 4. "호가 스프레드(Bid-Ask Spread)와 틱 레벨 마이크로스트럭처의 공포"
* 1초봉 OHLCV는 봉 마감 가격만 보여주므로 스프레드 마찰 비용을 삭제해 버린다.
* 삼성전자 0승 17패 사례처럼, $Ask_1$에 진입하고 $Bid_1$에 청산하면 주가가 전혀 움직이지 않아도 1틱 손실(-0.195%)과 수수료/세금(-0.20%)이 결합되어 **매매당 정확히 -0.395%의 확정 손실**이 계좌를 갉아먹는다. 실전 퀀트 시스템은 반드시 원본 틱과 호가창을 대조하는 이벤트 기반(Event-Driven) 체결 모델이어야 한다.

### 5. "선택 편향 없는 2,550개 전 종목 데이터 레이크가 전략의 승패를 가른다"
* 장전 거래대금 상위 40종목만 선별 수집하는 것은 생존 편향과 선택 편향으로 오염된 가짜 알파를 낳는다.
* 키움 32비트 환경으로 전환하여 2,550개 전 종목 틱을 무차별 적재(Hot: SQLite WAL)하고, 야간에 Parquet(Cold: ZSTD 압축)으로 계층화함으로써, 4TB 인프라 안에서 3~5년 치 전 종목 틱 레이크를 무손실 보관하는 엔터프라이즈급 데이터 파이프라인을 완성했다.
