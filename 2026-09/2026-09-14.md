## 1. 문제 인식 (Problem Recognition)

### ① 통계학 가설검정의 본질적 오해와 $\alpha$-$\beta$ 시소 딜레마
* **$p$-value에 대한 직관적 오해:** "귀무가설이 맞다고 가정했을 때 극단적 값이 나올 확률이 낮다면, 원래 극단적인 게 잘 안 나오니 귀무가설이 맞는 것 아닌가?"라는 직관적 혼선에 직면함.
* **본질 규명 (귀류법):** 이미 내 손에 극단적 표본 결과가 실제로 관측된 상태에서, 귀무가설 전제하의 발생 확률이 $p < 0.05$로 희박하다는 것은 "희귀한 기적이 우연히 터진 것"이 아니라 **"애초에 귀무가설이라는 전제 자체가 거짓말"**이라는 배척의 논리임을 규명해야 함.
* **오류의 상충(Trade-off):** 억울한 누명을 씌우지 않으려고 유의수준 $\alpha$(제1종 오류)를 지나치게 낮추면, 실제 존재하는 효과를 놓치는 $\beta$(제2종 오류)가 폭증하는 시소 관계가 발생함.
* **실무적 의문 (동등성 검정):** 신약 복제약(제네릭) 허가나 서버 리팩토링 배포처럼 "기존과 달라지지 않고 똑같다"는 것을 입증해야 할 때, 일반 검정에서는 $H_0: \mu \neq \mu_0$를 둘 수 없는 수학적 한계(분포의 중심점 부재)와 이를 극복하는 **동등성 검정(TOST)**의 필요성을 인식함.

### ② PostgreSQL `EXPLAIN`과 `EXPLAIN ANALYZE`의 괴리와 병목 노드 판독
* **견적서와 영수증의 괴리:** `EXPLAIN`은 과거 통계치(`pg_statistic`) 기반의 가상 비용 점수(`cost`)만 제시하므로, 실제 실행 시간(`actual time`)과 디스크 I/O 누수를 포착할 수 없음.
* **병렬 스캔과 루프의 왜곡:** 대규모 테이블(60만 건) 풀스캔 시 나타나는 `Parallel Seq Scan`에서 `rows=16.00 loops=3`의 의미를 단일 16건으로 오독하면 실제 처리량($16 \times 3 = 48$건)을 잘못 파악하게 됨.
* **디스크 정렬 병목:** 정렬 노드에서 `Sort Method: external merge Disk`가 발생하는 순간 메모리(`work_mem`) 한계를 초과하여 디스크 쓰기가 발생, 쿼리 레이턴시가 수십 배 폭증하는 인프라 병목을 모니터링해야 함.

### ③ 머신러닝: 항공 지연 예측의 ROC-AUC 0.64 정체와 "외부 날씨 결합" 가설
* **ROC-AUC의 통계적 본질:** 지연 모델의 ROC-AUC가 0.64선에서 정체된 상황에서, 이 수치가 **"정상 비행기 1대와 지연 비행기 1대를 비교했을 때 지연편을 맞출 확률이 64%에 불과하다(Wilcoxon Rank-Sum)"**는 현실적 한계를 직시함.
* **누락 변수 편향(Omitted Variable Bias):** 비행기 지연의 70%는 '기상 악화'에 기인하는데, 대회 데이터셋은 날씨를 제외하고 스케줄·기체번호만 제공하여 물리적 예측 한계선에 도달함.
* **가설 설정:** "미국 교통통계국(BTS)과 항공편 운항 지문을 대조하여 데이터셋의 실제 연도(2022년)를 역추적하고, 미국 30대 공항의 실측 ASOS 기상 데이터를 결합하면 ROC-AUC가 0.8+ 수준으로 비약할 것이다."

### ④ 퀀트 인프라: 백테스트와 실전 간 피처 불일치(Lookahead / Parity Break)
* 기존 `calculate_window_metrics()`는 과거 배열을 슬라이싱하여 연산하므로 실전 스트리밍 환경에서 동일 코드를 사용할 수 없음.
* 실전용 스트림 로직을 별도로 작성하는 순간 미세한 연산 차이(누수 및 룩어헤드)가 발생하여 "백테스트에서만 잘 되는 전략"으로 전락함.
* **해결 과제:** 동일 클래스 내에서 `batch`와 `stream` 두 모드를 동시에 구현하고 단위 테스트로 정합성을 100% 검증하는 피처 스토어와, 멀티 런 비교가 가능한 런 스토어(`RunStore`) 구축이 요구됨.

## 2. 직접 코드 실험 (Direct Code Experiment)

### ① 통계학: 주사위 이항분포를 통한 $\alpha$-$\beta$ 시소 및 표본 크기($n$) 수리 시뮬레이션
표본 수 $n=5$와 $n=60$ 환경에서 유의수준 $\alpha$, 제2종 오류 $\beta$, 검정력($1-\beta$)의 동적 변화를 정확한 이항분포 확률 질량 함수로 계산함.

```python
# stats_power_simulation.py
import scipy.stats as stats

# 가설: H0(정상 주사위, p=1/6) vs H1(사기 주사위, p=0.50)
p0, p1 = 1 / 6, 0.50

print("=== [실험 1] n = 5 (소표본의 극단적 시소게임) ===")
# 룰 A: 5번 모두 1이 나와야 사기꾼 (극단적 엄격함)
alpha_a = (1 / 6) ** 5
beta_a = 1 - (0.50**5)
print(f"룰 A (5회 전부 1)  | alpha: {alpha_a*100:.3f}% | beta: {beta_a*100:.2f}% | Power: {(1-beta_a)*100:.2f}%")

# 룰 B: 1이 3번 이상 나오면 사기꾼 (alpha <= 0.05 기준)
alpha_b = 1 - stats.binom.cdf(2, 5, p0)
beta_b = stats.binom.cdf(2, 5, p1)
print(f"룰 B (3회 이상 1)  | alpha: {alpha_b*100:.2f}% | beta: {beta_b*100:.2f}% | Power: {(1-beta_b)*100:.2f}%")

print("\n=== [실험 2] n = 60 (표본 크기 확보를 통한 시소 파괴) ===")
# H0 평균: 10회, H1 평균: 30회 -> 임계값 k = 20회 설정
k = 20
alpha_60 = 1 - stats.binom.cdf(k - 1, 60, p0)
beta_60 = stats.binom.cdf(k - 1, 60, p1)
power_60 = 1 - beta_60
print(f"임계값 k={k}회 이상 판정 | alpha: {alpha_60*100:.4f}% | beta: {beta_60*100:.4f}% | Power: {power_60*100:.2f}%")
```

```text

임계값 k=20회 이상 판정 | alpha: 0.0733% | beta: 0.3308% | Power: 99.67%
```

### ③ 항공 지연 Phase 7: 2022년 미국 30대 공항 기상 실측 데이터 다이렉트 결합 파이프라인
```python
# merge_weather_pipeline.py (핵심 발췌)
import numpy as np
import pandas as pd
from datetime import datetime
from meteostat import Hourly

TARGET_YEAR = 2022
AIRPORT_STATION_MAP = {
    "ATL": "72219", "DFW": "72259", "DEN": "72469", "ORD": "72530",
    "LAX": "72295", "CLT": "72314", "JFK": "74486", "SFO": "72494" # 총 30개 허브 공항 WMO 매핑
}

def fetch_and_merge_weather():
    start_date = datetime(TARGET_YEAR, 1, 1)
    end_date = datetime(TARGET_YEAR, 12, 31, 23, 59)
    weather_frames = []

    for iata, station_id in AIRPORT_STATION_MAP.items():
        data = Hourly(station_id, start_date, end_date).fetch()
        if data.empty: continue
        data = data.reset_index()
        data["Airport_Code"] = iata
        data["Month"] = data["time"].dt.month
        data["Day_of_Month"] = data["time"].dt.day
        data["Hour"] = data["time"].dt.hour
        weather_frames.append(data[["Airport_Code", "Month", "Day_of_Month", "Hour", "wspd", "wpgt", "prcp", "snow", "temp"]])

    weather_df = pd.concat(weather_frames, ignore_index=True)
    
    flight_df = pd.read_csv("data/train.csv")
    flight_df["Dep_Hour"] = (pd.to_numeric(flight_df["Estimated_Departure_Time"], errors="coerce").fillna(-1) // 100).astype(int)

    merged_df = pd.merge(
        flight_df, weather_df,
        left_on=["Origin_Airport", "Month", "Day_of_Month", "Dep_Hour"],
        right_on=["Airport_Code", "Month", "Day_of_Month", "Hour"],
        how="left"
    )
    merged_df.to_csv("data/train_with_weather.csv", index=False, encoding="utf-8-sig")
    print(f"★ 결합 완료: 크기 {merged_df.shape} | 결합 성공률: {merged_df['wspd'].notna().mean()*100:.2f}%")
```

### Issue 1: `meteostat` 메이저 버전 업데이트로 인한 `ImportError` 및 관측소 조회 크래시
* **현상:** `merge_weather_pipeline.py` 실행 시 `ImportError: cannot import name 'Hourly' from 'meteostat'. Did you mean: 'hourly'?` 발생. 이후 `Stations.nearby(iata=...)` 호출 시 `unexpected keyword argument 'iata'` 예외 발생하며 수집 전면 중단.
* **원인:** `meteostat`이 v2.x로 릴리즈되면서 클래스명이 소문자(`hourly`)로 개편되었으며, `nearby()` 메서드는 오직 위경도(`lat, lon`) 튜플만 수용하도록 변경됨.
* **해결:** 불안정한 런타임 검색 메서드를 완전히 제거하고, 미국 30대 핵심 허브 공항에 대한 **공식 기상청 WMO 고유 관측소 ID 딕셔너리(`AIRPORT_STATION_MAP`)를 구축하여 다이렉트 쿼리 방식으로 전환**.
* **결과:** 검색 오버헤드가 제거되어 수집 속도가 10배 이상 향상되었으며, **100만 건 항공 데이터 중 55.77%(557,700건)에 실시간 기상 데이터 결합 완료**.

### Issue 2: [★ 핵심] Phase 7 기상 결합 후 모델 성능 급락(AUC 0.64 ➔ 0.59) 사후 부검 (Post-Mortem)
* **현상:** 55만 건의 실측 날씨 데이터를 결합하고 LightGBM 5-Fold를 수행했으나, **ROC-AUC가 0.6416에서 0.5964로 급락**하고 Macro F1 역시 0.5746에서 0.5465로 하락함. 피처 중요도 확인 결과 모든 기상 변수(`wspd`, `snow`, `prcp`, `wpgt`)가 **`Importance = 0.0`**을 기록함.
* **원인 규명 3가지:**
  1. **시공간 정합성(Alignment) 붕괴:** 정기편 노선은 매년 동일 시각에 운항하므로 2022년 운항 편명과 겹쳤으나, 데이콘 주최 측이 외부 데이터 누출을 막기 위해 **연도를 다년도(2019~2022) 혼합했거나 일자(`Day_of_Month`)를 셔플링한 합성 데이터**를 배포함. 날짜가 어긋난 날씨는 타깃과 완전히 독립인 무작위 난수(Gaussian Noise)가 됨.
  2. **시차(Timezone) 불일치:** Meteostat은 영국 그리니치 표준시(UTC) 기준인 반면, 항공편 출발시각은 미국 현지 로컬 시각(EST/CST/PST)이므로 5~8시간의 물리적 시차가 발생함.
  3. **`colsample_bytree = 0.75`에 의한 피처 공간 오염:** LightGBM이 트리를 분기할 때마다 무작위로 75% 피처를 샘플링하는데, 10개의 무의미한 기상 노이즈 변수가 포함되면서 알짜 도메인 변수(`Route`, `Tail_Number`)를 선택할 확률을 희석시킴. 검증 손실 개선이 정체되어 `early_stopping`이 조기 발동하며 모델이 과소적합됨.
* **조치:** 외부 기상 변수를 과감히 배제하고, 내부 도메인 피처링인 **Phase 5(고확신 준지도 증강 8.9만 건) + Phase 6(비행시간 중앙값 역산 복원 & 공항 트래픽 혼잡도)** 결합 아키텍처를 최종 프로덕션 모델로 확정.

### Issue 3: PostgreSQL `Parallel Seq Scan`의 행 수 판독 왜곡
* **현상:** `order_items` 단일 상품 조회 쿼리에서 옵티마이저가 `rows=25`로 예상했고 실행계획 결과에 `rows=16.00`이 찍혀 16건만 반환된 것으로 오해함.
* **원인:** 병렬 쿼리 실행 시 `actual rows`는 전체 합계가 아니라 **"루프(작업자) 1회당 평균 처리 행 수"**를 나타냄. `loops=3`은 리더 프로세스 1개 + 백그라운드 워커 2개가 투입되었음을 뜻함.
* **해결:** 실제 전체 반환 행 수는 $16.00 \times 3 = 48\text{건}$으로 정확히 계산됨. 60만 건 모수 중 단 48건을 추출하는 상황에서 옵티마이저의 예측(워커당 25건)과 실측(16건) 오차가 9건에 불과함을 확인하여, `pg_statistic` 통계 정보가 매우 건강하게 유지되고 있음을 역증명함.

### Issue 4: 퀀트 유니버스 B-4 실시간 수집기와 백테스트 유니버스 결합도 분리
* **현상:** 백테스트 엔진이 `collector/universe.py`를 참조하려 하여 의존 방향이 역전되는 아키텍처 결함 발생.
* **원인:** 실시간 수집기는 웹소켓 세션 제약(20~40종목)에 종속된 임시 셋이고, 백테스트 유니버스는 전 종목 및 규칙 기반이어야 함.
* **해결:** `core/universe.py`를 신설하여 보통주 식별 규칙(끝자리 0) 및 `universe.yaml` 선언을 해석하도록 분리. 선언 대비 결손(`no_daily`, `no_lob`)을 추적하는 매니페스트 시스템을 구축하고, 백테스트 PnL(-1.301%) 불변성을 검증 통과함.

## 4. 퀀트 & 통계학적 인사이트 (Key Takeaways)

### 1. "p-value는 귀류법이며, 표본 크기($n$)는 $\alpha$-$\beta$ 시소를 통째로 들어 올리는 유일한 치트키다"
* $p$-value는 "귀무가설이 참일 확률"이 아니라, "귀무가설이 참이라는 가정하에 현재 데이터 같은 기적이 일어날 조건부 확률 $P(\text{Data} \mid H_0)$"이다.
* 소표본($n=5$)에서는 누명을 줄이려 하면($\alpha \downarrow$) 사기꾼을 놓칠 확률($\beta$)이 96.9%까지 치솟는다.
* 하지만 데이터를 충분히 모으면($n=60$) 표준오차($\sigma/\sqrt{n}$)가 바늘처럼 얇아지며 두 분포가 물리적으로 분리된다. 그 결과 $\alpha \le 0.07\%$로 극도로 엄격하게 잡으면서도 $\beta \le 0.33\%$(검정력 99.67%)로 사기꾼을 완벽히 적발할 수 있다. 대학 시절 손으로 풀었던 검정력 공식 $\text{Power} = \Phi(d \cdot \sqrt{n} - z_\alpha)$의 본질이 바로 이 삼각관계다.

### 2. "외부 데이터의 역설: 시공간 기준점(Alignment)이 어긋나면 도메인 피처는 순수 독약(Noise)이 된다"
* 도메인 관점에서 비행기 지연의 70%는 기상 악화 때문이지만, 완벽한 시공간 키(Key) 정합성이 검증되지 않은 외부 날씨 결합은 모델의 ROC-AUC를 0.64에서 0.59로 파괴했다.
* LightGBM은 정보 이득(Gain)이 없는 날씨 변수를 영리하게 거부(`Importance = 0.0`)했으나, 서브샘플링 파라미터(`colsample_bytree`)로 인해 트리들이 진짜 신호(`Route`, `Tail_Number`)를 학습할 기회를 박탈당했다.
* 퀀트에서도 거시경제 지표나 뉴스 센티먼트 데이터를 틱 데이터에 붙일 때, 밀리초 단위의 타임스탬프 동기화와 지연 체결(Lag)을 검증하지 않으면 알파가 아니라 백테스트를 파괴하는 독약이 됨을 명심해야 한다.

### 3. "EXPLAIN은 가짜 견적서, EXPLAIN ANALYZE는 실측 영수증이다"
* 프로덕션 DB에서 섣부른 `EXPLAIN ANALYZE`는 무거운 쿼리를 진짜 실행하여 CPU 100% 락을 유발하거나 `DELETE` 문으로 데이터를 날려버릴 수 있는 위험한 도구다.
* 따라서 튜닝 설계 단계에서는 0초 만에 끝나는 `EXPLAIN`으로 `Seq Scan` 여부만 안전하게 확인하고, 개발/검증 환경에서만 `EXPLAIN ANALYZE`로 `actual time`, `loops`, `external merge Disk`를 계측하는 2단계 검증 규율을 준수해야 한다.

### 4. "피처 스토어의 존재 이유는 연산 속도가 아니라 '백테스트와 실전의 동일성(Parity)'이다"
* 퀀트 시스템에서 피처 스토어(`Feature Store`)를 구축하는 진짜 이유는 백테스트 루프 속도 향상이 아니다.
* 백테스트용 배치 코드와 실전 자동매매용 스트리밍 코드가 미세하게 어긋나는 순간 발생하는 데이터 누수(Data Leakage)와 룩어헤드 편향을 원천 차단하기 위함이다. 단일 클래스 내 이중 구현(`batch` vs `stream`)과 220개 무결함 테스트(`test_feature_parity.py`)만이 실전 수익률을 보장한다.
