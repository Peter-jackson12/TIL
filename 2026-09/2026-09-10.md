## 1. 문제 인식 (Problem Recognition)

### ① "파이썬 판다스로 다 처리하면 되는데, 왜 굳이 DB에서 SQL을 튜닝하는가?"
- **판다스(In-Memory)의 한계와 OOM 위험성:** 판다스는 모든 데이터를 컴퓨터 RAM에 전부 올려서 연산한다. 수십만~수백만 행의 정형 데이터를 단순 조회/가공하기 위해 `SELECT *`로 수 GB의 데이터를 네트워크를 통해 파이썬 메모리로 퍼 올리면, 메모리 부족(OOM: Out of Memory)으로 프로세스가 튕기거나 극심한 I/O 병목이 발생한다.
- **공유 RDBMS 서버의 안정성 위협:** 데이터베이스는 여러 애플리케이션과 분석가가 공유하는 인프라다. 인덱스를 고려하지 않은 무거운 집계나 풀 스캔 쿼리를 파이썬 스크립트(`pd.read_sql`)로 무작정 던지면 DB 서버 CPU 점유율이 100%에 달해 서비스 장애(자체 DDoS)를 유발한다.
- **데이터 엔지니어링 대원칙(Pushdown):** 데이터를 코드로 가져오는 것이 아니라, **"대용량 필터링과 무거운 집계 연산은 C/C++ 기반으로 최적화된 DB 엔진으로 밀어 넣고(Pushdown), 파이썬은 정제된 최종 결과셋(수십~수백 행)만 가볍게 수신하여 모델링/시각화에 집중한다"**는 아키텍처 분업을 확립해야 한다.

### ② CBO 옵티마이저의 블랙박스와 `Seq Scan`에 대한 오해
- **SQL의 선언적(Declarative) 특성:** SQL은 "어떻게(HOW) 찾을 것인가"를 절차적으로 지시하는 언어가 아니라, "무엇(WHAT)이 필요한가"만 선언하는 언어다. 실행 경로(Execution Plan)를 결정하는 주체는 클라이언트 툴(DBeaver)이 아니라 DB 내부의 **비용 기반 옵티마이저(Cost-Based Optimizer, CBO)**다.
- **`Seq Scan`의 수리적 당위성:** 인덱스가 존재함에도 옵티마이저가 테이블 전체를 처음부터 끝까지 읽는 `Seq Scan`을 선택하는 것은 오류가 아니다.
  1. 테이블 크기가 수백 건 이하로 극히 작은 경우, B-Tree 트리를 탐색하는 오버헤드가 더 크다.
  2. 조회 대상 행이 전체의 수십 % 이상(높은 선택도)인 경우, 인덱스를 경유해 테이블 블록을 무작위로 왕복(Random Access I/O)하는 비용이 디스크 블록을 통째로 순차적으로 긁어오는(Sequential Scan I/O) 비용보다 기계적으로 훨씬 비싸기 때문이다.

### ③ 다단계 조인(Multi-stage JOIN)과 1:N 관계의 행 팽창(Row Explosion)
- **영수증 비유와 차수(Cardinality)의 본질:** 주문(`orders`, 50만 건)에 주문 상세(`order_items`, 154만 건)를 결합하면 행 수가 약 3배 이상 폭증한다. 하나의 주문서(1)에 여러 개의 품목(N)이 매칭되므로, 관계형 조인 규칙에 따라 1건의 주문 데이터가 품목 개수만큼 복제·펼쳐지는 것은 데이터 왜곡이 아닌 정당한 행 팽창이다.
- **Base 테이블 확정의 중요성:** 내가 뽑으려는 데이터셋의 1행(Row)이 **'고객 1명'인지, '주문 1건'인지, '구매 상품 1개'인지** 데이터의 세부 단위(Granularity)를 사전에 정의하지 않고 조인을 수행하면 심각한 지표 뻥튀기 왜곡이 발생한다.

### ④ `LEFT JOIN`과 `ON` vs `WHERE` 필터링 위치에 따른 데이터 보존성
- **기준(Anchor) 테이블의 문법적 위치:** `LEFT JOIN`에서 보존되는 '왼쪽'의 기준은 `ON` 절의 등호 좌변이 아니라, **`FROM A LEFT JOIN B`에서 `JOIN` 키워드의 좌측에 위치한 테이블(A)**이다.
- **SQL 3치 논리(Three-Valued Logic)와 강제 형변환 함정:** `LEFT JOIN` 후 우측 테이블의 조건을 `WHERE` 절에 배치하면, 우측 테이블이 없는 좌측 행의 컬럼값(`NULL`)이 `WHERE NULL = 1`로 평가되어 `UNKNOWN(False)` 처리된다. 결과적으로 미매칭 행이 전부 삭제되어 **`LEFT JOIN`이 사실상 `INNER JOIN`으로 변질**된다. 기준 모수를 보존하려면 우측 조건은 반드시 `ON` 절에 결합해야 한다.

### ⑤ 퀀트 인프라: 64비트 메인 환경과 32비트 키움 Open API+의 물리적 충돌
- **ActiveX OCX의 레거시 종속성:** 키움증권 Open API+는 32비트 Windows COM(ActiveX) 환경에서만 구동된다.
- **환경 격리의 필요성:** 메인 데이터 사이언스/ML 파이프라인(Python 3.14 64비트, uv)과 키움 수집 엔진이 동일 런타임에서 공존할 수 없으므로, 코스피/코스닥 2,500 전 종목 무차별 수집을 위한 32비트 파이썬 가상환경을 완전히 격리 구축해야 한다.

### ① SQLite/Python 환경에서의 B-Tree 인덱스 검증 및 Pushdown 파이프라인
```python
import sqlite3
from pathlib import Path
import pandas as pd

ROOT = Path(__file__).resolve().parent
DB_PATH = ROOT / "retail_warehouse.db"

# 1. SQLite 연결 (별도 서버 설치 없이 C-Engine 기반 경량 RDBMS 구동)
conn = sqlite3.connect(DB_PATH)

# 2. B-Tree 인덱스 생성 (고카디널리티 외래키 customer_id)
with conn:
    conn.execute(
        "CREATE INDEX IF NOT EXISTS idx_orders_customer ON orders (customer_id);"
    )

# 3. CBO 옵티마이저 실행계획 검증 (EXPLAIN QUERY PLAN)
explain_sql = """
EXPLAIN QUERY PLAN
SELECT order_id, order_date, total_amount
FROM orders
WHERE customer_id = 100;
"""
print("=== [SQLite CBO 실행계획 계측] ===")
for row in conn.execute(explain_sql):
    print(row)
# 결과: (..., 'SEARCH orders USING INDEX idx_orders_customer (customer_id=?)') -> Index Scan 검증 완료!

# 4. CTE 집계 Pushdown ➔ 정제된 VIP 데이터만 Pandas DataFrame으로 인출
tuned_query = """
WITH customer_totals AS (
    SELECT 
        o.customer_id,
        SUM(oi.qty * oi.price) AS total_spent,
        COUNT(DISTINCT o.order_id) AS total_orders
    FROM orders o
    JOIN order_items oi 
        ON o.order_id = oi.order_id
    GROUP BY o.customer_id
)
SELECT 
    c.customer_id,
    c.city,
    ROUND(ct.total_spent, 2) AS total_spent,
    ct.total_orders
FROM customer_totals ct
JOIN customers c 
    ON ct.customer_id = c.customer_id
WHERE ct.total_spent >= 50000
ORDER BY ct.total_spent DESC;
"""

df_vip = pd.read_sql(tuned_query, con=conn)
print("\n=== [Pushdown 결과: 파이썬 메모리로 적재된 VIP 데이터셋] ===")
print(df_vip.head())
conn.close()
```

### ② 다단계 조인 체인(4개 테이블) 및 1:N 행 팽창 검증 SQL
```sql
-- 1단계: 4개 테이블 체인 결합 (orders ➔ customers ➔ order_items ➔ products)
SELECT 
    o.order_id,
    o.order_date,
    c.customer_id,
    c.city,
    p.product_id,
    oi.qty,
    oi.price
FROM orders o
JOIN customers c 
    ON o.customer_id = c.customer_id
JOIN order_items oi 
    ON o.order_id = oi.order_id
JOIN products p 
    ON oi.product_id = p.product_id
ORDER BY o.order_id ASC, p.product_id ASC;

-- 2단계: 조인 전후 행 수 비교 (1:N 행 팽창 계측)
SELECT COUNT(*) AS total_orders_before FROM orders;              -- 결과: 500,000건
SELECT COUNT(*) AS total_rows_after                             -- 결과: 1,539,911건 (약 3.08배 팽창)
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN order_items oi ON o.order_id = oi.order_id
JOIN products p ON oi.product_id = p.product_id;

-- 3단계: 다품목 주문 중복 행 분포 역추적 (비즈니스 무결성 확인)
SELECT 
    o.order_id,
    COUNT(*) AS item_count
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
GROUP BY o.order_id
HAVING COUNT(*) >= 2
ORDER BY item_count DESC;
```

### ③ `LEFT JOIN` 필터링 위치(`ON` vs `WHERE`) 및 Anti-Join 검증 SQL
```sql
-- [방식 A: WHERE 절 필터] -> 미매칭 고객 및 타 매장 고객 탈락 (사실상 INNER JOIN 변환)
SELECT c.customer_id, c.city, o.order_id, o.store_id
FROM customers c
LEFT JOIN orders o 
    ON c.customer_id = o.customer_id
WHERE o.store_id = 1;

-- [방식 B: ON 절 필터] -> 10만 고객 전원 보존, 1번 매장 거래만 우측에 결합
SELECT c.customer_id, c.city, o.order_id, o.store_id
FROM customers c
LEFT JOIN orders o 
    ON c.customer_id = o.customer_id 
    AND o.store_id = 1;

-- [검증 C: Anti-Join] 주문을 단 한 번도 수행하지 않은 결손 고객(635명)만 정밀 추출
SELECT 
    c.customer_id,
    c.first_name,
    c.last_name,
    o.order_id
FROM customers c
LEFT JOIN orders o 
    ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;
```

## 3. 트러블슈팅 및 해결 (Troubleshooting & Resolution)

### Issue 1: `LEFT JOIN`에서 `ON` 조건문 좌우 순서로 인한 기준 테이블 오인
* **상황:** 연습문제를 풀던 중 `ON o.customer_id = c.customer_id` 코드를 보고, 등호 왼쪽에 `o`가 적혀 있어 `orders` 테이블이 살아남는 기준(Left)인 줄 착각함. 이 상태에서 미주문 고객을 보겠다고 `WHERE o.order_id IS NULL`을 추가했다가 주문 고객 99,365명이 전부 날아가 635명만 남는 현상 직면.
* **원인:** `LEFT JOIN`의 'LEFT'는 `ON` 뒤의 등호 좌우가 아니라, **쿼리 본문에서 `[Table A] LEFT JOIN [Table B]`로 선언될 때 `LEFT JOIN` 글자 좌측에 오는 `Table A`**를 의미한다. `ON` 절의 등호는 대칭 관계($A=B \iff B=A$)이므로 순서가 결과에 아무런 영향을 주지 않는다.
* **해결:** `FROM customers c LEFT JOIN orders o`에서 `c`가 100% 생존하는 기준임을 명확히 규명하고, 혼선을 방지하기 위해 **"등호 앞에는 먼저 선언된 좌측 테이블을 적는다(`ON c.customer_id = o.customer_id`)"**는 실무 표준 컨벤션으로 코드를 일원화함.

### Issue 2: `LEFT JOIN` 후 `WHERE` 절 조건 작성 시 묵시적 `INNER JOIN` 변환 버그
* **상황:** "전체 고객 목록을 유지하면서 1번 매장 주문만 결합"하려는 요구사항에서 `WHERE o.store_id = 1`을 작성했더니, 1번 매장 주문이 없는 대다수의 고객이 결과 집합에서 증발함.
* **원인:** SQL 3치 논리에 의해, 1번 매장 주문이 없는 행의 `o.store_id` 값은 `NULL`이다. 사후 평가 단계인 `WHERE` 절에서 `NULL = 1`을 평가하면 `UNKNOWN`이 반환되어 해당 행이 가차 없이 드랍된다.
* **해결:** 필터 조건을 `WHERE`가 아닌 `ON` 절 내부(`ON c.customer_id = o.customer_id AND o.store_id = 1`)로 이동함. 이를 통해 좌측 고객 모수는 온전히 100% 보존하면서 1번 매장 주문만 조건부로 결합되도록 수정함.

### Issue 3: 인덱스 컬럼 좌변 수식 가공으로 인한 B-Tree 무효화 (`Seq Scan` 추락)
* **상황:** `WHERE customer_id + 10 = 510` 조건으로 검색했을 때, B-Tree 인덱스가 걸려 있음에도 옵티마이저가 인덱스를 타지 않고 수십만 행 `Seq Scan`을 수행함.
* **원인:** B-Tree 인덱스는 원본 컬럼값(`customer_id`)의 대소 관계를 기준으로 정렬되어 있다. 좌변에 산술 연산(`+ 10`)을 적용하면 인덱스에 저장된 정렬 키와 비교할 수 없어 전체 행을 하나씩 계산하며 대조해야 한다.
* **해결:** 컬럼 원형을 절대 훼손하지 않는 형태로 수식을 우변으로 이항하여 `WHERE customer_id = 500`으로 쿼리를 리팩토링함 ➔ 즉시 `Index Scan`으로 복구됨.

### Issue 4: 키움증권 Open API+ COM 모듈 64비트 로드 실패 (`Win32 Error / Class Not Registered`)
* **상황:** 메인 프로젝트 가상환경(64비트 Python 3.14)에서 `QAxWidget("KHOPENAPI.KHOpenAPICtrl.1")`을 호출했을 때 COM 객체를 등록할 수 없다는 에러 발생.
* **원인:** 키움 Open API의 핵심 모듈(`KHOpenAPI.ocx`)이 32비트 DLL 바이너리로 빌드되어 있어, 64비트 프로세스 공간에 물리적으로 적재(Load)될 수 없음.
* **해결:** `C:\Projects\03_Personal_Quant\venv32`에 Python 32비트 전용 가상환경을 분리 생성하고, 추후 64비트 메인 퀀트 엔진과의 통신은 프로세스 간 통신(IPC: Local Socket 또는 Shared SQLite WAL DB) 구조로 연결하도록 아키텍처를 분리 설계함.

## 4. 퀀트 & 통계학적 인사이트 (Key Takeaways)

### 1. "데이터를 코드로 가져오지 말고, 연산을 데이터로 밀어 넣어라 (Pushdown Engine)"
* 퀀트 시세 데이터나 대용량 로그 분석 시, 수백만 행의 원시 데이터를 파이썬으로 무작정 가져와서 `df.merge()`, `df.groupby()`를 돌리는 것은 메모리 낭비이자 장애 유발 패턴이다.
* C/C++로 극한 최적화된 DB 엔진과 B-Tree 인덱스를 활용해 **"필터링과 그룹 집계는 DB 내부에서 끝내고, 모델링에 필요한 수백 줄의 최종 결과만 파이썬으로 인출"**하는 Pushdown 원칙이 엔터프라이즈 데이터 파이프라인의 기본 규격이다.

### 2. 인메모리 임시 해시(`Hash Join`)와 디스크 B-Tree 인덱스의 공존 원리
* **B-Tree 인덱스:** 데이터가 정렬된 상태로 디스크에 영구 보관되며, 단일 값 검색뿐 아니라 범위 검색(`BETWEEN`, `>`, `<`) 및 `ORDER BY`를 $O(\log N)$으로 커버한다.
* **Hash Join:** 쿼리가 실행되는 0.1초 동안, 옵티마이저는 작은 테이블을 메모리(`work_mem`)로 올려 순간적으로 해시 딕셔너리를 빌드(Build)하고, 큰 테이블을 한 번 훑으면서 $O(1)$로 짝을 맞춘(Probe) 뒤 **쿼리가 끝나는 즉시 메모리에서 완전히 파괴(Free)**한다.
* 두 메커니즘의 차이를 이해해야 정렬 비용(`Sort`)과 메모리 세팅의 트레이드오프를 정밀하게 조율할 수 있다.

### 3. 다단계 조인의 그래뉼래러티(Granularity)와 생존성(Preservation) 관리
* 조인은 단순히 테이블을 붙이는 작업이 아니라 데이터의 **해상도(단위)**를 결정하는 과정이다.
* 1:N 관계 결합 시 행 팽창이 정상적인지 판단하려면 `HAVING COUNT(*) > 1` 검증이 선행되어야 하며, 전체 모수를 보존해야 하는 분석(예: 미거래 고객 이탈율, 미체결 호가 분석)에서는 `INNER JOIN`으로 인한 데이터 누락을 방지하기 위해 `LEFT JOIN`과 `ON` 절 조건 배치를 엄격히 관리해야 한다.

### 4. 2,500 전 종목 무차별 수집(Data Lake)을 위한 32비트-64비트 하이브리드 아키텍처
* 퀀트 백테스팅에서 거래대금 상위 100종목만 사전에 선별 수집하는 행위는 심각한 **선택 편향(Selection Bias)**과 생존 편향(Survivorship Bias)을 유발한다.
* 시장의 레짐 체인지(Regime Shift)와 극단적 변동성을 포착하려면 2,500개 전 종목 틱/호가 데이터 레이크가 구축되어야 한다.
* 레거시 32비트 키움 Open API+는 무가공 원본 수집기(Collector)로 격리하여 SQLite에 무차별 직렬 적재하고, 64비트 환경의 퀀트 백테스터/ML 엔진이 이를 파싱·가공하는 **이원화 파이프라인**이 시스템 안정성과 통계적 순수성을 지키는 유일한 해법이다.
