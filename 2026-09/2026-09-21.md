## 1. 오늘 배운 것

### 1.1 퍼널은 이벤트 횟수가 아니라 '단계를 통과한 고유 집합'을 본다

퍼널의 핵심은 각 단계가 이전 단계의 부분집합이 되도록 정의하는 것이다.

[
S_0 \supseteq S_1 \supseteq S_2 \supseteq \cdots
]

구간 전환율과 이탈률은 다음처럼 계산한다.

[
Conversion_i = \frac{|S_i|}{|S_{i-1}|}, \qquad
Drop_i = 1 - Conversion_i
]

같은 사용자가 기능을 여러 번 사용해도 퍼널에서 알고 싶은 것은 보통 "몇 번 했는가"가 아니라 "몇 명/몇 구독이 이 단계까지 왔는가"이므로 `nunique()`나 `set` 교집합이 중요하다.

또한 전환율이 가장 낮은 구간을 찾았다고 원인까지 알아낸 것은 아니다.

> 퍼널은 **어디에서(Where)** 문제가 보이는지 알려 주지만, **왜(Why)** 그런지는 추가 분석이나 실험이 필요하다.

### 1.2 코호트 분석은 달력 시간을 상대 시간으로 바꾸는 작업이다

서로 다른 날짜에 시작한 사용자를 달력 날짜 그대로 비교하면 경험 기간이 다르다. 코호트 분석에서는 각 사용자의 시작점을 맞춰

[
Calendar\ Time \rightarrow M0, M1, M2, \dots
]

처럼 상대 시간으로 비교한다.

오늘 실습에서는 "첫 유효 기능 사용 월"을 코호트 시작점으로 사용했다. 리텐션은 매달 이전 달 사용자 수가 아니라 **최초 코호트 크기**를 분모로 둔다.

[
R_{c,m} =
\frac{\text{코호트 }c\text{ 중 }m\text{개월째 다시 사용한 고유 구독 수}}
{\text{코호트 }c\text{의 최초 구독 수}}
]

특히 중요한 점은 두 가지였다.

- M1에 사용하지 않았어도 M2에 복귀할 수 있으므로, 이 형태의 리텐션은 반드시 단조 감소하지 않는다.
- 아직 M3가 도래하지 않은 코호트는 0%가 아니라 **관찰 불가(`NaN`)**다.

즉,

[
\text{Not observed} \neq \text{Did not return}
]

이다.

### 1.3 Cohort와 Segmentation은 둘 다 사용자를 나누지만 질문이 다르다

- **Cohort:** 언제/어떤 시작 조건을 공유했는가?
- **Segmentation:** 어떤 사용자·상품 속성을 공유했는가?

예를 들어 가입 월별 리텐션은 Cohort이고, Basic/Pro/Enterprise 요금제별 리텐션은 Segmentation이다.

세그먼트별 최저값이 존재한다고 해서 차이가 실질적으로 큰 것도 아니고, 해당 속성이 원인이라는 뜻도 아니다. 오늘 `product_2` 검토에서도 최소값을 찾은 뒤 반드시 %p 차이, 분모 크기, 코호트 구성 차이를 함께 보도록 답안을 다듬었다.

### 1.4 AARRR은 하나의 순차 퍼널이 아니라 서비스의 여러 관점이다

AARRR의 각 단계는 서비스에 맞는 행동으로 먼저 정의해야 한다.

- Acquisition: 유입
- Activation: 핵심 가치 경험
- Retention: 재사용
- Revenue: 수익 행동
- Referral: 추천·공유

각 영역의 숫자를 단순히 크기순으로 비교하면 안 된다. Retention처럼 시간 조건이 있는 지표도 있고, Referral 행동 자체가 로그에 없다면 비슷한 이름의 컬럼을 억지로 대체해서도 안 된다.

오늘 다시 정리한 질문 구조는 다음과 같다.

- **AARRR:** 무엇을 볼 것인가?
- **Funnel:** 어디에서 떨어지는가?
- **Retention:** 언제 다시 오는가?
- **Segmentation:** 누구에게 차이가 있는가?
- **A/B Test:** 가설대로 바꿨을 때 정말 행동이 달라지는가?

### 1.5 A/B 테스트는 숫자 비교보다 비교 가능한 조건을 만드는 것이 먼저다

개선 전 60%, 개선 후 65%라고 해서

[
+5\%p
]

가 모두 개선안의 효과라고 말할 수 없다. 기간, 사용자 구성, 할인, 상품 구성 등 다른 요인이 함께 변했을 수 있다.

그래서 A/B 테스트에서는 무작위 배정으로 비교 가능한 집단을 만들고, 검증하려는 요소를 제외한 조건을 최대한 같게 유지한다.

실험 전에 정해야 할 것은 다음과 같다.

- 검증 가설
- 목표 지표
- 실험 대상
- Control / Treatment
- MDE
- 표본 크기
- 실험 기간
- 필요한 Guardrail Metric

진행 중에는 Early Stopping, Novelty Effect, Sample Contamination, SRM을 점검한다.

또한

[
p < \alpha
]

라고 해서 "효과가 있을 확률이 높다"거나 "바로 적용해야 한다"는 뜻은 아니다. **통계적 유의성**, **효과 크기**, **실질적 가치**, **가드레일 악화 여부**, **실험 과정의 정상성**을 함께 봐야 한다.

### 1.6 Ridge와 Lasso는 계수를 규제하는 두 방식이다

복습 중 Ridge와 Lasso의 차이가 헷갈려 다시 정리했다.

#### Ridge — L2

[
Loss + \lambda\sum_j \beta_j^2
]

계수를 전반적으로 작게 줄이지만 보통 정확히 0으로 만들지는 않는다.

#### Lasso — L1

[
Loss + \lambda\sum_j |\beta_j|
]

일부 계수를 정확히 0으로 만들 수 있어 변수 선택 효과가 있다.

외울 것은 간단하다.

[
L1 = Lasso, \qquad L2 = Ridge
]

그리고 (lambda)가 커질수록 규제가 강해져 계수는 더 작아지고, 지나치면 underfitting이 생길 수 있다. 계수 크기에 직접 벌점이 걸리므로 입력 변수 스케일링도 중요하다.

### Q1. `DataFrame.style` 오류는 왜 났고, uv 프로젝트에서는 어떻게 처리하는 게 좋은가?

노트북에서 다음 오류가 발생했다.

```text
AttributeError: The '.style' accessor requires jinja2
```

계산 로직 문제가 아니라 pandas Styler가 `jinja2`를 필요로 하는데 프로젝트 환경에 없었던 문제였다.

이 프로젝트는 이미 uv로 관리하고 있으므로 단순 `pip install jinja2`보다

```bash
uv add jinja2
```

로 프로젝트 의존성에 추가하는 편이 낫다. 그러면 `pyproject.toml`과 `uv.lock`에 의존성이 기록되어 다른 환경에서도 재현하기 쉽다.

### Q2. 수업 노트북을 매번 채팅에 첨부해야 하나?

### Q3. 세그먼트에서 가장 낮은 값이 나오면 바로 개선 우선순위인가?

아니다. 최솟값은 데이터에 항상 존재할 수 있다.

예를 들어 84.8%, 84.5%, 84.2%라면 84.2%가 최저인 것은 사실이지만 최대 차이는 0.6%p뿐이다. 따라서

- 차이의 크기
- 분자/분모
- 코호트 구성
- 관찰 기간
- 추가 비용

등을 함께 봐야 한다.

## 4. 아직 헷갈리는 것 / 다음에 확인할 것

### Product Analytics

리텐션은 정의에 따라 "정확히 N일/N개월째 돌아왔는가", "N일 이후 한 번이라도 돌아왔는가", "구간 내 한 번이라도 활동했는가" 등이 달라진다. 앞으로 리텐션율을 볼 때 숫자보다 먼저 **행동 정의와 시간 창(window)**을 확인한다.

### ML

Ridge/Lasso에서 왜 L1 제약의 마름모 꼭짓점 때문에 계수가 정확히 0이 되기 쉬운지, L2의 원형 제약과 함께 다시 그림으로 복습한다. 상관이 높은 변수에서 Lasso가 불안정해질 수 있는 이유와 Elastic Net도 이어서 확인한다.
