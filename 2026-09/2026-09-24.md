## 1. 오늘 배운 것

### 1.1 하나의 "통과"를 전체 시스템의 적격성으로 확대하면 안 된다

Stock 작업에서 오늘 가장 반복해서 확인한 원칙은 **검증의 범위를 정확히 이름 붙이는 것**이었다.

전체 raw 세션이 완전한 연구 입력으로 승격되지 않았더라도, 사전에 고정한 오전 구간만 독립적으로 확인하는 `raw_v2_prefix_qualification_v1`을 별도 계층으로 만들었다. 예를 들어 10:00 KST exclusive cutoff 이전만 검사하고, cutoff 이후의 유효 레코드를 boundary sentinel로 요구한다.

이때 통과가 의미하는 것은 `smoke_backtest_eligible=true`인 bounded prefix라는 사실뿐이다. 다음을 자동으로 뜻하지 않는다.

- 전체 세션 품질이 검증됐다.
- performance research가 허용됐다.
- FIRST_RESEARCH_CANDIDATE로 승격됐다.
- 실거래가 가능하다.

즉 **전체 스트림 적격성, bounded prefix 적격성, pipeline smoke, execution quote validity는 서로 다른 계약**이다.

### 1.2 합성 포트폴리오 엔진에서도 계좌 상태의 소유권을 한 곳에 모아야 한다

PR #30에서는 기존 단일 종목 replay/quote 검증을 재사용하면서 별도 opt-in `PortfolioSimulator`를 추가했다.

핵심 구조는 다음과 같다.

- 여러 종목이 하나의 현금을 공유한다.
- 종목별 position과 주문 상태를 분리한다.
- 주문 접수 시 현금 또는 매도 가능 수량을 예약한다.
- 취소 확인 전에는 예약과 체결 가능성을 유지한다.
- strategy는 intent만 만들고 실제 cash/position/risk/fill mutation은 simulator가 소유한다.

이 구조는 strategy가 계좌 상태를 직접 바꾸는 것보다 재현성과 감사 가능성이 높다. 같은 시각의 이벤트 순서와 예약 정책까지 계약으로 고정하면, "같은 입력인데 실행 순서에 따라 결과가 달라지는" 문제를 줄일 수 있다.

최종 PR #30과 병합 후 master에서는 GitHub-hosted Windows/Python 3.14 기준 전체 Git-only **1,963 passed / 6 deselected**, Session assessment **127 passed**가 확인됐다. 이는 합성 검증 결과이며 실제 x86/OCX/native 환경 인증은 아니다.

### 1.3 전략 어댑터와 실행 엔진의 책임을 분리하면 기존 전략을 재사용하기 쉽다

PR #31에서는 기존 `NxtResearchStrategy`를 다시 구현하지 않고, 종목별 전략 상태를 유지하는 adapter를 통해 공유계좌 엔진에 연결했다.

전략은 `OrderIntent`와 `CancelIntent`를 만들고, 전역 order id 충돌 방지와 cash/position mutation은 포트폴리오 엔진이 담당한다. 그 결과 전략 로직과 계좌 실행 현실성을 분리해서 검증할 수 있게 됐다.

이후 PR #33에서는 검증된 bounded prefix를 NXT portfolio smoke runner에 연결해 `event → signal → order → fill` 흐름을 재현할 수 있게 했다. 하지만 이 smoke는 전략 수익성 평가가 아니라 **파이프라인 연결과 재현성 확인**이다.

### 1.4 큰 원본을 직접 건드리지 않고 검증 가능한 working copy를 만드는 것도 데이터 엔지니어링 문제다

실제 2026-09-21 raw-v2 원본은 약 50.6GB이고, 0-byte WAL과 32,768-byte SHM residue가 남아 있어 기존 sealed qualifier가 즉시 거부하는 상태였다.

PR #34는 이 원본을 삭제·checkpoint·SQLite open으로 "정리"하지 않고, fail-closed frozen snapshot acquisition 경로를 만들었다.

핵심은 다음과 같다.

1. source main/WAL/SHM을 동시에 exclusive read handle로 잡는다.
2. source SQLite는 열지 않는다.
3. 한 번의 streaming read로 hash를 계산하면서 evidence와 working copy를 만든다.
4. source identity/stat이 바뀌지 않았는지 다시 확인한다.
5. working copy에서만 sidecar 정리와 최소 metadata 확인을 한다.
6. 성공해도 `snapshot_ready_for_prefix_qualification=true`까지만 선언한다.

PR #35에서는 source handle과 evidence seal을 최종 검증까지 더 오래 유지하도록 보강했다. 중요한 점은 **"복사가 성공했다"와 "연구에 써도 된다"가 다른 상태**라는 것이다.

### 1.5 데이터 품질 예외는 넓게 완화하지 말고 관측된 패턴만 좁게 격리해야 한다

실제 오전 prefix에서 한쪽 top3 quote가 모두 `-0`, 같은 side 잔량이 0이고 반대편 book은 정상인 패턴이 관측됐다. 바로 다음 `parse_error`가 같은 seq/received_ns/code/issues를 mirror하는 경우도 있었다.

PR #36은 이 좁은 패턴을 `missing/non-executable quote` 후보로 분리하는 합성 실험을 추가했다. 여기서도 candidate quote는 기존 quote validation에서 계속 `invalid_ask` 또는 `invalid_bid`로 실행 불가다.

PR #37은 정확히 짝지어진 one-sided zero-quote tick + mirrored parse_error pair만 quarantine하는 opt-in smoke-quality evaluator를 추가했다. master의 최신 기록에는 이 경로의 focused 검증 **75 passed**가 남아 있다.

반면 `trade_direction_unverified`, extra issue, pairing mismatch, unsafe control은 계속 fail-closed다. 즉 **quarantine은 execution permission이 아니다.**

현재 PR #38은 selected-instrument smoke-quality 정책을 더 좁게 분리하는 후속 후보로 열려 있으며, 아직 merge된 완료 작업으로 보지 않는다.

### 1.6 Career System에서는 정책을 바꾸기 전에 독립 검증이 모순을 잡아냈다

Career System의 matcher v2 r2는 fresh 16-case prediction을 먼저 고정한 뒤 blind role-fit label을 붙이는 방식으로 검증했다.

결과는 다음과 같이 기록됐다.

- role_fit: YES 8 / MAYBE 7 / NO 1
- hard contradiction: 1건
- review_queue: 7/16

pre-defined hard contradiction이 실제로 발생했기 때문에 production/default adoption은 보류됐다. 이후 software / AI-product 경계 감사를 진행했지만 taxonomy를 바로 다시 쪼갤 근거는 부족했고, mixed case는 review-first uncertainty path를 유지했다.

별도 AI-core product software 후보를 과거 14건에 대조한 결과도 `candidate_hit 2 / miss 10 / ambiguous 2`였고, clear hit 내부에서도 role_fit이 YES/NO로 갈렸다. 그래서 후보는 non-canonical 상태로 남고 r3 승격도 하지 않았다.

이 과정에서 배운 점은 **검증 세트를 정책에 맞추는 것이 아니라, 정책이 검증에서 깨질 수 있도록 prediction과 label 순서를 고정해야 한다**는 것이다.

### 1.7 Career vault는 "관측 사실"과 "해석된 경력 사실"을 분리해야 한다

matcher calibration을 닫은 뒤 실제 review 운영으로 돌아가면서 application-prep, eligibility check, career-vault reconciliation을 진행했다.

private vault에서는 행정 기록이나 source-backed observation과 해석된 work-history fact를 같은 값으로 덮어쓰지 않고, 충돌이 있으면 충돌 상태를 보존했다. resume-critical P0/P1 확인을 끝낸 뒤 reusable private career profile snapshot v1을 만들었고, tracked Git에는 개인 경력 사실·PII·private hash를 넣지 않았다.

그 다음 read-only consumer canary에서는 **인터페이스 경계 자체는 유지됐지만 downstream fact reproduction이 완전하지 않다**는 결과가 나왔다. 따라서 adapter/validator 구현을 바로 진행하지 않고, minimal snapshot revision이 같은 canary를 통과할 때까지 보류했다.

최신 PR #28 병합 시 검증은 Ubuntu **607 passed, 1 skipped**, Windows **608 passed**였으며 Ruff, format, tracked-file guard, installed wheel smoke도 통과했다.

## 3. 오늘의 핵심 정리

오늘 작업은 기능을 많이 붙이는 것보다 **서로 다른 검증 단계가 무엇을 증명하고 무엇을 증명하지 않는지 경계를 세우는 작업**이 중심이었다.

Stock에서는 `whole stream → bounded prefix → pipeline smoke → execution validity`를 분리했고, Career System에서는 `prediction freeze → blind label → contradiction check → canonical adoption`을 분리했다.

두 프로젝트 모두 같은 원칙으로 정리할 수 있다.

> 한 단계의 성공을 더 강한 주장으로 자동 승격하지 않는다. 각 결과는 자신이 실제로 검증한 범위까지만 말한다.
