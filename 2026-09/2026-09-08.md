## 1. 문제 인식 (Problem Recognition)

### ① 100만 행 대형 불균형 분류와 디폴트 임계값(0.50)의 치명적 함정
- **All-Zero 예측의 수리적 진실:** 100만 행 항공 운항 데이터 중 라벨 데이터(255,001건)의 실제 지연율은 **17.65%**에 불과한 심한 클래스 불균형 데이터였다. 기본값 `Threshold = 0.50`을 적용한 1차 베이스라인에서 모든 Fold의 Macro F1-Score가 소수점 넷째 자리까지 **`0.4516`으로 완벽히 동일하게 고정**되는 기현상이 발생했다.
- **원인 분석:** 모델이 예측한 지연 확률이 대부분 $0.15 \sim 0.30$ 사이에 머물러 있어, 0.50 기준선으로는 단 1건의 지연 비행기도 식별하지 못하고 **모든 샘플을 100% 정상(0)으로 예측($TP=0, FN=45,000$)**했기 때문이다.
  $$F1_{\text{정상}} \approx \frac{2 \times 0.8235 \times 1.0}{0.8235 + 1.0} \approx 0.9032, \quad F1_{\text{지연}} = 0.0000 \implies \text{Macro } F1 = \frac{0.9032 + 0}{2} = \mathbf{0.4516}$$
- **문제 해결 방향:** 단순 모델 교체나 하이퍼파라미터 튜닝이 아닌, 데이터셋의 자연 발생 확률(Base Rate, 18%)에 근접한 **최적 임계값(Threshold Grid Search) 탐색 엔진 구축**이 필수적임을 도출했다.

### ② 비지도학습의 거리 왜곡(K-Means)과 차원 축소의 수리적 본질(PCA)
- **K-Means 유클리드 거리의 왜곡:** `Channel`(1: 외식, 2: 소매)이나 `Region`(1, 2, 3) 같은 명목형(Nominal) 범주를 거리에 포함하면 알고리즘이 "지역 3은 지역 1보다 3배 멀다"는 비수학적 착각을 일으킨다. 또한 수만 단위인 `Fresh`가 수백 단위인 `Delicassen`의 거리를 압도하므로 `StandardScaler`를 통한 체급 통일이 강제된다.
- **"StandardScaler + 공분산 = 상관계수"의 수리적 등가성:** PCA가 단위에 왜곡되지 않으려면 표준화를 거친 후 공분산 행렬을 분해해야 하는데, 이는 본질적으로 **원본 데이터의 피어슨 상관계수 행렬(Correlation Matrix)을 분해하는 것과 완벽히 동일한 수학적 연산**임을 증명했다.
- **정보 압축과 손실(Loss)의 트레이드오프:** 6개 구매 피처를 PC1(44.1%)과 PC2(28.4%)로 압축했을 때 누적 설명 분산은 **72.5%**였다. 즉, 2차원 시각화를 얻는 대가로 $27.5\%$의 고유 변동성(노이즈 및 미세 분별력)을 버려야 하며, 가중합으로 변수가 섞여 "나이 35세 이상"과 같은 비즈니스 룰 설명력(Explainability)이 소멸함을 확인했다.

### ③ 준지도 학습(Pseudo-Labeling)과 오차 누적(Confirmation Bias)의 위험성
- **미라벨(未라벨) 74.5만 건의 실체:** 전체 100만 건 중 $74.5\%$는 타깃(`Delay`)이 결측된 미라벨 데이터였다. 
- **단순 백분위수 선별의 함정:** 에이전트가 제안한 "상위 15%를 지연(1), 하위 15%를 정상(0)"으로 채택하는 방식은 상위 15%의 예측 확률이 $0.223$에 불과하여, **정상 확률이 77.7%인 비행기 11만 대를 지연으로 둔갑시키는 치명적인 데이터 오염(Data Poisoning)**을 초래함을 간파했다.
- **비대칭 고확신 필터링:** 진짜 지연 확률이 높은 상위 2%($p \ge 0.235$)와 하위 10%($p \le 0.184$)만 엄선하여 순도 높은 결측치만 증강 데이터로 편입하는 정밀 전략을 수립했다.

### ④ 쿼리 옵티마이저(CBO)의 실행 사이클과 데이터 볼륨 병목
- **SQL 실행 3단계:** 작성된 SQL은 즉시 테이블을 읽지 않고 `파싱(Parsing) ➔ 최적화(Optimization) ➔ 실행(Execution)` 단계를 거친다.
- **데이터 볼륨과 인덱스 역전:** 데이터가 수천 건일 때는 옵티마이저가 메모리 블록 I/O를 아끼기 위해 Full Table Scan(Seq Scan)을 선택해도 빠르지만, 수백만 건으로 증가하면 인덱스를 타지 않는 쿼리는 디스크 I/O 병목을 유발해 전체 데이터베이스 CPU/메모리를 고갈시킨다.

### ⑤ 고빈도(HF) 퀀트 아키텍처와 편향 방지(Selection Bias) 철학
- **사전 선별 수집의 오류:** KIS API의 무료 세션당 40종목 제한을 우회하고자 "전일 거래대금 상위 150종목만 선별 수집"하려던 초기 기획은, 아침에 거래량이 없다가 장중 주도주로 폭발하는 종목(Regime Shift)을 영구히 누락시키는 **선택 편향(Selection Bias)**을 낳는다.
- **원천 데이터 레이크(Data Lake)의 무결성:** 원천 데이터는 시장의 모든 팩트(2,500 전 종목)를 편견 없이 보존해야 하며, 거래대금 필터링은 엔진 내부의 전략 파라미터로 격리되어야 함을 확인했다.

## 2. 직접 코드 실험 (Direct Code Experiment)

### ① `StandardScaler` 표준화 후 공분산 = 원본 상관계수 100% 수리 일치 증명
```python
import numpy as np
import pandas as pd
from sklearn.preprocessing import StandardScaler

# 나이(수십 단위)와 연봉(수천만 단위)의 단위 불균형 데이터
df = pd.DataFrame({
    'age': [20, 30, 50],
    'salary': [25000000, 40000000, 80000000]
})

# 1. 원본 데이터의 피어슨 상관계수 행렬
corr_matrix = df.corr()

# 2. StandardScaler 표준화 후 모집단 공분산 행렬 계산
scaled_data = StandardScaler().fit_transform(df)
cov_of_scaled = np.cov(scaled_data.T, bias=True)  # ddof=0

print("=== 1. 원본 상관계수 행렬 ===")
print(corr_matrix.round(4))

print("\n=== 2. 표준화 데이터의 공분산 행렬 ===")
print(pd.DataFrame(cov_of_scaled, columns=['age', 'salary'], index=['age', 'salary']).round(4))

# 두 행렬이 소수점 끝자리까지 정확히 일치함을 단언(Assert)
np.testing.assert_almost_equal(corr_matrix.values, cov_of_scaled, decimal=6)
print("\n✅ 수리적 검증 완료: Cov(StandardScaler(X)) == Corr(X)")
```

### ② 불균형 분류 F1 극대화를 위한 OOF 임계값(Threshold) 최적화 엔진
```python
import numpy as np
from sklearn.metrics import f1_score, confusion_matrix

# oof_probs: 5-Fold OOF 예측 확률 배열, y_true: 실제 지연 정답 (17.65% 양성)
thresholds = np.arange(0.10, 0.60, 0.01)
best_thresh, best_f1 = 0.5, 0.0

for th in thresholds:
    preds = (oof_probs >= th).astype(int)
    score = f1_score(y_true, preds, average="macro")
    if score > best_f1:
        best_f1 = score
        best_thresh = th

print(f"👑 최적 판정 임계값: {best_thresh:.2f} (기본 0.50 대비 대폭 하향)")
print(f"★ 튜닝 후 Macro F1 : {best_f1:.4f} (베이스라인 0.4516 ➔ 0.5724 폭등)")

# 최적 임계값 기준 Confusion Matrix로 TP 구출 검증
cm = confusion_matrix(y_true, (oof_probs >= best_thresh).astype(int))
print(f"구출된 실제 지연편(TP): {cm[1, 1]:,d}건 / 총 지연편 {cm[1].sum():,d}건")
```

### ③ 노선별 중앙값 기반 비행시간 역산 복원 및 공항 혼잡도(Traffic) 피처링
```python
import numpy as np
import pandas as pd

# 단측 결측치(출발만 있거나 도착만 있는 행) 역산 알고리즘
def impute_flight_durations(df: pd.DataFrame) -> pd.DataFrame:
    df = df.copy()
    
    # 1. 노선 결합 피처 생성
    df["Route"] = df["Origin_Airport"].astype(str) + "_" + df["Destination_Airport"].astype(str)
    
    # 2. 노선별 비행 소요시간 중앙값 산출
    route_median = df.groupby("Route")["Estimated_Duration"].transform("median")
    df["Estimated_Duration"] = df["Estimated_Duration"].fillna(route_median).fillna(df["Estimated_Duration"].median())
    
    # 3. 도착시간 결측 역산 (출발 시각 + 소요시간 = 도착 시각)
    arr_missing = (df["Arr_Hour"] == -1) & (df["Dep_Hour"] >= 0)
    calc_arr_min = (df.loc[arr_missing, "Dep_Hour"] * 60 + df.loc[arr_missing, "Dep_Minute"] + df.loc[arr_missing, "Estimated_Duration"]) % 1440
    df.loc[arr_missing, "Arr_Hour"] = (calc_arr_min // 60).astype(int)
    
    # 4. 공항 시간대별 동시 출항/입항 트래픽(혼잡도) 밀도 산출
    df["Origin_Traffic"] = df.groupby(["Month", "Day_of_Month", "Origin_Airport", "Dep_Hour"])["Route"].transform("count")
    df["Dest_Traffic"] = df.groupby(["Month", "Day_of_Month", "Destination_Airport", "Arr_Hour"])["Route"].transform("count")
    
    return df
```

## 3. 트러블슈팅 및 해결 (Troubleshooting & Resolution)

### Issue 1: GitHub 푸시 거절 — 111.3MB 대용량 CSV 파일과 커밋 히스토리 트랩
* **에러 로그:** `remote: error: File data/train.csv is 111.30 MB; this exceeds GitHub's file size limit of 100.00 MB`
* **원인:** Git은 커밋 히스토리 전체를 검사하므로, 이미 직전 커밋에 111.3MB 파일이 포함된 상태에서는 `.gitignore`에 `data/`를 추가하고 재푸시해도 거절당함.
* **해결:** 작업 파일은 보존한 채 커밋 헤드만 안전하게 1단계 되돌린 후 재커밋함.
  ```powershell
  git reset HEAD~1
  # .gitignore에 data/, *.csv 추가
  git add .
  git commit -m "feat: initial commit excluding large data files"
  git push -u origin master
  ```

### Issue 2: LightGBM `ValueError: train and valid dataset categorical_feature do not match`
* **원인:** 원본 데이터(`X_tr_orig`)와 가짜 라벨 데이터(`pseudo_X`)를 `pd.concat`으로 병합할 때, 양쪽의 카테고리 범주가 미세하게 달라 판다스가 내부적으로 `category` 타입을 자동으로 해제하고 `object`/`int64`로 묵시적 변환함. 이로 인해 Train셋은 비범주형, Valid셋은 범주형으로 타입이 불일치하여 엔진이 크래시됨.
* **해결:** 병합 직후 `cat_cols` 루프를 순회하며 `X_tr_aug[col] = X_tr_aug[col].astype("category")`를 명시적으로 재선언하여 스키마 무결성을 강제함.

### Issue 3: 무분별한 백분위수 Pseudo-Labeling에 의한 모델 오염(Data Poisoning)
* **상황:** 에이전트가 빈 `pseudo_y` 예외 처리를 위해 예측 확률 상위 15%와 하위 15%를 무조건 1과 0으로 선별하도록 변경함.
* **통계적 위험 포착:** 터미널 로그 분석 결과 상위 15%의 확신도 임계값이 **`0.223`**으로 나타남. 즉, 정상일 확률이 77.7%인 비행기 11만 건을 억지로 '지연(1)'으로 라벨링하여 학습셋에 50:50 비율로 쏟아부어 오차 누적을 유발할 뻔함.
* **해결:** 자연 지연율(18%)을 감안하여 **정상은 하위 10%($p \le 0.184$), 지연은 초고위험 상위 2%($p \ge 0.235$)만 엄선하는 비대칭 분위수 필터링**을 적용하여 순도 높은 89,438건만 증강함.

### Issue 4: 타깃 인코딩(Target Encoding) 단독 적용 시 AUC 급락 현상 (0.6357 ➔ 0.6043)
* **원인:** 고카디널리티 변수(`Tail_Number`, `Route`)를 단순 평균 지연율(연속형 실수)로 1:1 치환하고 원본 텍스트를 삭제하자, LightGBM 고유의 강력한 카테고리 간 상호작용 분기 능력(예: Southwest $\times$ Chicago O'Hare)이 완전히 거세됨.
* **해결:** 원본 카테고리 컬럼(`category` dtype)을 그대로 보존하고 베이지안 평활화 타깃 인코딩을 **추가적인 힌트 피처(`TE_Tail_Number`)로 병합 투입하는 '하이브리드 피처링'**으로 선회하여 AUC 반등(0.6107) 및 LogLoss 최저치(0.4633)를 달성함.

### Issue 5: KIS WebSocket OAuth `EGW00104: AppSecret 필수` 및 네이버 일봉 API 4,000일 확장
* **원인 1:** `pykrx`의 로그인 차단 및 `FinanceDataReader`의 상장사 캐시 URL 404 에러로 일봉 수집 중단. 네이버 금융 XML 직결 시 `count=1000` 설정으로 2022년 과거 행이 누락되어 `IndexError` 발생.
* **해결 1:** 네이버 캔들 API URL을 `count=4000`으로 확장하여 2022-04-20부터 2026-09-08까지 총 **1,074영업일의 8대 일봉 매트릭스 CSV(Shape: 1074, 4)**를 0.2초 만에 완벽 복원.
* **원인 2:** KIS 실시간 WebSocket 인증 시 구버전 키 명세(`secretkey`)로 요청하여 거절당함. `body`에 `appsecret`과 `secretkey`를 동시 패킹하고 다중 `.env` 경로 탐색 로직을 구축하여 해결.

| **Phase 3: Target Encoded** | 카테고리 삭제 후 TE 단독 치환 | 0.22 | 0.4635 | 0.6043 | 0.5521 | 14,895건 | 카테고리 입체 분기력 상실로 AUC 하락 |
| **Phase 4: Hybrid** | Category + TE 동시 투입 | 0.22 | 0.4633 | 0.6107 | 0.5579 | 14,386건 | AUC 반등 및 LogLoss 최저치 경신 |
| **Phase 5: Pseudo-Labeling** | 8.9만 건 비대칭 선별 준지도 학습 | **0.24** | **0.4587** | **0.6416** | **0.5746** | 13,527건 | **전 지표 역대 최고치(All-Time High) 달성** |

* **인사이트:** 준지도 학습(Phase 5)은 모델의 확률 분포 신뢰도(LogLoss 0.4587)와 전체 랭킹 변별력(AUC 0.6416)을 극대화했으며, 도메인 피처링(Phase 6)은 결측된 시간과 공항 활주로 병목을 채워줌으로써 현장에서 가장 중요한 **실제 지연 적발 건수(TP 15,866건)를 사상 최대로 갱신**했다.

### 2. "사전 선별 수집은 데이터를 오염시킨다" — 퀀트 데이터 레이크의 절대 원칙
* 무료 API의 제약(세션당 40종목)을 피하고자 특정 기준(예: 거래대금 40억 이상 150종목)으로 사전에 잘라 수집하는 행위는 **사후 확증 편향(Look-ahead / Selection Bias)**의 주범이다.
* 오전에 거래량이 없다가 오후에 폭발하는 급등주, 대형 악재로 거래 정지 직전까지 가는 소외주 등 시장의 극단적 꼬리 위험(Fat-tail Risk)과 국면 전환(Regime Shift)은 전 종목 데이터가 온전히 보존되어 있을 때만 검증할 수 있다.
* 따라서 **원천 수집기(Data Lake)는 코스피/코스닥 2,500개 전 종목을 무차별 수집(키움 32비트 25개 화면 분할 테크닉)**해야 하며, 전략 필터링은 엔진 내부에서 실행되어야 함을 시스템 설계 원칙으로 확립했다.

### 3. 고빈도(HF) LOB 처리의 황금률: 2-Step Architecture
* 09:00 장 시작과 동시에 쏟아지는 초당 수천 건의 틱을 실시간으로 1초봉 LOB(51개 컬럼)로 연산하려 하면 웹소켓 수신 버퍼 오버플로우와 패킷 드랍이 필연적으로 발생한다.
* **장중에는 무가공 원본 체결·호가 패킷을 SQLite WAL 모드로 무식하게 디스크에 직렬 기록(Append-only)**하고, **장마감 후 1초 단위로 안전하게 슬라이싱 집계하는 2단계 파이프라인**이 시스템 안정성과 백테스팅 재현성을 보장하는 유일한 길이다.

### 4. MLOps와 DevOps의 본질적 경계선
* DevOps는 코드(Code)의 무결성을 배포하지만, **MLOps는 시간이 흐름에 따라 현실 세계의 데이터 분포가 변하는 '데이터 드리프트(Data Drift)'를 방어**해야 한다.
* 퀀트 모델이나 항공 지연 모델처럼 계절성과 거시경제 국면(Macro Regime)에 따라 확률 분포가 이동하는 시스템은 고정된 모델을 방치해서는 안 되며, 파이프라인 레벨에서 지속적 모니터링과 자동 재학습(CT: Continuous Training) 체계가 탑재되어야 진정한 엔터프라이즈 MLOps가 완성된다.

### 5. AWS 클라우드 비용 아키텍처: S3 Parquet 콜드 스토리지의 압도적 효율
* 영업일 기준 0.5GB씩 발생하는 퀀트 틱 데이터를 AWS RDS PostgreSQL에 상시 적재하면 디스크 비용과 인스턴스 비용으로 월 3~4만 원 이상이 발생한다.
* 반면, 이를 로컬에서 Parquet(Snappy) 형식으로 1/5 토막(약 0.1GB) 압축한 후 **Amazon S3 표준 스토리지에 적재하면 1년 치(25GB) 누적 기준 월 보관료는 약 800원~1,000원에 불과**하다. 대용량 틱은 S3 데이터 레이크에 저장하고, 실시간 조회용 일봉/분봉만 RDBMS에 분리 적재하는 이원화 아키텍처가 퀀트 인프라 비용 최적화의 핵심이다.
