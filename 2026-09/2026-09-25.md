## 1. 오늘 배운 것

### 1.1 연구 속도를 높이려면 빠른 경로와 정확한 경로의 역할을 분리해야 한다

Stock에서는 대규모 전략 탐색을 위해 Fast Backtest v1을 별도 연구 파이프라인으로 구현했다. 빠른 탐색 경로는 후보를 넓게 훑는 데 사용하고, 중요한 결과는 Exact 경로와 다시 대조하는 구조를 유지했다.

오늘 작업에서는 raw 경로 기준 성능 근거를 남기고, 인과적 universe와 호가 깊이 cache를 추가해 이후 여러 종목·여러 조건을 반복 계산할 때 같은 입력을 불필요하게 다시 읽지 않도록 했다.

- Fast는 탐색 비용을 줄이는 도구다.
- Exact는 최종 결과의 신뢰 경계를 확인하는 기준이다.
- 속도를 위해 미래 정보를 섞거나 실행 계약을 바꾸면 안 된다.
- cache는 성능 최적화이지만 입력 시점과 provenance를 보존해야 한다.

### 1.2 운영 화면에서는 실행 버튼보다 실행 전 상태 확인이 먼저다

Collector를 매번 명령어로 직접 실행하지 않아도 되도록 Operator 화면에 읽기 전용 preflight, 수집 Run Plan, 실행 직전 체크리스트, Windows 바로가기 진입점과 상태 요약을 붙였다.

실시간 수집기는 프로그램이 켜지는 것만으로 성공이라고 볼 수 없기 때문에 실제 실행 전에 환경·경로·현재 상태를 먼저 확인하도록 진입점을 정리했다.

### 1.3 백테스트 후보는 in-sample 결과와 holdout을 분리해야 한다

9월 21일 데이터를 이용한 exploratory profitability 탐색에서 수익 후보를 찾았지만 이를 바로 전략 성능으로 확정하지 않고 후보와 holdout을 분리했다.

in-sample에서 가장 좋았던 후보 중 하나인 #268은 별도 후보로 동결하고, 9월 18일 데이터를 holdout으로 사전 등록했다.

좋은 결과를 본 뒤 검증 데이터까지 같은 방식으로 다시 고르면 holdout의 의미가 사라진다는 점을 다시 확인했다.

### 1.4 Career System은 matcher 변경과 실제 운영 진입점을 따로 검증해야 한다

Career Agent에서는 matcher v2를 먼저 shadow routing으로 추가한 뒤 production review routing으로 전환했다.

또 하루 작업을 한 번에 시작할 수 있도록 Career Operator v1을 추가해 daily orchestration을 연결했다.

이 과정에서 source text의 hash와 raw file hash를 분리했다. 같은 채용공고라도 저장 파일 자체와 실제 판단에 사용한 텍스트는 서로 다른 provenance이므로 하나의 hash로 취급하면 안 된다.

## 2. 직접 확인된 것과 아직 하지 않은 것

### 확인된 것

- Stock Fast Backtest v1 연구 파이프라인과 인과적 universe·호가 cache가 구현됐다.
- Collector Operator에 preflight, Run Plan, 상태 요약, Windows 진입점이 추가됐다.
- profitability 탐색 후보와 holdout을 분리해 기록했다.
- Career matcher v2가 shadow 검증을 거쳐 production review routing에 연결됐다.
- Career Operator v1의 daily orchestration이 병합됐다.

### 아직 완료하지 않은 것

- Fast 결과를 전략 적격성으로 바로 승격하지 않았다.
- in-sample 수익 후보는 holdout 검증 전까지 확정된 전략 성능이 아니다.
- Collector 운영 편의 기능이 실제 장중 장시간 안정성을 자동으로 증명하지는 않는다.
