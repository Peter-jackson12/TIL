## 1. 오늘 배운 것

### 1.1 검증 가능한 범위를 먼저 고정해야 한다

저장소에 코드와 테스트만 있고 실제 원본 데이터나 로컬 캐시가 없다면, CI가 확인할 수 있는 것은 **Git에 들어 있는 재현 가능한 계약**뿐이다. 이를 실제 데이터 검증과 섞어 쓰면 “CI 통과 = 실데이터 재현 성공”처럼 과장된 결론이 생길 수 있다.

Airplane에서는 이 경계를 명시적으로 나눴다.

- Git-only 검사: 저장소의 코드, 테스트가 만드는 임시 입력, 문서 구조처럼 GitHub Actions에서 재현 가능한 것
- local_data 검사: Git에 없는 원본 `train.csv`, HOMR/IEM 원자료 캐시 등 실제 외부 입력이 필요한 것
- CI 성공: Git-only 계약이 깨지지 않았다는 뜻
- 실데이터 재현: 필요한 원본을 복원한 뒤 별도로 실행해야 하는 일

PR #1 기준으로 Git-only 379개가 통과하고 local_data 24개는 명시적으로 선택 해제됐다. 이후 PR #2에서 Git-only 회귀가 추가돼 382개 통과·24개 선택 해제, 총 수집 대상 406개가 됐다. 서로 다른 시점의 숫자를 한 번의 “전체 테스트 통과”처럼 합쳐 말하지 않는 것도 중요하다.

**배운 점:** 테스트 개수보다 먼저 “이 테스트가 무엇을 증명하는가”를 정의해야 한다.

### 1.2 후보를 고르지 않는 것도 올바른 결과다

Stock의 첫 실데이터 백테스트 후보를 고르면서 처음에는 “가장 최근의 정상 종료 파일 하나를 골라 시험해 보면 되지 않을까?”라고 생각하기 쉽다. 하지만 실제로는 **선정 조건을 만족하는 근거가 없으면 후보를 지정하지 않는 것**이 더 안전하다.

기존 근거와 파일 메타데이터를 대조한 결과, 현재 raw v2 파일 5개 중 정상 종료된 실질 후보는 두 세션뿐이었다.

- `cf18cb43…`: 방향 정책 전환 이전 코드로 수집됐다. 기존 10,384건 표본 대조에서 구세대 방향 판정이 스펙과 8.6% 불일치했고, 현재 방향 정책을 적용하면 제어 레코드의 99.8%가 사라지는 문제가 이미 기록돼 있다.
- `21f8c124…`: `signed_volume` 정책 적용 이후 수집됐지만 말미에 무부호 FID15 체결 8건과 대응 `parse_error` 8건이 있어 현재 엄격 연구 경로가 거부한다.

여기서 더 중요한 점을 하나 발견했다. `inspect_raw_v2_sample.py`는 과거 파일에 최신 기본 정책을 강제로 적용하는 도구가 아니라 **파일에 저장된 당시 정책을 다시 적용해 내부 일관성을 확인하는 도구**다. 따라서 `cf18cb43…`가 `sample_consistent`로 나와도 “당시 unknown 정책으로 다시 계산한 값이 저장값과 같다”는 뜻이지, 현재 `signed_volume` 연구 계약에 적합하다는 뜻은 아니다.

그래서 다음 필수 단계는 과거 파일을 더 많이 파보는 것이 아니라 **현재 정책으로 새 clean closed 세션을 확보하는 것**으로 결정했다.

**배운 점:** “검사를 더 하면 언젠가 통과할 것”이 아니라, 그 검사가 실제로 내가 알고 싶은 질문에 답하는지 먼저 확인해야 한다.

### 1.3 재개 가능한 작업은 ‘계획의 정체성’과 ‘실행 예산’을 분리해야 한다

Airplane의 날씨 수집기는 요청 수·바이트·시간 상한을 두고 체크포인트에서 재개하도록 설계돼 있었다. 그런데 기존 v2에서는 이 **총예산 상한 자체가 `plan_fingerprint`에 포함**돼 있었다.

그러면 모순이 생긴다.

1. 한 번 cap에 도달하면 같은 cap으로는 더 진행할 수 없다.
2. cap을 늘려 재개하려 하면 fingerprint가 달라져 “다른 계획”으로 간주되어 재개가 거부된다.

즉 “필요하면 예산을 조금 늘려 같은 작업을 이어간다”는 CLI 의도와 실제 재개 계약이 충돌했다.

v3에서는 이를 분리했다.

- `plan_fingerprint`: selection, mapping, station/day 조회 구간, 요청당 크기, timeout, retry, padding 등 **결과의 정체성을 바꾸는 불변 조건**
- `budget_limit_history`: 실행마다 조정 가능한 누적 요청/바이트/시간 상한
- 누적 사용량: 재개해도 초기화하지 않음
- v2 체크포인트: 어떤 부분이 계획이고 어떤 부분이 예산인지 안전하게 분해할 수 없으므로 자동 이관하지 않고 네트워크 호출 전에 거부

**배운 점:** 체크포인트 재개 시스템에서 “같은 작업인가?”를 판정하는 identity와 “이번 실행에서 얼마까지 허용할까?”라는 resource ceiling은 서로 다른 개념이다.

### 1.4 README는 현재 상태, 상세 이력은 증거 보관소로 나누는 편이 낫다

Airplane README는 프로젝트가 커지면서 현재 결론, 과거 실험, 철회된 해석, 재현 명령이 한 문서에 계속 쌓였다. README를 프로젝트 컨트롤센터로 유지하되 다음처럼 역할을 분리했다.

- 상단: 현재 목표, 현재 파이프라인, 최신 검증 결과, 한계와 다음 단계
- 하단 evidence appendix: 과거 실험 회차, 세부 근거, 철회된 해석, 역사적 테스트 수, 재현 명령
- 문서 회귀 테스트: 필수 섹션·앵커·링크·재현 모듈 경로 등이 깨지지 않는지 Git-only로 검사

Stock에서도 비슷하게 `HANDOFF.md`와 `BACKTEST_TODO.md`의 원문 이력을 archive에 보존하고, 현재 행동·입력 판정과 과거 기록을 분리했다.

**배운 점:** 문서가 길어지는 것 자체보다 **현재 의사결정과 역사적 근거가 같은 레벨에서 섞이는 것**이 더 큰 문제다.

## 2. 문제 → 실험 → 해결 → 배운 점

### 2.1 Stock — 첫 실데이터 백테스트 입력을 왜 아직 고르면 안 되는가

**문제.** 첫 실제 백테스트를 시작하려면 raw DB 하나를 골라야 하지만, “최근 파일”, “용량이 큰 파일”, “closed라고 적힌 파일”만으로는 연구 입력 적합성을 보장할 수 없었다.

**확인.** 오늘 작업에서는 raw DB를 새로 열거나 신규 표본 검사·백테스트를 실행하지 않았다. 기존 세션 종료 근거, 기존 표본 검사 결과, 파일 메타데이터와 현재 코드 계약을 대조했다.

**결론.** 현재 5개 raw 파일 중 엄격 계약을 바로 통과하는 후보는 없다. 특히 `cf18cb43…`를 첫 100건 다시 검사하는 계획도 다음 필수 단계에서 제외했다. 그 검사는 저장 당시 unknown 정책의 내부 일관성만 확인할 뿐, 현재 기본 정책의 연구 적합성을 검증하지 못하기 때문이다.

**다음 경로.** 새 clean 세션을 확보한 뒤 다음 순서로 확인한다.

`writer_closed → finalization → 종료 보고 → signed_volume 정책 → 제한 표본 검사 → 품질 제어 기록 부재 확인 → 전체 무결성 검사 → 첫 시험 백테스트`

오늘 실제 수집기는 시작하지 않았다.

### 2.2 Stock — 실행 직전 probe가 막아 주는 것도 성공이다

clean 세션 수집 전 점검에서는 합성 probe가 오래된 `count == 41` 기대값 때문에 실패했다. 현재 방향 정책에 맞게 합성 기대값과 검사를 수정했다.

하지만 실제 수집은 그대로 **BLOCKED** 상태로 남겼다. mock/live 선택, 다음 시장 세션의 운영 여부에 대한 근거, 실제 로그인·전 종목 수집에 대한 사용자 승인 같은 운영 조건이 아직 확정되지 않았기 때문이다.

이 과정에서 “사전 점검 스크립트가 실패하지 않는 것”보다 **실제 실행 전에 불확실성을 막는 것**이 더 중요한 역할이라는 점을 다시 확인했다.

### 2.3 Airplane — GitHub CI와 로컬 실험을 같은 것으로 부르지 않기

**문제.** 일부 테스트는 Git에 없는 HOMR/IEM 원자료나 로컬 생성 파일이 필요했다. 이런 테스트가 파일 존재 여부에 따라 조용히 생략되면 CI가 무엇을 검증했는지 불명확해진다.

**해결.** `local_data` marker로 실제 입력 의존 검사를 분리하고, 기본 pytest 선택을 `not local_data`로 고정했다. 원본이 필요한 검사는 별도 명령으로 명시적으로 실행한다.

**배운 점.** “없으면 skip”보다 “이 검사는 로컬 원본이 필요하다”고 계약에 드러내는 것이 훨씬 낫다.

### 2.4 Airplane — 날씨 수집 재개의 예산 계약 수정

**문제.** v2 체크포인트는 실행별 총예산과 불변 수집 계획을 하나의 fingerprint에 섞었다.

**해결.** 체크포인트 스키마를 v3로 올리고, 불변 계획 fingerprint와 `budget_limit_history`를 분리했다. 이미 사용한 요청·바이트·시간은 그대로 누적하며, 같은 계획의 다음 실행에서 상한만 조절할 수 있게 했다. v2는 추측 이관하지 않는다.

이 변경은 **Git-only 코드·회귀 계약 수정**이며 새 날씨 다운로드, 전체 결합, 모델 재학습을 실행한 결과는 아니다.

### 2.5 GitHub 플러그인 기반 프로젝트 운영

오늘 여러 프로젝트를 다루면서 일반 ChatGPT의 역할을 더 명확하게 정리했다.

- GitHub에 있는 코드·문서·커밋·PR·Actions는 일반 ChatGPT + GitHub 플러그인에서 직접 처리
- 로컬 raw DB, OCX, 실제 시장 로그인/수집처럼 Git 밖의 상태가 필요한 작업만 로컬 환경으로 넘김
- 프로젝트별 `README.md + AGENTS.md`를 에이전트가 먼저 읽는 컨트롤센터로 사용
- TIL처럼 Markdown 중심 저장소는 Work를 거치지 않고 GitHub에서 직접 작성
- 여러 파일이 바뀌는 경우 브랜치 + PR + CI로 검증

TIL 저장소에도 오늘 `AGENTS.md` 기반 작업 지침과 생성 목차 정합성을 검사하는 GitHub Actions가 추가돼, “오늘 배운 내용 정리 → TIL 작성 → 자동 목차 검증” 흐름을 GitHub 안에서 닫을 수 있게 됐다.

**배운 점:** 에이전트에게 모든 일을 맡기는 것보다, **데이터가 어디에 있고 어떤 검증이 필요한지에 따라 실행 위치를 나누는 것**이 더 중요하다.

## 3. 내가 궁금했던 질문과 이해한 답

### Q1. 일반 ChatGPT를 프로젝트 컨트롤타워로 써도 되는가?

GitHub에 올라온 내용만 필요한 작업이라면 가능하다. 저장소 조회, 문서 검토, 코드 수정, 브랜치/PR, Actions 확인까지 GitHub 플러그인으로 처리할 수 있다. 반대로 Git에 없는 raw 데이터나 실제 프로그램 상태가 필요하면 그 부분만 로컬 작업으로 넘겨야 한다.

즉 구분 기준은 “작업이 어려운가?”보다 **필요한 근거가 어디에 있는가?**에 가깝다.

### Q2. README가 모든 문서의 컨트롤센터 역할을 해도 되는가?

가능하지만 현재 상태와 역사적 근거를 분리해야 한다. README 첫 부분에서 지금 무엇이 맞고 다음에 무엇을 해야 하는지 바로 보여 주고, 세부 회차와 과거 해석은 appendix로 내려야 에이전트와 사람이 모두 덜 헷갈린다.

### Q3. 테스트가 통과하면 다음 단계로 넘어가도 되는가?

테스트가 어떤 계약을 검증하는지에 따라 다르다. Git-only 테스트가 통과했다고 실데이터 품질이 검증된 것은 아니고, 과거 파일을 당시 정책으로 다시 계산해 일치했다고 현재 연구 정책에 적합한 것도 아니다. **검증 결과와 주장 범위를 항상 함께 기록해야 한다.**

## 5. 다음에 확인할 것

### Stock

다음 시장 세션에서 실제 수집을 실행하기 전 mock/live 선택, 시장 운영 여부, 사용자 승인 조건을 확정한다. 새 세션이 생기면 “최신 파일”이라는 이유로 바로 백테스트하지 않고, 오늘 정한 종료·정책·표본·무결성 순서를 그대로 적용한다.

### Airplane

Git-only 계약 수정은 끝났지만 실제 원본 근거 재현은 별도다. HOMR/IEM 원자료 캐시를 복원·해시 대조한 뒤 근거가 부족한 공항은 그대로 보류하고, 그 다음에 수정된 stratafix 300행 수집·결합과 날씨 유무 비교 실험으로 넘어간다.

### 운영 방식

프로젝트가 더 커질수록 “현재 판단”, “과거 이력”, “Git-only 검증”, “로컬 증거”, “아직 실행하지 않은 계획”을 문서와 테스트에서 분리한다. 이것이 컨텍스트가 길어져도 에이전트가 과거 결론을 현재 사실로 오해하지 않게 만드는 가장 중요한 안전장치다.
