## 1. 오늘 배운 것

### 1.1 모델보다 먼저 문제 유형과 평가 구조를 정해야 한다

Ames Housing의 `SalePrice`처럼 연속적인 값을 예측하는 문제는 회귀다. 지도학습에서는 입력 `X`와 정답 `y`를 구분하고, 데이터를 `train / valid / test`로 나누는 이유도 각각 다르다.

- **train:** 모델 파라미터를 학습한다.
- **valid:** 모델·하이퍼파라미터 선택과 중간 성능 확인에 사용한다.
- **test:** 모든 선택이 끝난 뒤 최종 일반화 성능을 확인한다.

특히 test를 반복해서 보며 모델을 고르면 사실상 test에 맞춰 의사결정을 하게 되므로, 더 이상 순수한 최종 평가셋이라고 보기 어렵다.

회귀에서는 평균값만 예측하는 단순 baseline도 중요하다. 복잡한 모델이 정말 의미가 있으려면 최소한 이런 기준보다 나아야 한다. 오늘 실습에서는 `y_train` 평균을 valid 전체의 예측값으로 두고 `MSE`, `RMSE`, `MAE`, `R²`를 비교하는 구조를 다시 확인했다.

- **MSE:** 오차를 제곱해 평균내므로 큰 오차의 영향이 커진다.
- **RMSE:** MSE에 제곱근을 취해 목표값과 같은 단위로 돌아온다.
- **MAE:** 절대오차의 평균이라 해석이 직관적이다.
- **R²:** 단순 평균 예측 대비 설명력이 얼마나 개선됐는지 보는 관점으로 이해할 수 있다.

### 1.2 알고리즘 이름보다 데이터와 목적에 맞는 선택 기준이 중요하다

1장 2강에서는 여러 모델의 성격을 한 번에 비교했다.

- **Linear Regression:** 연속값 예측용이며 계수와 절편을 직접 확인할 수 있어 해석이 쉽다.
- **KNN / K-means:** 거리를 사용하므로 특성 스케일에 민감하다.
- **Decision Tree:** 규칙 기반으로 공간을 나누기 때문에 일반적으로 거리 기반 모델처럼 스케일링이 필수는 아니다.
- **K-means:** 정답 없이 비슷한 관측치를 K개 군집으로 묶는 군집화다.
- **PCA:** 관측치를 그룹으로 나누는 것이 아니라 여러 특성을 더 적은 수의 새로운 축으로 압축하는 차원축소다.

K-means의 `K`는 **군집의 수**, KNN의 `K`는 **참조할 이웃의 수**라는 차이도 다시 구분했다.

### 1.3 시계열에서는 시간 순서 자체가 데이터다

Bike Sharing Demand 실습에서는 일반적인 랜덤 분할과 시계열 분할의 차이가 선명했다. 시계열을 무작위로 섞으면 미래 관측치가 train에 들어가 실제 운영 상황인 “과거로 학습해 미래를 예측”하는 구조가 깨질 수 있다.

따라서 다음 순서를 유지했다.

> 시간 정렬 → Trend / Seasonality / Residual 확인 → 정상성 진단 → 필요 시 차분 → 과거 Train / 이후 Test 분리 → 예측

`seasonal_decompose()`에서는 장기 변화인 **Trend**, 일정 주기로 반복되는 **Seasonality**, 둘을 제거한 뒤 남는 **Residual**을 나눠 보았다. ADF Test로 정상성을 진단하고, 정상성이 부족한 경우 1차 차분 후 다시 확인하는 흐름도 정리했다.

ARIMA의 `order=(p, d, q)`는 다음 의미다.

- `p`: AR이 참고하는 과거 실제값의 차수
- `d`: 차분 횟수
- `q`: MA가 참고하는 과거 예측오차의 차수

실습에서는 `ARIMA(2, 1, 1)`을 사용하고, 마지막 6개월을 시간 순서 그대로 Test로 두어 예측값과 실제값을 비교하는 구조를 만들었다. 추가 실습에는 ADF를 이용한 `d` 판단, 95% 예측구간, MAE/RMSE 평가도 포함됐다.

### 1.4 분석 결과를 Streamlit 화면까지 연결할 수 있다

시계열 분석은 노트북 안에서 끝내지 않고 Streamlit 웹앱 구조로도 연결했다.

흐름은 다음과 같다.

1. 사용자가 CSV를 업로드한다.
2. `datetime`을 날짜/시간으로 변환하고 정렬한다.
3. 월별 `count` 합계를 만든다.
4. 사용자가 1·3·6개월 중 예측 기간을 선택한다.
5. 전체 월별 데이터에 ARIMA 모델을 학습한다.
6. 선택한 기간만큼 미래 값을 예측해 표와 그래프로 보여준다.

`uploaded_file is not None` 같은 조건은 단순 문법이 아니라, 입력이 준비되기 전에 파일을 읽으려는 실행을 막는 UI 상태 가드라는 점도 중요하다.

### 1.5 편향-분산은 Train 점수 하나가 아니라 곡선과 gap으로 봐야 한다

3장에서는 Decision Tree의 깊이를 바꾸며 `learning_curve`와 `validation_curve`를 사용해 underfitting과 overfitting을 비교했다.

- 모델이 너무 단순하면 train과 validation 모두 성능이 낮을 수 있다.
- 모델이 너무 복잡하면 train은 좋아지지만 validation과의 차이가 커질 수 있다.
- 좋은 복잡도는 train 성능만 최대화하는 값이 아니라 validation 성능과 두 집합의 gap을 함께 봐야 한다.

즉 **학습오차가 낮다 = 좋은 모델**은 아니다. 일반화 성능을 함께 확인해야 한다.

### 1.6 Ridge, Lasso, ElasticNet은 복잡도를 계수에 벌점으로 제어한다

규제 파트에서는 선형모델의 계수를 그대로 크게 두지 않고 벌점을 추가해 과적합을 완화하는 방식을 다시 정리했다.

- **Ridge(L2):** 계수를 전반적으로 줄이는 방향이다.
- **Lasso(L1):** 일부 계수를 0으로 만들 수 있어 변수 선택 효과가 생길 수 있다.
- **ElasticNet:** L1과 L2를 함께 사용한다.

Ridge에서는 `alpha`를 바꾸며 R²와 계수 크기의 변화를 비교했고, Lasso와 ElasticNet도 같은 데이터에서 나란히 확인했다. 다중공선성 진단용 VIF도 Train 데이터에서 계산해 규제모델 비교와 연결했다.

### 1.7 불균형 데이터에서는 Accuracy 하나만 보면 위험하다

한 클래스가 압도적으로 많은 데이터에서는 모든 샘플을 다수 클래스로 예측해도 Accuracy가 높게 나올 수 있다. 그래서 불균형 분류에서는 다음 지표를 함께 본다.

- Recall
- Precision / F1
- PR-AUC
- Confusion Matrix

대응 방법으로는 `class_weight`, Random Under Sampling, SMOTE를 비교했다. 여기서 중요한 규칙은 **SMOTE 같은 재표본화는 Train에만 적용해야 한다**는 것이다. validation/test까지 합성하면 평가 데이터의 독립성이 깨지고 leakage가 생긴다.

임계값도 0.3, 0.5, 0.7처럼 바꾸며 Recall과 Precision의 trade-off를 확인하도록 구성했다. 분류 확률을 0.5에서 자르는 것은 자연법칙이 아니라 의사결정 기준이라는 점과 연결된다.

### 1.8 교차검증도 전처리 경계를 잘못 잡으면 leakage가 생긴다

불균형 분류에서는 일반 `KFold`보다 각 fold의 클래스 비율을 보존하는 `StratifiedKFold`가 적합할 수 있다.

더 중요한 점은 스케일링과 SMOTE를 **교차검증 바깥에서 먼저 전체 데이터에 적용하지 않는 것**이다. `Pipeline` 안에 전처리와 모델을 함께 넣으면 각 fold의 Train 부분에서만 `fit`이 일어나도록 경계를 유지할 수 있다.

오늘 정리한 원칙은 다음과 같다.

> 교차검증은 단순히 데이터를 여러 번 나누는 기법이 아니라, 매 fold에서 실제 미래 데이터처럼 평가셋을 격리하는 절차다.

### 1.9 Bagging과 Boosting은 여러 모델을 쓰지만 결합 방식이 다르다

앙상블 파트에서는 Decision Tree 하나와 Bagging, Random Forest, Gradient Boosting, XGBoost, LightGBM을 비교했다.

- **Bagging / Random Forest:** 여러 모델을 병렬적으로 학습해 평균화하며 분산을 줄이는 방향이다.
- **Boosting:** 앞 모델이 놓친 부분을 뒤 모델이 순차적으로 보완한다.

Random Forest에서는 OOB score와 feature importance, 트리 수 증가에 따른 안정성을 확인했고, Boosting에서는 `staged_predict`, `learning_rate × n_estimators`, early stopping을 다뤘다.

모델 선택에서 정확도만 보는 대신 학습 시간과 검증 성능을 같이 보는 구조도 중요했다.

### 1.10 SHAP은 “무엇을 근거로 예측했는가”를 보는 도구이지 인과 증명이 아니다

Random Forest와 XGBoost의 성능을 비교한 뒤 feature importance와 TreeSHAP을 이용해 모델 해석으로 넘어갔다.

- **Global SHAP:** 전체 데이터에서 어떤 특성이 예측에 많이 기여했는가?
- **Local SHAP:** 특정 한 샘플의 예측에 어떤 특성이 어느 방향으로 기여했는가?

SHAP 값이 크다고 해서 현실 세계에서 그 변수가 결과의 원인이라고 증명되는 것은 아니다. 어디까지나 **학습된 모델의 예측 구조를 설명하는 값**이다.

### 1.11 하이퍼파라미터 튜닝도 평가셋을 보호하는 구조가 먼저다

마지막에는 GridSearchCV, RandomizedSearchCV, Optuna TPE를 비교했다.

- **Grid Search:** 지정한 조합을 체계적으로 전부 탐색한다.
- **Randomized Search:** 주어진 예산만큼 무작위로 후보를 탐색한다.
- **Optuna/TPE:** 이전 trial 결과를 이용해 다음 탐색 위치를 더 효율적으로 고른다.

탐색 방식이 달라도 비교 조건은 같아야 한다. 같은 CV 기준에서 baseline과 tuned model을 비교하고, hold-out Test는 최종 모델을 정한 뒤 한 번 확인하는 흐름이 중요하다.

## 2. 다시 확인한 질문과 답

### Q1. 시계열은 왜 일반 `train_test_split()`로 무작위 분할하면 안 될까?

미래 데이터가 Train에 섞이면 미래 정보를 이용해 과거를 맞히는 형태가 될 수 있다. 실제 배포 상황과 다른 평가가 되므로 시간 순서를 유지해 과거를 Train, 이후 기간을 Test로 두는 것이 기본이다.

### Q2. K-means의 K와 KNN의 K는 같은 뜻일까?

아니다. K-means에서는 만들 **군집 수**, KNN에서는 예측할 때 참고할 **이웃 수**다. 둘 다 거리 개념을 사용하지만 목적은 다르다.

### Q3. SMOTE를 전체 데이터에 먼저 적용하면 왜 안 될까?

validation/test에 해당하는 정보까지 이용해 합성 샘플을 만들 가능성이 생기기 때문이다. 교차검증에서는 SMOTE를 Pipeline 내부에 넣어 각 fold의 Train 부분에만 적용해야 한다.

### Q4. Test 성능을 여러 번 확인하며 모델을 골라도 될까?

그렇게 하면 Test 결과가 모델 선택 과정에 영향을 주므로 Test가 사실상 validation 역할을 하게 된다. 최종 일반화 평가를 위해서는 모델 선택을 끝낸 뒤 Test를 확인하는 구조가 더 안전하다.

즉, 자동화가 늘어날수록 “어떤 결과가 어디까지 검증됐고 어느 저장소가 그 사실을 소유하는가”를 문서 계약으로 남기는 것이 중요하다.

## 4. 아직 확인할 것

`ML_3`의 실제 수치 결과를 학습 기록에 남기려면 로컬 데이터로 각 노트북을 실행해 출력과 그래프를 확인해야 한다. 현재 GitHub에 반영된 풀이만으로는 실행되지 않은 metric 값을 확정하지 않는다.

Streamlit `app.py`도 코드가 작성된 것과 실제 로컬에서 업로드→집계→ARIMA 학습→예측까지 end-to-end로 실행된 것은 별개의 검증이다. 필요하면 별도 실행 결과를 남긴다.

Career System의 STATUS는 작업 재개용 snapshot이므로, 다음 작업을 시작할 때는 문서에 적힌 SHA나 열린 PR 상태를 그대로 믿지 않고 GitHub 원격 상태를 다시 확인해야 한다.
