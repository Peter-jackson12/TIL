## 1. 오늘 배운 것

### 피처 엔지니어링·파생변수·피처 선택·하이퍼파라미터 구분

- **피처 엔지니어링**은 원본 정보를 모델이 쓰기 좋은 입력으로 표현하는 작업이다. 결측 처리, 범주 인코딩, 구간화, 조합 변수 생성 등이 포함된다.
- **파생변수**는 기존 값으로 새로 만든 변수다. 건물 나이의 구간, 재료 사용 개수, 두 범주의 조합 등이 예다. 파생변수 생성은 피처 엔지니어링의 일부다.
- **피처 선택**은 후보 입력 중 사용할 것을 고르는 작업이다. 변수를 추가하는 것과 구분한다.
- **하이퍼파라미터**는 트리 깊이, 정규화 강도처럼 학습 방식이나 모델 복잡도를 정하는 설정이다. 파생변수 자체와는 다르지만, 구간 경계나 희귀 범주 통합 기준처럼 전처리에도 조정할 설정이 있을 수 있다.

희귀 범주를 묶을 때는 전체 데이터의 빈도로 결정하지 않고 **각 학습 폴드에서 기준을 학습한 뒤 검증 데이터에 적용**해야 한다. 새 범주를 만났을 때의 처리도 함께 정한다.

지진 프로젝트의 넓은 피처 실험 보고서는 논리적 변수 수와 원-핫 인코딩 후 행렬의 열 수를 따로 기록했다. 범주 조합 몇 개를 추가해도 실제 입력 차원은 크게 늘 수 있다. 또한 정규화된 면적·높이 값으로 만든 비율을 실제 면적·높이의 물리적 단위로 해석하면 안 된다.

### 정밀도와 재현율은 분모가 다르다

피해 3등급을 양성으로 보는 경우:

- **Precision(정밀도)**: 3등급으로 예측한 건물 중 실제 3등급의 비율이다.
- **Recall(재현율)**: 실제 3등급 건물 중 3등급으로 찾아낸 비율이다.
- **F1**은 정밀도와 재현율의 조화평균이다. **Macro F1**은 등급별 F1을 동일한 비중으로 평균한다.

3등급을 더 쉽게 예측하도록 결정 규칙을 바꾸면 실제 3등급을 더 많이 찾을 수 있지만, 다른 등급을 3등급으로 잘못 분류하는 경우도 늘 수 있다. 따라서 Recall 하나의 상승만으로 개선을 확정하면 안 된다. 혼동행렬에서 **어느 방향의 오류가 줄고 늘었는지** 함께 봐야 한다.

오류의 중요도와 비용은 팀 문제 정의에서 합의할 사항이다. 단일 지표를 보고 임의의 비용 비율이나 실제 재난 대응 효과를 만들어 붙이지 않는다.

### 정답을 사용한 입력 변수와 정상적인 타깃 인코딩은 다르다

검토한 노트북 코드에는 건물의 피해 등급을 조건에 넣어 입력 후보를 만드는 경로가 있었다. 이런 변수는 예측하려는 정답을 미리 알아야 계산할 수 있으므로 **직접적인 타깃 누수 위험**이 있다.

- 정답 열 하나만 마지막에 삭제해도, 이미 정답으로 만든 파생변수에 정보가 남아 있으면 해결되지 않는다.
- 데이터를 나눈 뒤 같은 행의 정답으로 파생변수를 만드는 것도 해결책이 아니다. 실제 예측 시점에 계산할 수 있는 입력인지 먼저 확인해야 한다.
- 반면 타깃 인코딩은 학습 데이터의 범주별 정답 통계를 표현하는 기법이다. 학습 행에는 교차 적합 등을 적용하고, 검증·테스트 행에는 해당 행의 정답을 쓰지 않는 방식으로 설계해야 한다.
- 평균·빈도처럼 정답을 사용하지 않는 통계라도 분할 전에 전체 데이터로 학습하면 검증 데이터의 분포가 전처리에 들어갈 수 있다. 직접적인 정답 누수와 구분하되, 학습·검증 경계는 지켜야 한다.
- 정답과의 연관성을 이용한 변수 선택도 학습 폴드 안에서 수행해야 한다. 파이프라인 밖에서 전체 자료로 미리 선택했다면 나중에 파이프라인으로 감싸도 그 누수가 사라지지 않는다.

**확인 범위:** 노트북의 코드 경로를 검토한 내용이다. 노트북이 다시 읽는 실제 파생 CSV의 생성·저장 이력과 실행 당시 입력은 확인하지 못했다. 특정 점수가 얼마나 부풀려졌는지, 수정 후 재실행이 끝났는지는 확인된 결과로 기록하지 않는다.

## 2. 프로젝트 보고서에서 배운 검증 방법

아래 내용은 공개 저장소의 고정 커밋에 있는 보고서를 읽고 정리했다. 이 TIL 작성 과정에서 모델을 새로 학습하거나 원본 데이터로 재검증한 결과는 아니다.

### 같은 결과를 재현하는 것과 다른 조건에서도 잘 되는 것은 별개다

TE·ROS·RF 재현 보고서는 기존 층화 분할 결과를 재현한 뒤 지역 그룹 분할에서 별도로 평가했다. 같은 지역의 특성이 학습·검증에 함께 나타나는 조건과 처음 보는 지역을 평가하는 조건은 질문이 다르다.

- 층화 CV 점수만으로 미관측 지역에 대한 일반화를 주장하지 않는다.
- 여러 전처리 변경을 함께 적용한 결과에서는 개별 변경의 기여를 분리해서 단정하지 않는다.
- 실패한 실행 시도, 수정한 실행 조건, 최종 완료 결과를 함께 남겨야 재현 과정이 설명된다.
- 교차검증의 폴드와 반복 시드는 같은 건물을 다시 사용한다. 반복된 예측 행 수를 독립적인 새 표본 수처럼 세면 안 된다.

### 결정 규칙도 검증 데이터에 맞춰 고르면 과적합될 수 있다

3등급 결정 규칙 보고서는 바깥 검증 폴드를 직접 보고 보정값을 고르는 대신, 바깥 학습 데이터 안의 추가 분할로 보정값을 선택했다.

규칙 보정 전후 비교는 동일 모델·동일 외부 폴드에서 해야 한다. 어떤 모델에서 개선된 규칙이 다른 모델에서도 유효하다는 보장은 없다. 이미 생성한 OOF 예측을 이용한 후보 동결은 새 독립 평가와도 구분한다.

### 변수를 많이 만들었다고 개선된 것은 아니다

넓은 피처 실험에서는 변수 수를 늘린 후보의 평균 Macro F1이 조금 높아졌지만, 보고서에 미리 정한 개선 기준에는 못 미쳤고 큰 과소평가 오류도 늘었다. 따라서 “피처 추가 성공”으로 단순 요약하지 않았다.

여기서 가져갈 점은 다음과 같다.

1. 분모가 0인 비율, 처음 보는 범주·지역의 대체값을 정의한다.
2. 지역 통계와 상수·중복 변수 제거 기준은 학습 폴드에서만 구한다.
3. 같은 분할·같은 기준선과 비교하고, 주지표와 등급별 오류를 함께 확인한다.
4. 같은 개발 자료를 반복해서 탐색하면 선택 편향이 남는다. 반복 CV의 표준편차를 곧바로 독립 표본의 표준오차로 해석하지 않는다.
5. 후보 실험 완료와 최종 모델 확정, 홀드아웃 평가, 서비스 배포를 각각 구분한다.

확인한 최신 연구 상태 문서에는 후속 실험 완료 및 감사 결과가 기록되어 있었다. 이는 **저장소의 완료 보고를 확인한 것**이며, 팀 공통 모델 채택이나 최종 평가를 이번 기록에서 새로 확정한 것은 아니다.

## 3. GitHub 협업에서 정리한 것

오늘은 팀원이 VS Code에서 같은 프로젝트를 받고 개인 브랜치로 작업한 뒤 PR을 보내는 흐름과, 다른 사람의 브랜치가 보이지 않을 때의 확인 방법을 질문했다.

- VS Code에 GitHub 로그인하는 것과 프로젝트 저장소를 **clone하여 연결하는 것**은 별개다.
- 먼저 올바른 저장소를 열고 원격 저장소 주소가 팀 저장소를 가리키는지 확인한다.
- **fetch**는 원격의 최신 커밋·브랜치 정보를 가져온다. 현재 작업 브랜치에 자동으로 병합하는 단계는 아니다.
- 원격 브랜치가 보여도 로컬 브랜치가 자동 생성된 것은 아니다. 해당 원격 브랜치를 추적하는 로컬 브랜치로 전환해야 한다.
- 원격에서 확인되지 않는 브랜치는 아직 push되지 않았거나 다른 원격·포크에 있을 수도 있다. 단순 화면 새로고침만으로 해결된다고 단정하지 않는다.
- 개인 브랜치에 commit → push → PR 생성 → 변경 검토 → merge의 순서로 공통 브랜치에 반영한다.
- PR의 base와 compare 방향, 변경 파일 범위, 데이터·비밀값 포함 여부, 검사 결과를 함께 확인한다.

이 항목은 질문을 통해 정리한 협업 절차다. 각 팀원의 로컬 설정이나 fetch·PR 생성 성공을 직접 확인했다는 뜻은 아니다.

## 4. 데이터 검증 코드를 읽으며 배운 일반 원칙

별도 작업의 코드 변경에서는 공개 가능한 일반 원칙만 추려 기록한다.

- 저장된 “검증 통과” 표시만 신뢰하지 않고 실제 데이터와 메타데이터에서 조건을 다시 계산해 대조한다.
- 개수뿐 아니라 식별자 집합, 중복, 누락, 제외 이유가 서로 일치하는지 검증한다.
- 시간은 시간대 포함 여부와 순서를 확인하고, 서로 다른 표현이 같은 시점을 가리키는지도 점검한다.
- 과거 형식의 기록을 읽을 때는 당시 버전의 검증 규칙을 명시한다. 현재 설정 변경이 과거 기록의 의미를 조용히 바꾸지 않도록 한다.

변경 내용의 검토와 테스트 재실행은 다르다. 이 기록에서는 해당 작업의 테스트를 직접 재실행하거나 운영 상태를 검증하지 않았다.
