### 1.1 BI와 Tableau의 기본 구분

BI는 데이터를 연결·정리하고 질문에 맞는 지표와 시각화로 의사결정을 돕는 흐름이다. 차트를 먼저 고르기보다 **무엇을, 어떤 단위와 집단에서 비교할지**를 정한다.

- **자료형**은 문자열·숫자·날짜 등 값의 형식이다.
- **차원 / 측정값**은 분석에서의 역할이다. 차원은 묶는 기준, 측정값은 합계·평균처럼 집계할 대상이다. 숫자로 저장된 식별자도 차원으로 쓸 수 있다.
- **불연속 / 연속**은 뷰에서 값을 표시하는 방식이다. 불연속 필드는 개별 머리글, 연속 필드는 축을 만든다. 차원과 불연속, 측정값과 연속을 같은 뜻으로 외우지 않는다.
- **Live**는 원본에 질의하는 연결, **Extract**는 추출해 저장한 데이터를 사용하는 방식이다. 추출의 갱신 시점과 원본의 최신성은 별도로 확인한다.

마크 카드의 색상·크기·레이블·세부 정보(Detail)는 표현과 분석 단위를 바꾼다. Detail에 차원을 추가하면 기존 마크가 더 세분될 수 있다. 화면에 글자를 표시하는 레이블과 같은 역할은 아니다.

차트는 질문에 맞춘다. 범주 간 크기는 막대, 시간 추이는 선, 두 수치의 관계는 산점도, 분포는 히스토그램·상자그림처럼 선택한다. 차트 종류보다 분모·집계 기준·축·필터를 먼저 확인한다.

### 1.2 데이터 결합과 행의 단위

| 방식 | 핵심 | 확인할 점 |
|---|---|---|
| Join | 키를 기준으로 테이블의 열을 결합 | 일대다·다대다에서 행이 늘어 측정값이 중복될 수 있음 |
| Union | 비슷한 구조의 행을 아래로 이어 붙임 | 열 이름·자료형·중복 행 여부 |
| Relationship | 논리 계층에서 테이블 관계를 정의 | 각 테이블의 단위를 유지하며 분석에 맞게 결합되지만 관계 키·카디널리티 검토는 필요 |
| Data Blending | 별도 데이터 원본을 집계한 결과를 연결 | 주/보조 원본과 연결 필드, 집계 수준에 주의 |

물리 계층의 Join·Union과 논리 계층의 Relationship을 구분한다. Tableau Prep은 분석 전에 정리·변환하는 데이터 준비 흐름을 구성할 때 사용한다.

예를 들어 주문 1건과 주문상품 여러 행을 결합하면 주문 총액이 상품 수만큼 반복될 수 있다. 결합이 성공했다는 것과 합계가 맞다는 것은 별개다. **한 행이 무엇인지 → 결합 후 행수와 고유 키 수 → 합계와 분모** 순서로 점검한다.

### 1.3 계산 필드와 집계 수준

- `IF`는 조건식을 순서대로 평가하고, `CASE`는 기준 표현식의 값과 `WHEN` 값을 비교한다.
- `IIF`는 조건에 따라 값을 반환하며 NULL로 인한 unknown 처리도 고려한다.
- `SUM`은 합계, `COUNT`는 NULL이 아닌 값의 개수, `COUNTD`는 NULL을 제외한 고유 값 개수다.
- 매개변수는 계산이나 필터 등에 연결해서 쓰는 입력값이다. 매개변수를 만들기만 해서는 뷰가 자동으로 달라지지 않는다.
- 행 수준 값과 집계값을 한 식에서 무심코 섞으면 오류나 의도와 다른 계산이 생긴다. 원하는 분석 단위를 먼저 정한 뒤 식의 수준을 맞춘다.

비율에서 특히 주의한다.

```text
AVG([이익] / [매출])        : 각 행의 이익률을 같은 비중으로 평균
SUM([이익]) / SUM([매출]) : 전체 이익을 전체 매출로 나눈 비율
```

두 식은 일반적으로 다르다. 매출 0·NULL 처리도 필요하며, 전체 이익률을 구하려는 질문에는 합계의 비율이 맞는지 먼저 판단한다.

### 1.4 LOD: 화면과 다른 수준에서 계산하기

- `FIXED`: 지정한 차원을 기준으로 계산한다.
- `INCLUDE`: 현재 뷰의 차원에 지정한 차원을 더해 세부적으로 계산한다.
- `EXCLUDE`: 현재 뷰의 차원 중 지정한 차원을 제외해 계산한다.

```text
{ FIXED [고객 ID] : SUM([매출]) }
{ INCLUDE [주문 ID] : SUM([매출]) }
{ EXCLUDE [지역] : SUM([매출]) }
```

위 식은 개념을 정리한 예시이며, 오늘 실행 결과를 기록한 것은 아니다. 주문 ID가 데이터에서 실제로 유일한지, 한 주문이 여러 행인지도 확인해야 한다.

관련 필터·계산 순서는 **컨텍스트 필터 → FIXED → 일반 차원 필터 → INCLUDE/EXCLUDE**로 이해했다. 이 앞에는 추출·데이터 원본 필터 등이 있으므로 Tableau 전체 처리 순서를 네 단계만으로 생각하지 않는다.

FIXED 결과가 일반 차원 필터에 기대한 대로 반응하지 않으면 계산 수준과 필터 순서를 함께 본다. 무조건 컨텍스트로 바꾸기보다 어떤 집단을 분모로 유지하려는지 먼저 정한다.

### 1.5 테이블 계산: 이미 만들어진 뷰 위에서 계산하기

- `RANK(SUM([매출]))`: 현재 계산 범위 안에서 집계 매출의 순위를 구한다.
- `TOTAL(SUM([매출]))`: 계산 범위의 합계다.
- `RUNNING_SUM(SUM([매출]))`: 정해진 방향·순서로 누적한다.
- `WINDOW_AVG(SUM([매출]), -2, 0)`: 현재 마크와 앞의 두 마크를 포함하는 창의 평균이다.

`WINDOW_AVG(..., -2, 0)`이 항상 “3개월 평균”인 것은 아니다. 월별 마크와 정렬·누락 월 처리가 갖춰져야 그렇게 읽을 수 있다. 시작 부분에는 앞선 마크가 부족해 실제 평균 대상 수가 적을 수도 있다.

**Addressing**은 어느 차원을 따라 계산을 진행하는지, **Partitioning**은 어디에서 계산 집단을 나누고 다시 시작하는지다. 같은 계산식이라도 계산 방향·파티션·정렬에 따라 값이 달라진다. LOD가 데이터의 집계 수준을 정한다면 테이블 계산은 뷰에 만들어진 마크를 대상으로 계산한다.

### 1.6 그래프 인접 리스트와 연결 요소

무방향 그래프에서 간선 `u-v`는 인접 리스트 양쪽에 기록한다. 모든 정점을 순회하면서 아직 방문하지 않은 정점에서 DFS/BFS를 시작하면, 새 탐색을 시작한 횟수가 연결 요소 수다.

- 한 번의 탐색은 시작 정점에서 도달할 수 있는 정점들을 방문한다.
- 간선이 없는 고립 정점도 연결 요소 하나다.
- 간선에 등장한 정점만 저장하면 고립 정점을 빠뜨릴 수 있다.
- 인접 리스트 기반 전체 탐색은 정점 수 V와 간선 수 E에 대해 O(V+E)다.

오늘은 이 개념을 확인했다. 별도 문제의 풀이 완료나 채점 통과는 확인하지 않았다.

## 2. 내가 궁금했던 질문과 이해한 답

### Q1. Tableau의 차원별 집계는 SQL GROUP BY처럼 이해해도 될까?

입문 비유로 유용하다. `GROUP BY 지역`으로 지역별 합계를 만드는 것처럼, 뷰의 차원 조합이 측정값을 어떤 단위로 묶어 보여 줄지 결정한다.

다만 Tableau에는 Detail의 차원, 필터 순서, LOD, 테이블 계산이 함께 작용한다. 화면의 계산을 SQL 한 문장의 GROUP BY와 완전히 동일시하기보다는 **어떤 차원 조합마다 값 하나를 만드는가**를 묻는 출발점으로 사용한다.

### Q2. 주문 평균과 고객별 합계의 평균은 왜 다른가?

주문마다 같은 비중을 주는지, 고객마다 같은 비중을 주는지가 다르다.

- 주문당 평균: 주문별 금액을 구하고 주문 수를 기준으로 평균낸다.
- 고객당 평균 매출: 고객별 매출 합계를 구한 뒤 고객을 같은 비중으로 평균낸다.

고객마다 주문 수가 다르면 두 값도 달라진다. FIXED로 고객 합계를 만들었더라도 그 값이 원래 행에 반복된 상태에서 평균내면 행 수의 영향을 받을 수 있다. **LOD 식만 보지 말고 최종 집계의 단위와 가중치까지 확인한다.**

### Q3. R²와 R²의 표준편차는 같은 뜻인가?

R²는 회귀의 결정계수다. 평가 데이터의 평균을 예측하는 기준과 비교해 제곱오차가 얼마나 줄었는지 나타낸다. 보통 1에 가까울수록 좋고, 0보다 작을 수도 있다.

CV에서 각 폴드의 R²를 구한 뒤:
- 평균 R²는 그 분할들에서의 평균 성능을 본다.
- R² 표준편차는 폴드 사이 점수가 얼마나 달라지는지 본다.

표준편차는 점수 자체도, R² 공식의 “분산 설명”과 같은 값도 아니다. 평균이 낮은 모델이 일관되게 낮은 점수를 낼 수도 있으므로 안정성만 보고 선택하지 않는다. 폴드 점수의 표준편차를 그대로 신뢰구간으로 해석하지도 않는다.

### Q4. Optuna는 어떤 역할로 나뉘나?

| 구성 | 역할 |
|---|---|
| Objective | 한 후보를 평가하고 최적화할 점수를 반환하는 함수 |
| Trial | 하이퍼파라미터 한 조합을 제안받아 평가하는 1회 |
| Study | 여러 trial의 탐색 과정과 결과를 관리 |
| Sampler | 다음 후보를 제안하는 방식 |

이번 코드는 `TPESampler(seed=42, n_startup_trials=3)`와 `n_trials=9`를 사용한다. 정상적으로 순차 완료되는 코드 흐름에서는 처음 3회가 시작용 무작위 탐색이고 이후 6회가 축적된 결과를 이용하는 TPE 제안이다. 지정한 정수 범위 안에서 유망한 후보를 찾는 방식이며, 전역 최적을 보장하지 않는다.

Pruning은 성능이 좋지 않은 trial을 중간에 중단하는 별도 기능이다. **이번 objective에는 report·should_prune 같은 중간 보고·중단 코드가 없다.** Optuna를 사용했다는 이유만으로 가지치기를 수행했다고 쓰지 않는다.

### Q5. 배깅과 부스팅은 편향·분산 중 무엇을 주로 줄이나?

일반적인 설명으로 배깅·랜덤포레스트는 여러 모델의 예측을 합쳐 **주로 분산을 줄이고**, 부스팅은 앞 단계의 부족한 예측을 순차적으로 보완해 **주로 편향을 줄인다**. 실제 편향·분산 변화는 데이터·기본 학습기·규제·반복 수에 따라 달라지므로 둘을 배타적인 법칙처럼 외우지 않는다.

## 3. 진행 중인 실습과 확인한 산출물

### 3.1 ML 6장 1강: 세 가지 탐색을 같은 기준으로 비교

Ames Housing의 `SalePrice`를 숫자형 특성 12개로 예측하는 RandomForestRegressor 코드다. 학습/hold-out을 80/20으로 나누고 `random_state=42`를 사용한다.

| 탐색 | 후보 설정 | 탐색 중 CV 학습 횟수 |
|---|---|---:|
| GridSearchCV | 트리 수 100/200/300 × 깊이 4/8/12 | 9 × 5 = 45 |
| RandomizedSearchCV | 트리 수 100~300, 깊이 4~12의 정수에서 9회 | 9 × 5 = 45 |
| Optuna TPE | 같은 정수 범위, 9 trial | 9 × 5 = 45 |

세 방식 모두 5-fold·R²를 사용하지만 **탐색 공간은 완전히 같지 않다.** Grid는 9개 격자 조합만, RandomizedSearch와 Optuna는 그 사이 정수도 후보로 삼는다. RandomizedSearch의 `randint(100, 301)`·`randint(4, 13)`에서 상한은 제외된다.

45회는 탐색 중 모델 적합 횟수다. Grid/RandomizedSearch는 기본 refit에 따른 전체 학습 데이터 적합 1회가 추가된다. Optuna 뒤의 최적 후보 CV 재평가, 기준/튜닝 후보 비교, 최종 적합도 별도다. 따라서 노트북 전체 학습 횟수를 방식당 45회로 세면 안 된다.

마지막 셀의 흐름은 다음과 같다.

1. 후보별 CV 평균을 우선 비교하고, 동점이면 표준편차·시간을 참고한다.
2. 기준 RF와 선택한 튜닝 후보를 같은 5개 폴드에서 비교한다.
3. 튜닝의 평균 검증 R²가 좋아지면 튜닝 후보, 아니면 기준 모델을 선택한다.
4. 최종 모델을 학습 데이터 전체에 적합한 뒤 hold-out을 한 번 평가한다.
5. 모델과 설정·평가 메타데이터를 저장한다.

`cross_validate` 결과의 `test_score`는 **CV 안의 검증 폴드 점수**다. 처음 분리한 hold-out 점수와 이름이 비슷해도 다른 데이터에서 나온다. 후보 선택에 사용한 CV는 선택 낙관성이 있을 수 있으므로 hold-out을 반복해서 보며 후보를 바꾸지 않는다.

**확인 범위:** 실습은 진행 중이다. 확인한 GitHub 노트북의 코드 셀 6개에는 저장 출력이 없었다. 실제 최적 조합·R²·시간·저장 파일 생성 여부는 이 파일만으로 확인할 수 없어 수치를 적지 않았다. 저장 출력이 없다는 사실로 로컬에서 실행하지 않았다고 단정하지 않는다. 이번 TIL 작성 과정에서도 모델을 재실행하지 않았다.

### 3.2 Tableau Public 게시와 수업 개념의 연결

Airplane의 [공개 Tableau 포트폴리오](https://public.tableau.com/app/profile/.82847805/viz/airplane_portfolio/1)에 지연 패턴·날씨와 지연·모델 오류의 세 탭이 게시되었고, 공개 README에도 링크가 연결되었다. 세 탭 로딩을 확인한 범위이며, 모든 필터 조합이나 새로고침 동작 전체를 검증했다는 뜻은 아니다.

오늘 수업의 **집계 수준·분모·테이블 계산 범위**를 실제 대시보드를 읽는 기준으로 연결했다. 비율이 이미 집계된 자료라면 그 비율을 다시 단순 평균내기보다, 원래 분자·분모와 집단을 확인해야 한다.

공개 프로젝트 문서에는 분류기 비교·탐색 범위 확장·확률 보정 결과도 추가되었다. 수업과 연결해 기억할 점은 다음이다.

- 같은 행·폴드로 비교해도 탐색 후보와 예산이 다르면 결론은 시험한 범위로 제한한다.
- 확률 보정 품질, 순위 구분 성능, 임계값을 적용한 분류 성능은 서로 다른 평가 축이다.
- 보정기는 검증 경계 안에서 적합하고 임계값 선택도 분리해야 한다.
- 오늘의 Ames 회귀 실습과 Airplane 분류 프로젝트의 결과를 서로 대신하는 근거로 쓰지 않는다.
