### 문제: 연구마다 틱을 처음부터 다시 재생하고 있었다

- 진입 피처(모멘텀·변동성·체결 대금 등)를 연구마다 원본 틱에서 다시 계산했다. 설계 문서 기준으로 한 연구의 격자 계산은 날짜당 1.6~2.0시간이 걸렸고, 같은 이름의 피처가 연구마다 다른 정의로 구현될 위험도 있었다.
- 목표: **전 보통주 × 30초 격자** 피처 표(약 114개 열, float32)를 날짜별로 한 번 만들고, 이후 연구는 같은 정의·같은 해시의 표를 읽는다.

### 해결 1: 누수 차단을 구조로 고정

| 원칙 | 설계 내용 |
|---|---|
| 시각 절단 | 시각 `t`의 피처는 `received_ns < t_ns` 이벤트만 사용(같은 ns는 미래로 봄). 기존 동결 함수와 정의가 같은지 회귀 검사 |
| 결측 | 창 전체를 관측하지 못했으면 null. 부분 창 외삽·0 채우기 금지 |
| 횡단면 순위 | 같은 `t`의 행끼리만 계산 |
| 정적 자료 | 공개 시각이 `t`보다 늦은 값은 사용하지 않음 |
| 라벨(미래 수익) | 별도 봉인 저장소. 피처 코드가 라벨 코드를 import하지 못하게 함 |
| 결속 | 날짜별 manifest에 입력·코드·피처 목록·환경의 SHA256 |

아래는 "엄격한 `<` 절단"을 이해하려고 AI가 정리한 예시 코드다(프로젝트 코드 아님).

```python
import numpy as np

def signal_cut(received_ns: np.ndarray, t_ns: int) -> int:
    """t 시점에 알 수 있는 이벤트 수. 같은 ns는 포함하지 않는다."""
    return int(np.searchsorted(received_ns, t_ns, side="left"))
```

### 해결 3: 2GiB 상한에서 터진 횡단면 계산을 시간축으로 분할

- **문제:** 장 전체(08:00~15:35) 전 종목 횡단면 피처를 한 번에 메모리에 올리자 프로세스당 2GiB 상한을 넘었다.
- **해결:** 상한을 올리는 대신 격자 시각 `t_s` 구간별로 나눠 계산했다. 횡단면 피처는 같은 `t`끼리만 계산하므로 `t_s`로 잘라도 결과가 바뀌지 않는다는 것이 근거다. 기록상 같은 날짜가 최대 약 1.4GiB로 통과했다.
- 확인일용 기준 변환기와 대조(5일)도 같은 밤 통과했다. 피처 목록 v1 동결은 사용자 결정 2건이 남아 있다.

## 2. 내가 궁금했던 질문과 이해한 답

### 여러 AI 세션을 동시에 쓰면 결정은 어디에 남겨야 할까?

- 이 프로젝트는 조정 세션(컨트롤 타워) 하나가 사용자 결정을 위키(현재 상태·작업표·연구 상시 규칙)에 기록하고 작업을 배정한다. 구현은 작업 ID별 세션이 각자 git worktree에서 합성 데이터로만 하고, 다른 세션이 독립 리뷰(P0~P3 등급)를 한다. 운영 반영·로그인·원본 접근·push는 사용자가 매번 승인한다.
- 앞으로도 계속 적용할 기준(비용·대상·검증 방식)은 단계 폴더 문서가 아니라 같은 날 "상시 규칙" 문서에 한 줄로 남긴다. 단계 폴더 문서는 다음 세션이 읽지 않는다는 것을 실제 사고(현금 가정 불일치)로 겪었다.
- 작업표는 덧붙이지 말고 고쳐 쓴다. 덧붙이기만 하다가 60~80KB까지 불어난 적이 있다.

### Git Bash의 `rm -rf /tmp/tmp*`는 무엇을 지우나?

- 하위 에이전트가 정리하겠다며 이 명령을 실행한 일이 기록돼 있다. Git Bash의 `/tmp`는 사용자 `%LOCALAPPDATA%\Temp`에 대응하므로 다른 프로그램의 임시 폴더까지 지웠을 수 있다(실제로 무엇이 지워졌는지는 미확인, 저장소·데이터 영향 없음으로 기록).
- 임시 파일은 세션 전용 폴더에만 만들고, 와일드카드 삭제는 쓰지 않는다.
