오늘은 파일을 GitHub에 반영하는 과정에서 “저런 걸 블롭이라고 하는 건가?”라고 질문했다. Git 객체가 맡는 역할을 구분하고, 공개 프로젝트의 README 디자인 작업을 통해 파일 생성·브랜치 반영·CI 검증이 각각 다른 단계임을 정리했다. 오늘 새로 확인된 수업 진도는 없어 전날의 머신러닝 학습을 오늘 수업으로 다시 기록하지 않는다.

## 1. 오늘 배운 것

### 1.1 blob은 파일 내용, tree는 이름과 구조를 연결한다

- **blob:** 파일의 내용을 저장하는 Git 객체다. 텍스트뿐 아니라 이미지 같은 바이너리 파일의 내용도 담을 수 있다.
- **tree:** 이름·모드·객체 ID를 연결한다. 파일 이름은 blob 자체가 아니라 tree의 항목에 들어가며, 하위 폴더는 다른 tree를 참조한다.
- **commit:** 루트 tree와 부모 커밋, 작성 정보·메시지 등을 연결하여 한 시점의 스냅샷과 이력을 표현한다.
- **브랜치 ref:** 특정 커밋을 가리키는 참조다. 새 객체를 만들었다고 자동으로 브랜치가 그 객체를 사용하는 것은 아니다.

개념적으로는 `파일 내용(blob) → 경로 구조(tree) → 이력(commit) → 브랜치 참조(ref)` 순서로 연결해 생각할 수 있다. blob 생성이 성공했더라도 해당 blob을 포함한 tree와 commit을 만들고 대상 브랜치 ref를 갱신해야 그 브랜치의 파일 목록에 반영된다.

여러 파일을 함께 바꿀 때는 최신 tree를 바탕으로 필요한 경로만 교체하고 하나의 commit으로 묶으면 파일 간 의존성이 맞는 상태를 한 번에 반영할 수 있다. 그 사이 다른 변경이 들어오면 최신 이력을 다시 확인하고, 강제 갱신으로 다른 작업을 덮어쓰지 않아야 한다.

### 1.2 README의 정적 정보와 움직이는 장식을 분리한다

오늘 공개 Airplane 디자인 기록에서는 연구 그림을 정적 SVG로 유지하고, 고양이 장식은 반복 GIF로 구성했다.

- SVG는 축·수치·본문처럼 확대해서 읽어야 하는 정적 정보에 사용했다.
- GIF는 여러 프레임을 담은 장식 애니메이션에 사용했다.
- 움직임이 부담스러운 경우를 위해 접을 수 있는 영역과 정지 그림 대안을 함께 제공했다.
- 장식이 연구 수치처럼 보이지 않도록 데이터 영역과 분리했다.

로컬에서 SVG나 CSS 애니메이션이 보이는 것과 GitHub README에 삽입했을 때 보이는 것은 따로 확인해야 한다. 파일 자체의 표현 능력만으로 게시 화면의 동작을 단정하지 않고, 실제 표시 위치에서 확인하는 것이 중요하다.

디자인 변경에서는 색과 장식을 바꾸더라도 축·단위·분모·평균·표준편차·해석 범위를 보존해야 한다. 보기 좋아졌다는 사실만으로 모델 성능이나 사용자 이해도가 개선되었다고 말할 수는 없다.

### 1.3 검증 결과에는 대상 커밋이 붙어야 한다

작업 완료를 판단할 때 다음을 구분한다.

1. 파일이나 Git 객체가 만들어졌는가?
2. 의도한 브랜치가 최종 커밋을 가리키는가?
3. 그 커밋에서 실행된 CI가 완료되었는가?
4. 화면 확인과 자동 검사가 각각 무엇을 검증했는가?

중간 커밋의 실패와 최종 커밋의 성공은 서로 다른 상태다. 과거의 초록 표시를 최종 파일의 검증으로 대신하지 않고, CI의 `head_sha`와 확인하려는 커밋을 맞춰야 한다. 자동 검사 성공 또한 모든 화면·모든 실행 환경을 검증했다는 뜻은 아니다.

## 2. 내가 궁금했던 질문과 이해한 답

### “저런 걸 블롭이라고 하는 건가?”

Git에서 저장하는 파일의 **내용 객체**를 가리킨다면 blob이 맞다. 다만 브라우저의 파일 화면, 파일 이름, 폴더 구조, 브랜치 전체를 모두 blob이라고 부르는 것은 정확하지 않다.

같은 내용을 서로 다른 파일 이름으로 저장하면 같은 blob을 참조할 수 있다. 이름과 위치는 tree가 구분한다. 따라서 “blob을 만들었다”와 “원하는 브랜치에 파일이 반영됐다”는 확인 지점이 다르다.
