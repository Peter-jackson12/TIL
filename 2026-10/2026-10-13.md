## 1. 오늘 배운 것

오늘은 이론 강의에서 **네팔 지진 피해 등급 예측 팀프로젝트**로 넘어갔다. 과제 요구사항과 문제 정의를 정리하고, 개인 브랜치의 분석 결과·참고자료를 검토했다. 실제 학습 실행은 별도 작업에서 진행되었으며, 아래 성능과 검사 결과는 공개 저장소의 보고서를 확인한 기록이다. 이 TIL을 작성하면서 원본 데이터를 다시 학습하거나 독립 재실행하지는 않았다.

### 1.1 문제 정의는 예측 대상과 활용 한계를 함께 적는다

- 분석 단위는 건물 한 채, 목표는 2015년 네팔 지진에서 관측된 피해 등급 1·2·3의 분류다.
- 건물의 위치·구조·재료와 피해의 **관련성**을 분석할 수 있지만, 변수 중요도가 곧 인과관계의 증거는 아니다.
- 단일 지진의 무작위 분할 성능만으로 미래 지진이나 다른 지역의 건물 안전을 예측할 수 있다고 일반화하지 않는다.
- 점검·내진 보강 우선순위 검토를 위한 기초 분석이라는 활용 방향과 실제 현장 의사결정에 사용 가능한 수준을 구분한다.
- 목적 문구에 동의했다는 사실이 공통 분할·오류 비용·최종 모델·역할까지 확정했다는 뜻은 아니다.

공통 문서에는 Macro F1과 함께 실제 3등급을 1·2등급으로 낮춰 예측하는 오류를 구분해 살펴보는 방향이 반영되어 있다. 개인 실험 결과를 팀 최종 성과로 옮겨 적지 않는다.

### 1.2 불균형 처리는 “했는가”보다 “무엇이 좋아지고 나빠졌는가”가 중요하다

필수 비교 모델은 Logistic Regression, Decision Tree, Random Forest, sklearn의 GradientBoostingClassifier다. 같은 개발 분할·평가 기준에서 비교해야 한다.

- **Macro F1:** 각 등급의 F1을 같은 비중으로 평균한다.
- **Accuracy:** 전체 정답 비율로, 다수 등급의 성능에 영향을 많이 받는다.
- **등급별 Precision/Recall/F1:** 전체 평균이 가리는 손익을 확인한다.
- **혼동행렬:** 3→1과 3→2처럼 오류의 방향과 크기를 확인한다. 비율을 보고할 때 분모가 실제 3등급 전체인지 명시한다.

개인 기준선에서 LR에 balanced 가중치를 적용했을 때 1등급 Recall은 올랐지만 Precision과 Macro F1은 낮아졌다. 따라서 “소수 등급을 더 찾았다”와 “전체 목적에 더 적합해졌다”는 서로 다른 판단이다.

또한 RF·GB의 낮은 초기 성능만 보고 모델 자체가 부적합하다고 결론 내리지 않았다. 학습 점수도 함께 낮은지 확인하고, 분할 후보 변수 수 제한을 완화한 비교를 검토했다. 제한된 설정에서 나온 결과와 충분히 튜닝한 모델의 성능을 구분해야 한다.

### 1.3 age=995: 특이한 값이라는 관찰과 오류라는 판정은 다르다

오늘의 질문은 **“995년처럼 보이는 연령 값을 어떻게 처리해야 하며, 다른 프로젝트는 어떻게 했는가?”**였다.

확인한 공식 설명은 age를 건물 연령으로 정의하지만, 995의 별도 코딩 의미까지 설명하지 않는다. 따라서 결측 대체 코드 또는 실제 995년 건물이라고 단정하지 않는다.

개인 브랜치에 정리한 네 참고자료는 다음처럼 접근이 달랐다.

| 참고자료 | 보고된 처리 | 참고할 때의 한계 |
|---|---|---|
| Sahil Ali 프로젝트 | 995 표시 변수를 만들고 훈련 중앙값으로 대체 | 작성자의 missing 해석과 공식 의미는 별개. 내부 CV 전처리 순서도 점검 필요 |
| Zhang/Worley 프로젝트 | 995 유지 | 유지 사례는 되지만 역사 건물이라는 해석과 검증 절차를 그대로 채택하지 않음 |
| Atheer 프로젝트 | Isolation Forest로 훈련 이상치 제거 | 995만 제거한 실험이 아니며, 희귀하지만 유효한 행을 잃을 수 있음 |
| Poudyal·Shakya 논문 | 넓은 연령 범위 등을 제거 | 연령 처리 단독 효과가 아니며, 입력·성능 보고의 일관성 한계가 있음 |

**논문에 사용되었다는 이유만으로 정답인 전처리는 아니다.** 삭제·대체가 보존하는 정보와 잃는 정보를 따져야 한다.

후속 개발 CV에서 비교할 수 있는 제안은 다음과 같다. 오늘 새로 실행해 우열을 확인한 결과는 아니다.

1. 원값 유지.
2. 원값 유지 + `age_is_995` 표시.
3. 각 학습 fold에서 995를 제외하고 구한 중앙값으로 대체 + 표시 변수.

모델·fold·검증 행을 고정하고 age 표현만 바꿔 비교한다. 피해 등급별 중앙값이나 검증 정답을 이용해 값을 바꾸면 예측 시 사용할 수 없는 정보가 들어갈 수 있다. 현재 개인 최종 모델은 기존 age=0/995 보존 정책을 유지했다.

### 1.4 전처리와 샘플링도 학습 과정에 포함된다

- 최종 평가용 데이터를 먼저 분리한다.
- 인코더·스케일러·대체값은 각 CV 학습 fold에서만 fit한다.
- 검증 fold와 최종 평가 데이터에는 학습된 변환만 적용한다.
- 오버샘플링·언더샘플링은 학습 fold 내부에만 적용한다.
- 범주형·지역 코드·이진 플래그를 일반 연속값처럼 보간하면 타당하지 않은 조합이 생길 수 있다.

개인 실험에서는 일반 SMOTENC 파일럿과 별개로, 같은 보호 특성을 가진 행 사이의 일부 수치만 보간하고 이웃이 없으면 복제하는 자체 제약형 방식을 비교했다. 이를 라이브러리 기본 SMOTENC와 같은 구현이라고 부르면 안 된다. **데이터 형식 제약을 지켰다는 사실도 실제 건물의 공학적 타당성을 보장하지 않는다.**

### 1.5 CV 평균, OOF 집계, 최종 테스트는 다른 결과다

- CV 평균은 fold별 점수의 평균이다.
- OOF 집계 점수는 각 행의 검증 예측을 모아 다시 계산한 값이다. F1처럼 비선형인 지표에서는 fold 평균과 같다고 가정하지 않는다.
- fold 표준편차는 점수의 변동 정도이며 곧바로 신뢰구간으로 읽지 않는다.
- 최종 테스트는 모델·전처리·설정 선택을 끝낸 뒤 평가한다.

개인 보고서는 후보 동결 후 홀드아웃을 한 번 평가했다고 기록한다. 이후 그 결과를 보며 팀 후보를 다시 고른다면 같은 데이터를 새로운 독립 테스트라고 부를 수 없다. 후속 age 처리 연구는 개발 CV와 구분해 설계하고, 이미 본 홀드아웃의 역할을 명시해야 한다.

### 1.6 팀 협업에서는 공통 기준과 개인 탐색을 분리한다

- `main`: 팀 공통 기반·합의한 문서.
- 개인 브랜치: 개인 전처리·모델링·참고자료와 실험 결과.
- PR: 팀에 채택할 변경의 범위와 근거를 검토한 뒤 통합.

각자 전체 분석 과정을 수행하는 것과 협업이 필요 없다는 것은 다르다. 데이터 버전·분할·평가지표·다음 공유 시점을 맞춰야 비교가 가능하다. 문서를 먼저 읽고 이미 진행 중인 분석을 중복 구현하지 않는 것도 협업의 일부다.

## 2. 내가 궁금했던 질문과 이해한 답

### Q1. 이상치는 바로 삭제하면 되는가?

아니다. 드문 값, 데이터 입력 오류, 도메인상 유효한 극단값을 구분해야 한다. 공식 의미가 확인되지 않은 age=995는 가설을 명시하고, 원본을 보존한 파생 실험으로 처리 방법을 비교하는 편이 안전하다.

### Q2. 불균형을 해결했는데 왜 점수가 떨어질 수 있는가?

가중치나 샘플링이 분류 경계를 바꾸면서 특정 등급의 Recall을 높이는 대신 Precision 또는 다른 등급 성능을 잃을 수 있다. 전체 지표와 등급별 오류를 함께 봐야 한다.

### Q3. 저장소를 받았는데 uv sync 후에도 pandas·Streamlit이 없을 수 있는가?

가상환경 활성화, 의존성 설치, 앱 실행은 다른 단계다. `uv sync`가 별도의 requirements 파일을 자동으로 읽어 모두 설치하는 것은 아니다. 이번 개인 앱의 공개 실행 안내는 `requirements-dashboard.txt`를 기준으로 한다.

대화에서 확인한 실제 오류는 다음과 같다.

```text
Failed to spawn: streamlit
program not found
ModuleNotFoundError: No module named 'pandas'
```

저장소 안내에 따른 실행 예시는 다음과 같다. **이 명령으로 사용자 PC에서 앱이 정상 실행되었다는 후속 결과는 확인하지 못했다.**

```bash
python -m pip install -r requirements-dashboard.txt
python -m streamlit run app.py
```

설치한 Python과 실행하는 Python이 같은 환경인지도 확인해야 한다. `uv run streamlit app.py`에는 Streamlit의 `run` 하위 명령도 빠져 있었다.

### 3.1 지진 개인 분석 결과 — 저장소 보고서 기준

개인 최종 보고서와 검증 기록에서 다음을 확인했다.

| 항목 | 확인 내용 |
|---|---|
| 선택 모델 | 기존 전처리 + 무가중치 Logistic Regression |
| 개발 CV Macro F1 | 0.683677 |
| 최종 홀드아웃 Macro F1 | 0.686771 |
| 최종 홀드아웃 Accuracy | 74.24% |

이 수치는 **개인 브랜치의 보고된 결과**이며 팀 최종 선정·제출 완료를 뜻하지 않는다. CI 성공도 모든 원본 데이터 실험이나 사용자 PC에서의 실행을 재현했다는 뜻이 아니다. 오래된 중간 테스트 수보다 후속 검증 기록의 범위를 우선 확인했다.

새 샘플링 방식을 구현했어도 CV에서 기존 기준선을 개선하지 못했으면 최종 모델에 채택하지 않을 수 있다. 구현의 복잡성과 모델 선택 근거를 분리해서 설명하는 점이 중요했다.

### 3.2 다른 개발 작업에서 가져온 일반 원칙

당일 개발 변경·검증 기록을 검토하며 다음 원칙도 정리했다.

- 최적화 전에 프로파일링으로 호출 횟수와 누적 시간을 확인한다.
- 상위 함수와 하위 함수의 누적 시간은 겹칠 수 있으므로 그대로 합하지 않는다.
- 실행 환경·캐시·프로파일러 조건이 다르면 전후 시간 차이를 모두 코드 개선 효과로 해석하지 않는다.
- 중복 조회를 줄이는 것과 필요한 검증 자체를 생략하는 것은 다르다.
- 코드 검사, 합성 회귀, 패키지 설치 검사, 실제 운영 적용, 사용자 화면 확인은 각각 별도 근거로 기록한다.

구체적인 비공개 운영 정보나 원문 코드는 공개 학습 기록에 포함하지 않았다.
