## 1. 오늘 배운 것

### 1.1 파라미터는 입력값이고, 계산·필터와 연결되어야 작동한다

파라미터를 만든 것만으로 시각화가 달라지지는 않는다. 사용자가 선택한 값을 계산식이나 필터가 참조하도록 연결해야 한다.

- 지표 선택: 매출·이익·수량 중 선택한 값에 따라 표시할 계산을 바꾼다.
- 기준값 선택: 목표값과 실제 집계값을 비교한다.
- Top N 선택: 순위 필터가 참조할 N을 조절한다.
- 파라미터 액션: 차트에서 선택한 마크의 값을 파라미터로 전달한다.

설계 순서는 **답할 질문 → 사용자가 바꿀 기준 → 파라미터 → 계산·필터 → 결과 확인**이다. 문자열·숫자·날짜 등의 자료형과 허용값 목록·범위도 목적에 맞게 정한다.

### 1.2 필터는 종류보다 실행 순서와 적용 범위가 중요하다

화면에 같은 필터가 있어도 어떤 계산보다 먼저 적용되는지에 따라 결과가 달라진다.

- 컨텍스트 필터는 일반 차원 필터보다 앞서 데이터를 제한한다.
- FIXED LOD는 일반 차원 필터보다 먼저 계산되므로, 그 필터만 바꿨을 때 값이 그대로일 수 있다.
- FIXED가 모든 필터를 무시하는 것은 아니다. 데이터 원본·컨텍스트 등 앞선 단계의 필터는 영향을 준다.
- 테이블 계산 필터는 계산 후 표시할 마크를 제한하므로, 계산에 사용한 데이터까지 처음부터 제거하는 필터와 다르다.
- 빠른 필터는 조작 UI를 가리키는 표현이지 별도의 실행 단계가 아니다.

예를 들어 지역을 먼저 제한한 뒤 Top N을 구하려면 지역 필터를 컨텍스트로 만드는 방법을 검토한다. 여러 지역을 함께 선택하면 그 합집합에서 Top N을 구하는 것이며, 지역별로 각각 N개를 뽑는 것과는 다르다.

또한 필터를 현재 시트·선택한 시트·관련 데이터 원본의 시트 중 어디에 적용할지 확인해야 한다. 비교 기준으로 남겨 두려던 전체 지표까지 함께 바뀌면 해석이 달라진다. 컨텍스트 사용이 항상 성능을 높이는 것도 아니다.

### 1.3 대시보드 액션은 클릭 후의 상태까지 설계한다

- **필터 액션:** 선택과 관련된 데이터만 남긴다.
- **강조 액션:** 다른 데이터의 맥락은 유지하며 선택 항목을 눈에 띄게 한다.
- **URL 액션:** 관련 외부 페이지를 연다.
- **파라미터 액션:** 선택값을 계산에 사용할 입력으로 전달한다.
- **탐색:** 다른 화면으로 이동한다. 이동만으로 필터가 자동 전달된다고 가정하지 않는다.

출발 시트·대상 시트와 실행 방식(마우스 올림·선택·메뉴)을 정하고, 선택을 해제했을 때 전체 표시·제외·기존 필터 유지 중 무엇이 일어날지도 확인한다.

계층을 펼치는 드릴다운과 별도 상세 화면으로 이동하는 흐름도 구분한다. 여러 액션을 한 번의 클릭에 겹치기보다 **선택 → 해제 → 다른 항목 선택 → 상세 이동 → 복귀**를 실제 사용 순서대로 점검해야 한다.

### 1.4 시각화는 질문과 읽는 순서부터 정한다

대시보드 구성은 사용자의 의사결정과 핵심 지표에서 시작한다. 전체 현황 → 변화·비교 → 상세 원인 후보처럼 읽는 순서를 만든다.

- 색·위치·크기와 가까이 배치한 요소의 관계를 활용해 중요한 정보를 먼저 읽게 한다.
- 범주 구분용 색, 크기의 순서를 나타내는 색, 기준값 양쪽의 차이를 나타내는 색을 구별한다.
- 색만으로 의미를 전달하지 않고 제목·라벨도 사용한다.
- 불필요한 장식을 줄이더라도 단위·축·분모·출처·한계를 없애지는 않는다.
- 막대 길이 비교는 보통 0 기준이 중요하다. 선 그래프의 확대 축은 목적과 범위를 명확히 표시해야 한다.
- 이중 축이나 입체 표현이 차이를 과장하지 않는지 점검한다.

### 1.5 KPI는 이름보다 분모·기간·대상이 먼저다

가입자가 늘었는데 매출이 정체된 상황에서 재구매 부족은 가능한 가설이지 이미 확인된 원인이 아니다. 첫 구매 전환·재구매·객단가 등으로 나누어 데이터를 확인해야 한다.

KPI마다 다음을 명시한다.

1. 무엇을 세는가: 고객·주문·매출 중 측정 대상
2. 누가 분모인가: 가입자·첫 구매자·구매자 등
3. 언제까지 보는가: 기준일과 관찰 기간
4. 무엇을 제외하는가: 취소·환불·중복 주문 등의 처리

예를 들어 가입 후 일정 기간 내 첫 구매율과 첫 구매 후 일정 기간 내 재구매율은 출발점과 분모가 다르다. 아직 관찰 기간이 지나지 않은 신규 고객을 미구매·미재구매로 확정하면 최근 코호트가 불리해지는 **우측 검열** 문제도 생긴다.

SMART는 목표를 구체화하는 기준이며 지표 자체와 같지 않다. 북극성 지표 역시 사업 가치를 잘 대표하는지 확인할 후보이지 수익성이나 다른 진단 지표를 대체하는 만능 숫자가 아니다.

### 1.6 집계 단위가 잘못되면 그럴듯한 대시보드도 틀린다

고객·주문·배송 테이블은 한 행이 뜻하는 단위(grain)가 서로 다르다. 주문 하나에 배송 기록이 여러 개 있는 상태로 조인하면 주문 금액이 반복되어 합계가 커질 수 있다.

- 조인 전후 행 수·고유 키·결측·매출 합계를 비교한다.
- 관계 설정이나 사전 집계를 검토하되, 잘못된 키까지 자동으로 해결된다고 생각하지 않는다.
- 객단가를 `SUM(매출) / COUNTD(주문 ID)`로 계산해도 이미 중복된 매출 합계는 고쳐지지 않는다.
- 고객별 첫 구매일을 FIXED로 구할 때도 유효 주문의 정의와 필터 순서를 함께 확인한다.

또한 **전체 기간 주문 2회 이상**은 **첫 구매 후 정해진 기간 내 재구매**와 다르다. 특정 달의 첫 구매 코호트를 고를 때 후속 주문까지 그 달로 제한하면 재구매 관찰이 잘린다. 코호트 선택 기간과 행동 관찰 기간을 분리해야 한다.

비율 변화는 퍼센트와 퍼센트포인트를 구별하고, 변화가 보이면 표본 수와 구성 차이도 함께 확인한다. 쿠폰·채널과 지표의 연관만으로 인과 효과를 확정하지 않는다.

### 1.7 코딩테스트: 마지막 정상 요청 시점을 저장하는 딕셔너리

3장 1강의 중복 요청 문제에서 핵심은 사용자와 요청 ID를 묶은 키별로 **마지막 정상 처리 시점**을 저장하는 것이다.

- 같은 키의 새 요청이 제한 시간 이내라면 중복으로 센다. 경계값도 포함한다.
- 중복 요청은 저장된 정상 시점을 갱신하지 않는다.
- 처음 보거나 제한 시간을 지난 정상 요청일 때만 시점을 갱신한다.
- 입력이 시간순이라는 조건을 이용하면 평균적으로 요청 수에 비례하는 시간에 순회할 수 있다.

중복 요청 때마다 시간을 갱신하면 비교 기준이 마지막 요청으로 바뀌어 다른 문제를 풀게 된다. 상태를 언제 갱신하는지가 풀이의 의미를 결정한다. 이날은 풀이 설명을 확인했으며 직접 실행 결과는 기록하지 않는다.

## 2. 내가 궁금했던 질문과 이해한 답

### 문서를 wiki처럼 나누어 필요한 것만 읽으면 RAG 같은 역할을 하나?

넓은 의미에서는 관련 문서를 찾아 현재 질문에 필요한 문맥을 제공하는 역할을 할 수 있다. 벡터 데이터베이스가 반드시 필요한 것은 아니며 링크 탐색·파일 검색으로도 필요한 내용을 가져올 수 있다.

다만 문서를 쪼갰다는 사실만으로 검색 기반 생성이 자동 구현되거나 토큰이 줄어드는 것은 아니다. 결국 모든 문서를 다시 읽으면 이점이 작다.

- README: 프로젝트 개요와 주요 진입점
- AGENTS: 반드시 지켜야 할 규칙과 작업별 문서 안내
- 상세 문서: 주제별 기준·근거의 원본
- 코드·테스트: 문서 설명이 현재 구현과 맞는지 확인할 근거

항상 필요한 규칙을 깊은 링크 뒤에 숨기지 않고, 같은 설명의 복사본을 여러 곳에 두어 서로 어긋나지 않게 관리하는 것이 중요하다.

### 오늘 특히 눈여겨볼 개념은?

파라미터 문법을 외우는 것보다 **필터와 계산의 순서**, **한 행의 의미와 중복 집계**, **코호트의 관찰 기간**을 우선 확인해야 한다. 이 세 가지가 틀리면 화면이 정상적으로 표시되어도 숫자의 의미가 달라진다.

### 3.1 포트폴리오 문서의 정보 순서와 근거 보존

Airplane의 당일 변경에서는 문제·선택 이유·검증 결과를 먼저 배치하고 긴 상세 표를 접어 두는 구조를 확인했다. 좁은 화면을 고려해 개요 표를 목록으로 바꾸고 표지 글자를 키우는 변경도 있었다.

읽기 쉬운 반올림 수치와 원본 정밀 수치를 구분하고, 평가 집단·분모·한계를 결과 가까이에 남기는 것이 중요하다. 과거 실험을 설명하기 위한 문서 개선을 새로운 실험이나 성능 향상으로 기록하지 않는다.

[확인한 변경](https://github.com/Peter-jackson12/Airplane/commit/6a175683516d62b90069b4aa3496bdb7c5a00e9f)의 [CI](https://github.com/Peter-jackson12/Airplane/actions/runs/38210283829)는 성공했다. 자동 검사 성공과 모든 실제 화면·발표 자료 검수 완료는 별개다.

### 3.2 결정적인 테스트와 검증 수준의 구분

Career Agent의 당일 기록에서, 무작위로 만들어진 문자열에 특정 부분 문자열이 있을 것이라고 가정한 테스트는 변조가 실제로 일어나지 않을 수 있음을 확인했다. 의미가 명확한 필드나 바이트를 결정적으로 바꾸고, 변경이 실제 발생했는지까지 단언해야 회귀 테스트가 의도한 실패를 검사한다.

또한 의미가 같은 JSON이어도 원본 바이트 동일성을 검사하는 계약에서는 다시 저장한 파일이 다를 수 있다. 값의 의미를 비교할지 원본 표현까지 비교할지 먼저 정해야 한다.

[검증 기록](https://github.com/Peter-jackson12/career-agent/blob/e02b82a73daef0e0f780f2af99f703aa2c67e17d/docs/WS50_VALIDATION_20261012.md)에 적힌 로컬 테스트·격리 설치·합성 화면 점검은 저장소가 보고한 결과다. 이 TIL 작성 중 로컬에서 재실행한 것은 아니다. 해당 최신 문서 커밋의 [CI](https://github.com/Peter-jackson12/career-agent/actions/runs/38223203239)는 성공했지만, 실제 사용 환경의 업그레이드나 두 컴퓨터 간 전환 완료를 의미하지 않는다.

### 3.3 프로젝트 검토에서 정리한 일반 원칙

시간에 따라 상태가 달라지는 프로그램에서는 입력을 거르는 시점과 상태를 갱신하는 순서가 결과를 바꿀 수 있다. 최종 결과에서 일부 항목을 제거하는 방법이 입력 단계에서 조건을 적용한 뒤 상태를 다시 계산하는 방법과 같다고 가정하면 안 된다.

경계 시각·동일 시각·실패 후 재시도를 합성 입력으로 검증하고, 개발 과정에서 반복 확인한 데이터와 독립 평가 데이터는 구분해야 한다. 이는 검토에서 정리한 일반 원칙이며 새로운 실험을 직접 수행했다는 기록은 아니다.

- 액션 선택 해제·화면 복귀·복수 필터 조합에서 의도한 상태가 유지되는지 확인하기.
- KPI 계산 전에 조인 전후 합계와 코호트 관찰 기간이 보존되는지 점검하기.
- wiki형 문서에서 작업별로 필요한 문서만 찾아 읽는지, 필수 규칙과 최신 근거를 놓치지 않는지 확인하기.

당일 Tableau 실습 파일과 코딩테스트 실행 산출물은 이 기록의 확인 범위에 없다. `product_2` 기본 브랜치에서 당일 커밋은 확인되지 않았으며, 별도 로컬 자료가 없었다는 뜻은 아니다.
