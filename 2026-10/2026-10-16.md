## 1. 오늘 배운 것

### Claude Code 세션 압축은 고정 주기보다 맥락과 보존 기준이 중요하다

- `/context`로 컨텍스트 사용 상황을 확인하고, `/compact`는 기존 작업을 이어 가기 위해 대화의 앞부분을 요약한다. `/clear`는 이전 작업과 분리해 새 작업을 시작할 때 사용한다.
- 자동 압축은 모델과 세션의 컨텍스트 한도에 따라 발생한다. 모든 작업에 적용되는 하나의 적정 압축 주기가 공식적으로 정해져 있는 것은 아니다. 컨텍스트가 커졌거나 하나의 작업 단계가 끝났을 때를 기준으로 판단한다.
- 압축 요약에서는 실험 설정, 정확한 수치, 실패 원인, Git 상태, 미완료 작업 같은 세부 정보가 빠질 수 있다. 목표·제약·파일 경로·커밋·검증 결과·실패·다음 작업은 저장소 문서나 인계 기록처럼 세션 밖에서도 확인할 수 있는 곳에 남긴다.
- 이번 대화에서 정리한 운영안은 **컨트롤 타워 세션은 필요할 때 압축하고, 하위 작업 세션과 그 결과는 보관하는 방식**이다. 이는 사용자의 작업 방식에 맞춘 운영 제안이지, 공식 규칙이나 실제 세션에서 검증한 결과는 아니다.
- 압축 1회당 비용 절감 또는 추가 비용을 하나의 고정값으로 단정하지 않는다. 실제 사용량은 도구의 사용량 표시와 해당 계정·모델의 과금 기준으로 확인해야 한다.

### 네팔 지진 프로젝트 학습 세션 31~36단계 (ML)

사용자가 금요일에 진행한 학습 전용 세션(Google AI 모델 대화, 인계 문서는 1~30단계 완료 기준)의 기록을 직접 전달해 반영했다. 이 기록의 설명·표는 그 대화에서 AI가 제시한 것이며, 아래 "확인 범위"의 검증 결과를 함께 읽어야 한다. 실제 프로젝트 수치(G2, Group CV 등)는 인계 문서에 "기존 연구 기록 인용"으로 적힌 값이고 이번에 독립 검증하지 않았다.

- **31단계 희소 범주 묶기(Rare Category Grouping):** `value_counts()` → `counts[counts < 5].index` → `isin()`·`~`·`where()`로 희소 조합을 `Other`로 묶는 방법. 임계값 5는 실습용 임의 기준이고, 목조와 철근콘크리트처럼 성격이 다른 범주가 `Other`에 섞이면 정보가 희석될 수 있다. 빈도 기준은 **Train(Fold)에서만 계산(fit)** 하고 Validation에는 그 목록을 적용(transform)해야 하며, Train에 없던 새 범주는 `Other`로 보낸다. 정답(`damage_grade`)을 쓰는 타깃 누수와 입력 변수 빈도만 쓰는 분포 누수를 구분했다.
- **32단계 파생 변수 후보 점검:** 0으로 나눈 `inf`(`replace(0, np.nan)`), 새로 생긴 결측, `age=995`가 `age_per_floor`로 번지는 이상값 전파, 기존 변수의 선형 결합 수준인 중복 변수(상관 0.95 이상 의심)를 투입 전 확인하는 3가지 체크.
- **질문과 답: 피처 엔지니어링과 하이퍼파라미터 튜닝의 차이.** 피처 엔지니어링은 모델에 보여 줄 입력 정보를 만드는 일, 튜닝은 알고리즘의 학습 강도·제약을 조정하는 일이다. 입력이 바뀌면 적절한 파라미터도 바뀔 수 있으므로 보통 베이스라인 → 피처 → 모델 비교 → 튜닝 순으로 진행한다고 정리했다. (대화에서 "성능 향상의 80%", "0.03~0.05 대 0.003~0.008" 같은 수치는 일반적인 경험칙으로 제시된 것이며 근거 자료는 확인하지 못했다.)
- **33단계 파생 변수 투입 전후 비교:** 같은 `StratifiedKFold` 분할 위에서 Baseline과 +Feature를 Fold별로 짝지어 비교하고, 평균 차이·Fold 승패·표준편차 변화와 위험 오류(3→1) 증가 여부를 함께 본다.
- **34단계 로지스틱 회귀와 트리 모델의 상호작용:** 선형 모델은 `height/floors` 같은 비율을 직접 만들어 주어야 하고, 트리는 중첩 분할로 상호작용을 어느 정도 근사하지만 `max_depth`가 제한되면 비율 변수가 분할 수를 아껴 준다는 설명.
- **35단계 미관측 지역 일반화:** 지역 원-핫 변수를 넣은 모델은 Stratified CV에서 점수가 높아도 `GroupKFold`(지역 기준)에서는 크게 떨어질 수 있다. 지역 번호는 지진 강도의 대리 변수일 수 있고, 검증 방식은 배포 환경(사후 복구 vs 미래 진단)에 맞춰야 한다. 설명 중 네팔 1차 지역 Group CV의 Macro F1 0.365650, 3등급 Recall 0.631%는 기존 프로젝트 기록의 인용이다.
- **36단계 오류 주도 피처 엔지니어링:** `pd.crosstab`으로 오차 행렬을 만들고, 실제 3등급·예측 1등급 행만 슬라이싱해 정답 그룹과 `groupby().agg()`로 비교한 뒤, 발견한 조건(시멘트이면서 4층 이상)을 플래그 변수로 만드는 흐름. 가상 데이터 30채에서는 그 규칙을 정답 생성 규칙에서 그대로 가져왔기 때문에 오류가 0이 되는 것은 당연한 결과이며, 실제 일반화 성능의 증거는 아니다.
- 37단계(프로젝트 연구 사례 종합)는 예고만 있었고 진행 기록은 없다.

## 2. 내가 궁금했던 질문과 이해한 답

### 압축은 얼마나 자주 해야 할까?

매번 같은 대화 길이나 일정한 시간 간격을 기준으로 삼기보다, 컨텍스트 사용량과 작업의 논리적 경계를 함께 본다. 압축 전에 현재 상태를 기록하고, 압축 후 요약에 핵심 결정과 미완료 항목이 남았는지 확인하는 것이 중요하다.

### 컨트롤 타워와 하위 세션은 어떻게 관리할까?

컨트롤 타워는 전체 방향과 의사결정을 이어 가도록 압축할 수 있지만, 하위 세션의 원문·실행 결과·검증 자료는 보관한다. 세션 요약을 프로젝트의 유일한 진실 공급원으로 삼지 않고 Git 커밋, 보고서, 실험 데이터와 테스트 결과를 기준 자료로 유지한다.

### 문제: 키움 버전 업데이트 날 수집기가 로그인 대기에서 멈췄다

- 10/16 아침 첫 수집 시작이 "서버 접속 시도 중"에서 멈췄고, 사용자가 중지·재시작한 뒤에야 수집이 시작됐다. 9/16~10/16 키움 버전처리 로그(VerLog) 20개를 전수 확인하니 10/8에도 같은 실패가 있었다.
- 설계 문서가 VerLog로 재구성한 순서:
  1. 수집기 `CommConnect()` → 키움 starter가 서버 파일과 로컬 파일 CRC 비교
  2. OCX·DLL CRC가 다르면 업데이트 프로그램(`opversionup`)이 starter를 종료하고 파일 교체 시도
  3. 32비트 수집 프로세스가 OCX를 로드한 채 로그인 이벤트를 기다리고 있어 삭제 실패(`Access denied`)
  4. starter가 종료돼 로그인 이벤트가 오지 않고, 수집기에는 로그인 타임아웃이 없어 계속 대기
- 원인은 "업데이트 실패"가 아니라 **내 프로세스가 교체 대상 파일을 잡고 있었다**는 것이다. 일부 구간(약 3분 공백, 키움 자동 재실행 여부)은 문서에 추측으로 표시돼 있다.

### 대책 비교와 선택

| 후보 | 판단 |
|---|---|
| 수집 전 별도 프로세스로 로그인·버전 확인 | 확인 프로세스도 OCX를 로드하므로 같은 충돌 → 채택 안 함 |
| 로그인 대기 중 업데이트를 감지해 원본 생성 전 스스로 종료 | 업데이트가 삭제를 시도하기 전(로그상 약 11~23초 여유)에 OCX를 놓을 수 있음 → **채택** |
| 업데이트 뒤 자동 재시작 | 자동 로그인·재시작은 운영 원칙 밖 → 별도 과제 |

- 신호: 1초마다 `opversionup` 프로세스 존재(ctypes Toolhelp32, subprocess 없이) 또는 VerLog의 새 `NKVersionUp 실행`·`파일 삭제 실패` 줄. 원본 생성 전 로그인 타임아웃 300초도 추가했다(사용자 결정).
- **원본을 만든 뒤에는 절대 스스로 종료하지 않는다.** 그때는 60초마다 경고만 남긴다. 원본 전 종료는 상태를 `failed`가 아닌 `cancelled`로 남겨 기존 "취소 복구" 버튼을 그대로 쓰게 했다.
- 독립 리뷰에서 반영한 것: 프로세스 열거가 정상 종료(`ERROR_NO_MORE_FILES`)가 아니면 오류로 올려 경고 경로로 보냄, 핸들은 항상 닫음, `PROCESSENTRY32W` 크기(32비트 556 / 64비트 568)를 테스트로 고정, 감지 패턴을 `^opversionup`으로 좁힘, VerLog를 처음부터 다시 읽을 때 감시 시작 전 시각의 줄은 무시.
- 테스트는 가짜 OCX·합성 프로세스 목록만 쓰고 실제 로그인·키움 폴더에 접근하지 않는다. 실제 업데이트 상황 실측은 아직 없다(미확인).

### 개장 지연일(수능날 등)의 침묵 종료 판정

- 수집기는 09:00 이후 체결·호가가 600초 없으면 피드 이상으로 보고 종료를 시도한다. 개장이 늦어진 날엔 정상 수집기가 스스로 멈출 위험이 코드상 있다(실측 없음). 위 1절의 NXT 수능일 공지 확인과 같은 맥락이다.
- 콘솔이 그날 개장 시각 파일(해시 동봉)을 넘기면 수집기는 **침묵 종료 판정 창만** 옮긴다. 공식 근거가 없거나 파일 검증이 실패하면 "첫 KRX 정규 체결부터(11:00까지 없으면 11:00부터)"로 판정한다. 잘못 멈추는 위험보다 늦게 알아채는 위험을 택한 절충이다. 파일 검증 실패가 수집 시작 자체를 막지는 않는다.
- 연구 쪽 규칙: 개장 지연일은 기본 통계에서 제외하고 개장 후 상대 시각 결과를 따로 보고하며, 그날은 매매하지 않는다.
- 옛 수집기는 모르는 요청 키를 오류 없이 무시하므로, 새 콘솔만 올리면 적용된 것처럼 보이는 조용한 실패가 생긴다. 그래서 호환표를 만들고 수집기·콘솔을 **쌍으로 배포·롤백**하기로 했다(실제 배포는 10/19 저녁).
